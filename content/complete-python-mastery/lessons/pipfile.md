## دو فایلی که Pipenv خودکار می‌سازه

هر بار که با `pipenv install` یه پکیج نصب می‌کنی، دو فایل توی پروژه ساخته یا به‌روزرسانی می‌شن: `Pipfile` و `Pipfile.lock`. این دو فایل با هم، وابستگی‌های پروژه و نسخه‌ی دقیقشون رو ثبت می‌کنن.

## `Pipfile`: چه پکیج‌هایی، با چه محدودیت نسخه‌ای

```ini
[source]
url = "https://pypi.org/simple"

[dev-packages]

[packages]
requests = "*"

[requires]
python_version = "3.7"
```

- `[packages]`: پکیج‌هایی که برنامه‌ی اصلی بهشون نیاز داره. علامت `*` یعنی «هر نسخه‌ای» (چون هنگام نصب، نسخه‌ی خاصی مشخص نکردیم).
- `[dev-packages]`: پکیج‌هایی که فقط حین توسعه لازمن (مثلاً ابزارهای تست) — برای اجرای واقعی برنامه ضروری نیستن.
- `[requires]`: نسخه‌ی پایتونی که این پروژه بهش نیاز داره.

## `Pipfile.lock`: نسخه‌ی دقیق هر پکیج

`Pipfile` فقط می‌گه «چه پکیجی، با چه محدودیتی» — ولی `Pipfile.lock` (یه فایل JSON) دقیقاً می‌گه **چه نسخه‌ی مشخصی** روی این سیستم نصب شده، شامل وابستگی‌های غیرمستقیم (پکیج‌هایی که خودِ `requests` بهشون نیاز داره، نه چیزی که خودمون مستقیم نصب کردیم).

## چرا این تفکیک مهمه: تکرارپذیری روی سیستم دیگه

فرض کن پروژه رو روی یه سیستم دیگه (مثلاً سرور production) کپی می‌کنی — بدون پوشه‌ی محیط مجازی، فقط کد و این دو فایل. با این دستور، همه‌ی وابستگی‌ها نصب می‌شن:

```bash
pipenv install
```

اگه `Pipfile` بگه `requests = "*"`، Pipenv **آخرین نسخه‌ی موجود در آن لحظه** رو نصب می‌کنه — که ممکنه با نسخه‌ای که روی سیستم توسعه نصب بود فرق داشته باشه! برای جلوگیری از این ناسازگاری، می‌شه گفت دقیقاً همون نسخه‌های ثبت‌شده توی `Pipfile.lock` نصب بشن:

```bash
pipenv install --ignore-pipfile
```

این تضمین می‌کنه محیط production دقیقاً همون نسخه‌هایی رو داره که موقع توسعه تست کردی — یکی از رایج‌ترین دلیل‌های «روی سیستم من که کار می‌کرد» رو از بین می‌بره.

## جمع‌بندی

- `Pipfile`: چه پکیج‌هایی، با چه محدودیت نسخه‌ای (خوانا برای انسان).
- `Pipfile.lock`: نسخه‌ی دقیق هر پکیج و وابستگی‌هاش (برای بازتولید دقیق محیط).
- `pipenv install --ignore-pipfile`: نصب دقیقاً طبق `Pipfile.lock`، نه `Pipfile`.
