## کش‌کردن

کش‌کردن (caching) یکی از پراستفاده‌ترین الگوهای معماری توی نرم‌افزاره، ولی همیشه درست استفاده نمی‌شه. بیا اول مفهوم پایه‌ش رو توضیح بدیم: با استفاده از cache، داده رو به مصرف‌کننده‌ش نزدیک‌تر می‌کنیم تا بازیابیش سریع‌تر باشه.

### دو مثال

همه‌ی مرورگرهای مدرن cache دارن. نقشِ cache توی مرورگر ساده‌ست: وقتی یه صفحه‌ی وبِ خاص رو مرور می‌کنی، به‌جای درخواست از سرور راه دور، صفحه از حافظه‌ی مرورگر بازیابی می‌شه و خیلی سریع‌تر نمایش داده می‌شه. توسعه‌دهنده‌ها می‌تونن cache رو غیرفعال کنن تا مطمئن بشن صفحه‌ی نمایش‌داده‌شده همیشه به‌روز باشه.

یه مثال دیگه که برای ما معمارها مرتبط‌تره: یه سرویس نیاز به داده از دیتاستور داره — فرض کن دیتاستور یه دیتابیس رابطه‌ای مثل SQL Server‌ـه. طبیعتاً سرویس یه کد توی لایه‌ی دسترسی به داده داره که به دیتابیس وصل می‌شه و دستورات SQL برای بازیابیِ داده صادر می‌کنه. این عملیاتِ بازیابی می‌تونه زمان‌بر باشه — دیتابیس باید دستور SQL رو کامپایل کنه، داده رو بازیابی کنه، و بعد کد باید داده رو به آبجکت‌هایی که باهاشون کار می‌کنه سریالایز کنه — همه‌ی این‌ها می‌تونن زمان ببرن. اضافه کن به این، احتمال اینکه دیتابیس فیزیکاً از کد فاصله داشته باشه، و یه فرایندِ ناکارآمد به دست میاد.

برای جلوگیری از این تأخیر، می‌تونیم از cache استفاده کنیم. cache یه لایه‌ی دیگه‌ست که معمولاً بین دیتاستور و لایه‌ی منطق کسب‌وکار می‌شینه و داده رو طوری ذخیره می‌کنه که بازیابیش خیلی راحت و سریع باشه. موتورهای cache معمولاً داده رو توی حافظه (memory) نگه می‌دارن، که بازیابی رو فوق‌العاده سریع می‌کنه. بعضی موتورها — مثل Redis — به‌صورت دوره‌ای داده رو روی دیسک هم ذخیره می‌کنن، ولی همچنان بازیابی از حافظه انجام می‌شه.

### مصالحه‌ی cache

موتورهای cache یه مصالحه در مقایسه با دیتابیس‌های سنتی ارائه می‌دن: **cache قابلیت‌اطمینان رو با performance مبادله می‌کنه.** داده‌ای که توی حافظه ذخیره می‌شه، فراره و توی صورت کرش‌کردنِ سرور از دست می‌ره. از طرف دیگه، در مقایسه با دیتابیس‌های سنتی — که معمولاً داده رو روی دیسک ذخیره می‌کنن — عملکرد بهتری داره. به همین دلیل، تقریباً همیشه به دیتابیس به‌عنوان **منبع حقیقتِ واحد (single source of truth)** نگاه می‌کنیم — یعنی داده‌ی واقعیِ اصلی توی دیتابیس ذخیره شده، و اگه داده توی cache نبود، برمی‌گردیم و از دیتابیس بازیابیش می‌کنیم.

### کِی و چی رو کش کنیم؟

به‌عنوان معمار، باید بتونیم تعیین کنیم آیا، کِی و چطور باید از cache توی سیستممون استفاده کنیم. برای این کار، بیا نوع داده‌ای که می‌خوایم کش کنیم رو تعریف کنیم. قاعده‌ی سرانگشتی اینه:

> Cache باید داده‌ای رو نگه داره که **زیاد خونده می‌شه** و **کم تغییر می‌کنه**.

دلیلش ساده‌ست: اگه داده زیاد خونده می‌شه، می‌خوایم بازیابیش سریع و راحت باشه تا تجربه‌ی کاربری بهینه بشه و حداقل بار روی سیستم بمونه. با گذاشتنِ داده توی cache، دقیقاً همین رو به دست میاریم — فرایندِ بازیابی سبک‌وزنه چون داده توی حافظه‌ست و به هیچ عملیات I/O نیاز نیست، در نتیجه خیلی سریعه.

از طرف دیگه، داده باید کم تغییر کنه. دلیلش اینه: یکی از بزرگ‌ترین چالش‌های cache، هم‌گام نگه‌داشتنش با دیتاستور — همون منبع حقیقت — ه. اگه دیتاستور و cache همگام نباشن و داده‌ی متفاوت داشته باشن، می‌تونه به خرابیِ داده و تجربه‌ی کاربریِ بد منجر بشه.

### یه مثال از مشکل

فرض کن اپلیکیشنمون داده‌ی قیمت سهام رو می‌گیره و به کاربر نمایش می‌ده. برای سرعت، داده توی cache ذخیره می‌شه. طبیعتاً داده‌ی سهام خیلی زیاد تغییر می‌کنه — فرض کنیم هر ثانیه عوض می‌شه. بیشتر کاربرها این داده رو دائم جلوی چشمشون دارن، پس می‌بینن اعداد به‌صورت زنده تغییر می‌کنن — که با بخشِ «زیاد خونده می‌شه»ی قاعده‌مون همخوانی داره.

حالا وقتی داده — که یادته هر ثانیه تغییر می‌کنه — عوض می‌شه، چه اتفاقی می‌افته؟ فرض کن سیستم از الگوی قبلی پیروی می‌کنه — یعنی سه سرور با یه load balancer جلوشون. توجه کن که هر سرور، cache خودش رو داره. فرض کن سرویس یه API برای به‌روزرسانیِ کدِ سهام در معرض دید می‌ذاره. یه فراخوانیِ جدید به این API می‌رسه و load balancer اون رو به سرور شماره‌ی یک مسیریابی می‌کنه. سرور داده رو می‌گیره، دیتابیس مرکزی رو به‌روز می‌کنه، و cache خودش رو هم به‌روز می‌کنه. و اینجاست مشکل: cache روی سرورهای دیگه، داده‌ی کهنه (stale) داره — یعنی داده‌ای که دیگه مرتبط نیست. cacheهای دیگه در نتیجه‌ی این فراخوانیِ API به‌روز نشدن. پس حالا دو سرور داده‌ای دارن که به‌روز و مرتبط نیست، و وقتی کاربر قیمت سهام رو بخواد و load balancer درخواست رو به یکی از این سرورها بفرسته، کاربر داده‌ی اشتباه می‌بینه — که بده.

### دو نوع cache

برای فهمیدنِ راه‌حل، بیا انواع cache رو دسته‌بندی کنیم. به‌طورکلی دو نوع cache داریم: **cache درون‌حافظه/درون‌فرایند (in-memory in-process)** و **cache توزیع‌شده (distributed)**.

**درون‌حافظه/درون‌فرایند:** یه پیاده‌سازیِ cache‌ـه که بخشی از کدِ خودِ سرویسه. از حافظه‌ی سرویس استفاده می‌کنه و به‌عنوان بخشی از فرایند سرویس اجرا می‌شه. تقریباً همه‌ی زبان‌های برنامه‌نویسی، کتابخونه‌هایی برای cache درون‌حافظه دارن، و راستش برای پیاده‌سازیِ ساده، می‌تونی از یه collection concurrent استاتیک استفاده کنی و کارت راه بیفته. همون‌طور که حدس می‌زنی، cache درون‌حافظه توی performance عالیه، چون دسترسی بهش دقیقاً مثل صدازدن یه کلاس توی کده که داده رو از حافظه‌ی همون فرایند می‌گیره. از طرف دیگه، توی اندازه محدوده، چون فقط می‌تونه به اندازه‌ی حافظه‌ی فرایند (معمولاً چند گیگابایت) داده نگه داره.

**توزیع‌شده:** یه موجود کاملاً متفاوته. یه محصول جداست که داده‌ی cache‌شده رو توی یه فرایند جدا نگه می‌داره و یه اینترفیسِ راحت برای دسترسی به داده ارائه می‌ده. بهترین بخشِ cache توزیع‌شده اینه که واقعاً توزیع‌شده‌ست — یعنی فضای ذخیره‌سازیِ cache روی سرورهای مختلف پخش می‌شه، و این به cache توزیع‌شده اجازه می‌ده داده‌ی خیلی بزرگی رو ذخیره کنه — اندازه‌ی cache فقط محدود به مجموعِ حافظه‌ی همه‌ی سرورهاییه که cache روشون نصب شده. موتورهای cache توزیع‌شده معمولاً به‌عنوان سرویس روی سرورها نصب می‌شن و هر سرویس، یه «نود» نامیده می‌شه. نکته‌ی جالب درباره‌ی موتورهای cache توزیع‌شده اینه که نودها به‌صورت داخلی همگام می‌شن، و این مسئولیتِ خودِ مکانیزمِ cache‌ـه که مطمئن بشه همه‌ی نودها از داده‌ی جدید خبردارن. پس وقتی یه سرور خاص cache رو به‌روز می‌کنه، بلافاصله بین بقیه‌ی نودها هم توزیع می‌شه — این‌طوری همه‌ی سرورهای دیگه هم‌گام می‌مونن و داده‌ی یکسانی دارن.

### پس ضعفِ cache توزیع‌شده چیه؟

جواب: performance. cache درون‌حافظه/درون‌فرایند فوق‌العاده سریعه چون توی همون فرایند و با همون کد اجرا می‌شه. با cache توزیع‌شده، این مزیت رو نداریم — cache توی یه فرایند دیگه، و بعضی‌وقت‌ها حتی روی یه سرور دیگه اجرا می‌شه، که یه عملیات شبکه به فرایند بازیابی اضافه می‌کنه. علاوه بر این، بیشتر موتورهای cache توزیع‌شده فقط اجازه‌ی ذخیره‌ی انواع پایه (رشته، عدد و…) رو می‌دن، درحالی‌که cache درون‌حافظه/درون‌فرایند می‌تونه هر چیزی رو ذخیره کنه — که این هم یه مزیتِ performance دیگه‌ست، چون نیازی به سریالایز و دی‌سریالایز‌کردنِ داده نیست.

### برگردیم به قاعده‌مون

بحثِ «کم تغییر می‌کنه» رو نیمه‌کاره گذاشتیم. اگه داده زیاد تغییر کنه — مثل داده‌ی قیمت سهام — و از cache درون‌حافظه/درون‌فرایند استفاده کنیم، باید یه مکانیزم برای همگام‌سازیِ بین داده‌ی دیتابیس و هر کدوم از cacheهای درون‌حافظه بسازیم. این مکانیزم دائم دیتابیس رو زیر فشار می‌ذاره و یکی از مزایای اصلیِ cache — یعنی کاهشِ بار روی سیستم — رو از دست می‌دیم. از طرف دیگه، اگه از cache توزیع‌شده استفاده کنیم، احتمالاً مشکلی نداریم — داده‌ی به‌روزشده بلافاصله بین همه‌ی نودها همگام می‌شه و سرورها به داده‌ی تازه دسترسی دارن.

### جمع‌بندی: کدوم رو کِی؟

| | درون‌حافظه/درون‌فرایند | توزیع‌شده |
|---|---|---|
| Performance | فوق‌العاده سریع | کندتر (به خاطر شبکه) |
| اندازه‌ی حداکثر | محدود به حافظه‌ی یه فرایند | مجموعِ حافظه‌ی همه‌ی نودها |
| هم‌گامیِ بین سرورها | باید خودت پیاده کنی | خودکار |
| نوع داده‌ی قابل‌ذخیره | هر چیزی | معمولاً فقط انواع پایه |
| پیچیدگیِ راه‌اندازی | ساده، مثل استفاده از یه کلاس | نیاز به آموزش و راه‌اندازی |

از **cache توزیع‌شده** استفاده کن اگه به توزیع بین سرورها، failover و ذخیره‌ی حجم بالا نیاز داری. از **cache درون‌حافظه/درون‌فرایند** استفاده کن اگه بهترین performance ممکن و ذخیره‌ی آبجکت‌های پیچیده رو می‌خوای.
