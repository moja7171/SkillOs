## طراحی سرویس لاگ‌گیری

سرویسِ لاگ، اولین سرویسیه که جزئیاتش رو بررسی می‌کنیم. شاید یه‌کم عجیب به نظر برسه — بالاخره این کسل‌کننده‌ترین سرویسه. بیا با یه چیزِ جالب‌تر شروع کنیم — نه؟

خب، دلیلی که با همین سرویس شروع می‌کنیم دوتاست. **اول**، می‌خوایم تأکید کنیم که لاگ‌گیری مهمه. خیلی از توسعه‌دهنده‌ها، و متأسفانه معمارها، لاگ‌گیری رو یه فکرِ بعدی می‌بینن. ولی این روشِ درستِ برخورد باهاش نیست. لاگ‌گیری یکی از سنگ‌بناهای هر اپلیکیشنیه و باید مثل هر سرویسِ دیگه‌ای باهاش رفتار بشه. **دوم**، می‌خوایم همه‌ی سرویس‌هامون رو طوری بسازیم که از همون اول لاگ‌گیری توشون باشه، نه اینکه بعداً اضافه بشه. برای این کار، باید سرویسِ لاگ آماده باشه تا بقیه‌ی سرویس‌ها بتونن باهاش ارتباط برقرار کنن.

درسته که توی اپلیکیشنِ خاصِ ما، سرویسِ لاگ از یه صف می‌خونه و مستقیم با سرویس‌های دیگه تعامل نداره — ولی همچنان، همیشه ایده‌ی خوبیه که از اینجا شروع کنیم.

### قدم‌های جزئیاتِ هر جزء

اینا قدم‌هاییه که برای جزئیاتِ هر جزء لازمه: **اول**، نوعِ اپلیکیشن رو تعیین کن — اپ وب؟ سرویس؟ دسکتاپ؟ **دوم**، پشته‌ی فناوریِ جزء رو تعیین کن. **سوم**، معماری رو طراحی کن.

### نوعِ اپلیکیشن

برای این، باید یادمون باشه سرویسِ لاگ قراره چیکار کنه: باید رکوردهای لاگ رو از یه صف بخونه، شاید یه اعتبارسنجی انجام بده، و بعد توی دیتاستور ذخیره‌شون کنه. و اینجا نکته‌ی مهمیه: سرویسِ لاگ منتظرِ هیچ درخواستی نیست. همیشه روشنه و هر چند وقت یه‌بار داده رو از صف pull می‌کنه.

بیا ببینیم این چطور با انواعِ اپلیکیشن‌ای که می‌شناسیم جور درمیاد. **اپ وب و وب API** هر دو خارج از بحثن، چون همون‌طور که گفتیم، سرویسِ لاگ بر پایه‌ی مدل درخواست-پاسخ نیست، بلکه همیشه آنلاینه و فعالیتش رو خودش شروع می‌کنه. قطعاً **اپلیکیشنِ موبایل** هم نیست — روی سرور اجرا می‌شه، نه کلاینت. **کنسول** چطور؟ به نظر می‌رسه یه انتخابِ خوبه. اپلیکیشن‌های کنسول بهترین گزینه برای فرایندهای طولانی‌مدت با رابط کاربریِ محدودن — دقیقاً همون چیزی که از سرویسِ لاگ می‌خوایم. نیازی به هیچ UI نداریم و این یه فرایندِ طولانی‌مدته. پس این یه کاندیدای خوبه. بعدی، **سرویس**. یادته سرویس‌ها خیلی شبیهِ کنسول‌ان، با دو فرقِ مهم: هیچ UI‌ای اصلاً ندارن و توسط یه نوع مدیرِ سرویس مدیریت می‌شن. پس به نظر می‌رسه سرویسِ لاگ می‌تونه یه سرویس هم باشه. آخری، **اپلیکیشنِ دسکتاپ** که البته برای سرویسِ لاگ که روی سرور اجرا می‌شه اصلاً مرتبط نیست.

پس با اپ کنسول و سرویس می‌مونیم. کدوم بهتره؟ راستش جوابِ قطعی‌ای نداره و عمدتاً به سلیقه‌ی شخصی بستگی داره. ترجیح می‌دیم به‌عنوانِ سرویس بسازیمش، ولی اگه به‌عنوانِ اپلیکیشنِ کنسول طراحیش کنی هم اشتباهی نکردی.

### پشته‌ی فناوری

خب، حالا نوعِ اپلیکیشن رو داریم. بریم سراغِ پشته‌ی فناوری. یادته موقعِ تصمیم‌گیری درباره‌ی پشته‌ی فناوری، اول باید تعیین کنیم چه عناصری توی جزء نیاز به انتخابِ پشته دارن؟ توی سرویسمون، دو عنصر هست: کدِ خودِ جزء و دیتاستور.

بیا با کد شروع کنیم. چون سرویسِ لاگ قراره یه سرویس باشه، نیازمندیِ خاصی از پشته‌ی فناوری نداریم. فقط لازمه کد بتونه به API صف دسترسی داشته باشه و داده رو توی یه دیتاستور ذخیره کنه. این کارِ خاصی نیست و هر پلتفرمِ توسعه‌ای می‌تونه انجامش بده. علاوه بر این، هیچ نیازمندیِ ویژه‌ای درباره‌ی performance نداریم — البته می‌خوایم سریع باشه، ولی نیازمندیِ خاصی محدودمون نمی‌کنه.

پس حالا وقتشه بریم سراغِ توسعه‌دهنده‌ها و ببینیم با چه پلتفرم‌هایی تجربه دارن. بیا این کار رو بکنیم. به نظر می‌رسه تیم توسعه با پشته‌ی مایکروسافت — یعنی پلتفرمِ .NET و SQL Server — آشناست. این خوبه، چون .NET یه پلتفرمِ عمومیه که می‌شه توی سرویس‌ها و اپ‌های وب هم ازش استفاده کرد، و این وقتی بریم سراغِ سرویس‌های دیگه، مفید خواهد بود.

تنها نکته‌ش اینه که .NET یه‌کم قدیمی شده و پروژه‌های جدید باید از .NET Core استفاده کنن — نسل بعدیِ کراس‌پلتفرم و ماژولارِ .NET. تیم با .NET Core آشنایی نداره، ولی بعد از یه بحثِ کوتاه، درباره‌ی یه فرایندِ آموزش به توافق می‌رسیم و تصمیم می‌گیریم سرویس بر پایه‌ی .NET Core باشه و دیتابیس هم SQL Server.

نکته‌ای که باید ذکر بشه: اگه تیم مثلاً با Java و MySQL آشنا بود، اون هم عالیه. Python و Postgres هم همین‌طور. تقریباً هر ترکیبی کار می‌کنه، فقط باید پلتفرم بتونه به‌شکلِ کنسول یا سرویس پیاده بشه و به دیتابیس دسترسی داشته باشه.

### طراحیِ معماری

خب، پشته‌ی فناوری رو داریم. حالا بیا معماری رو طراحی کنیم. یادته بحثمون درباره‌ی معماریِ لایه‌ای — که گفتیم توی بیشترِ موارد، معماریِ پیش‌فرضِ هر جزءه؟ خوبه، بیا ببینیم اینجا هم جواب می‌ده یا نه.

یادته معماریِ لایه‌ای سه لایه داره: رابط کاربری/سرویس (UI/SI)، منطقِ کسب‌وکار (BL) و دسترسیِ داده (DAL) که توی دیتاستور می‌نویسه. حالا فکر می‌کنی این الگو اینجا جواب می‌ده؟ چند لحظه بهش فکر کن.

خب، امیدواریم یه نظر داشته باشی درباره‌ی اینکه آیا معماریِ لایه‌ای برای سرویسِ لاگ مناسبه یا نه. جواب اینه: مناسبه، ولی نه دقیقاً. مسئله‌ی اصلی، لایه‌ی اوله — UI یا API. سرویسِ لاگ هیچ UI یا APIای نداره. یه فرایندِ طولانی‌مدته و هیچی رو در معرض دید نمی‌ذاره — نه API، نه رابط کاربری. بقیه‌ی لایه‌ها واقعاً مرتبطن — به لایه‌ی BL برای مدیریتِ رکوردهای لاگ نیاز داریم و به لایه‌ی DAL برای دسترسی به دیتابیس.

پس کاری که می‌کنیم اینه که الگوی لایه‌ای کلاسیک رو کمی تغییر می‌دیم و لایه‌ی بالایی رو به یه **لایه‌ی polling** تبدیل می‌کنیم. این لایه مسئولِ دسترسی به صف و بازیابیِ رکوردهای لاگیه که باید توسط لایه‌ی منطقِ کسب‌وکار مدیریت بشن.

### جریانِ کار

پس این جزء چطور کار می‌کنه؟ چه جریانی رو پیاده می‌کنه؟ لایه‌ی polling یه تایمر اجرا می‌کنه که هر چند ثانیه صف رو poll می‌کنه. اگه رکوردهای جدیدی از صف برگردن، لایه‌ی polling می‌فرستدشون به لایه‌ی منطقِ کسب‌وکار. این لایه اعتبارسنجیشون می‌کنه و مطمئن می‌شه هیچ داده‌ی آشغالی فرستاده نشده. اگه همه‌چیز درسته، می‌فرستدشون به لایه‌ی دسترسیِ داده، که توی دیتابیس ذخیره‌شون می‌کنه. و این اساساً معماریِ درونیِ سرویسِ لاگه.

### یه نکته‌ی دیگه: تزریق وابستگی

یادته بحثمون درباره‌ی تزریق وابستگی — چطور وابستگی بینِ اجزای کد رو حذف می‌کنه؟ خوبه، توی سرویسِ لاگ ازش استفاده می‌کنیم تا بینِ لایه‌ی polling و لایه‌ی منطقِ کسب‌وکار، و بینِ لایه‌ی منطقِ کسب‌وکار و لایه‌ی دسترسیِ داده، اتصالِ محکم نداشته باشیم. خوشبختانه، .NET Core یه مکانیزمِ تزریق وابستگیِ عالی از قبل توش تعبیه شده — پکیجِ Microsoft.Extensions.DependencyInjection — که کارِ سنگین رو برامون انجام می‌ده. راستش وقتی تزریق وابستگی این‌قدر از قبل تعبیه‌شده باشه، واقعاً سخته دلیلی برای استفاده‌نکردن ازش پیدا کنی.

کدی که polling صف و اعتبارسنجی رو مدیریت می‌کنه، یه کدِ ساده و بدونِ کتابخونه‌ی بیرونیه. لایه‌ی دسترسیِ داده هم از Entity Framework برای دسترسی به دیتابیس و ذخیره‌ی رکوردها استفاده می‌کنه — این کتابخونه قابلیت‌های ORM بهمون می‌ده که اساساً رکوردهای دیتابیس رو به‌شکلِ آبجکت‌های کامل نمایش می‌ده.

### جمع‌بندی

عالیه، اولین سرویسمون رو طراحی کردیم. حالا یه معماریِ کامل برای سرویسِ لاگ داریم، همراه با نوعش و پشته‌ی فناوریش. امیدواریم از این تجربه لذت برده باشی و آماده باشی برای سرویسِ بعدی — که حداقل به‌همون‌اندازه سرگرم‌کننده خواهد بود.
