## بخش نیازمندی‌ها

بخشِ بعدی توی سند معماری، بخشِ نیازمندی‌هاست. این هم یه بخشِ کوتاهه — معمولاً نه‌بیشتر از یه صفحه، اغلب کمتر — و مخاطبش هم همه‌ی اعضای تیم و مدیریته.

توی این بخش، انواع نیازمندی‌های سیستم رو توصیف می‌کنیم. همون‌طور که احتمالاً از بخش‌های قبلیِ این دوره یادته، دو نوع نیازمندی داریم: **نیازمندی‌های کارکردی** که سیستم چیکار باید بکنه رو توصیف می‌کنن، و **نیازمندی‌های غیرکارکردی** که سیستم با چی باید کنار بیاد رو توصیف می‌کنن. یه یادآوریِ کوتاه: نیازمندی غیرکارکردی، performance موردنیاز، بار مورد‌انتظار و حجم داده، SLA و بیشتر رو مشخص می‌کنه.

بخشِ نیازمندی‌های سندِ معماری، به‌طور مختصر هر دو نوع نیازمندی رو توصیف می‌کنه. این بخش باید کوتاه باشه و نیازمندی‌ها باید توی یه لیستِ بولت با حداکثر ۳ خط برای هر نیازمندی نوشته بشن.

### چرا این بخش لازمه؟

شاید بپرسی، شبیه بخش پس‌زمینه، مگه تیم از قبل با نیازمندی‌ها آشنا نیست؟ چرا باید یادآوریشون کنیم؟ سؤال خوبیه، بیا جوابش رو بدیم. دو دلیل مهم برای گنجاندنِ نیازمندی‌ها توی سند معماری هست:

**اول:** شبیه بخش پس‌زمینه، این بخش توی سند گنجونده می‌شه تا خواننده‌ها بتونن روی نیازمندی‌ها نظر بدن و مطمئن بشن همه از چیزی که سیستم باید بکنه و تحت چه شرایطی کار کنه کاملاً آگاهن. این فرصتِ خوبیه برات که درکت از سیستم رو اعتبارسنجی کنی و مطمئن بشی هر چیزی که طراحی می‌کنی، یه مشکلِ واقعیِ مشتری رو حل می‌کنه.

**دوم:** یادت باشه معماری بر اساسِ یه نیازمندیِ کاملاً مشخص طراحی می‌شه. خیلی از ویژگی‌های معماری — مثل افزونگی، پیام‌رسانی، ذخیره‌سازیِ داده و بیشتر — با توجه به یه نیازمندیِ خاص طراحی می‌شن. مثلاً اگه یه نیازمندیِ غیرکارکردی هست که یه پیام هیچ‌وقت نباید از دست بره، شاید یه مکانیزمِ پیام‌رسانیِ مبتنی بر صف انتخاب کنی. اگه نیازمندی عوض بشه و یهو تحملِ از‌دست‌رفتنِ پیام معنی‌دار بشه، ممکنه معماری هم عوض بشه و به‌جاش پیام‌رسانیِ مبتنی بر REST API پیشنهاد بدی. به همین دلیل، فوق‌العاده مهمه که نیازمندی‌های دقیق — به‌خصوص غیرکارکردی‌ها — توی سند معماری مشخص بشن. این‌طوری روشن می‌کنی چه نیازمندی‌هایی معماری رو تعیین کردن و مطمئن می‌شی همه ازشون خبردارن.

توجه کن این بخش به هیچ‌وجه جایگزینِ سندِ طراحی‌ای که تحلیل‌گر سیستم می‌سازه نیست. این بخش فقط یه نمای‌کلیِ سطح‌بالا از نیازمندی‌هاست — بیشتر یه لیستِ نقاطِ بحث، نه یه سندِ کامل. پس همه‌ی نکته‌ها و ظرافت‌های هر نیازمندی رو توصیف نکن؛ یه توضیحِ کوتاه و مختصر کافیه.

### ساختار بخش

اول، **نیازمندی‌های کارکردی**. یه لیست از نیازمندی‌های کارکردیِ اصلی بده — معمولاً بیشتر از ۵ تا نه. یادت باشه، یه لیستِ بولت با حداکثر سه خط برای هر نیازمندی.

بعد، **نیازمندی‌های غیرکارکردی**. برخلافِ نیازمندی‌های کارکردی، توی این لیست فوق‌العاده مهمه که دقیق و مشخص باشی. دلیلش اینه که درحالی‌که نیازمندی‌های کارکردی معمولاً توی سندهای طراحیِ دیگه‌ای هم مستندسازی می‌شن، نیازمندی‌های غیرکارکردی معمولاً توی هیچ سندِ دیگه‌ای جز سندِ معماری نمیان. به همین دلیل، مطمئن شو لیستِ نیازمندی‌های غیرکارکردی، هرچند کوتاه و مختصر، همه‌ی جزئیاتِ لازم برای فهمِ کاملِ خواننده رو داره.

خب، درباره‌ی بخشِ نیازمندی‌ها حرف زدیم. بریم سراغ بخشِ بعدی.
