## بخش جزئیات اجزا

آخرین و مهم‌ترین بخشِ سندِ معماری، بخشِ جزئیاتِ اجزا (Components Drill-Down)ـه. این بخش، اجزایی که توی بخشِ نمای‌کلیِ معماری معرفی شدن رو با جزئیات توصیف می‌کنه.

این طولانی‌ترین بخش با فاصله‌ست. هیچ محدودیتِ واقعی‌ای برای طولش نیست — مدرس این دوره سندهایی ساخته که فقط همین بخشش بیشتر از ۱۰۰ صفحه بوده. این به این معنی نیست که این طولِ توصیه‌شده‌ست — ۱۰ صفحه هم می‌تونه کافی باشه. طولش تابعِ تعدادِ اجزا و سطحِ جزئیاتیه که باید بهش رسید.

مخاطبِ این بخش، تیم توسعه‌ست. اگه لیدرِ QA هم بخواد نگاهی بندازه، خوش‌اومده، ولی لازم نیست. توی موقعیت‌های نادر، بعضی از افرادِ مدیریت هم شاید بخوان نگاهی بندازن، ولی احتمالاً بعد از چند صفحه می‌فهمن کارِ مهم‌تری دارن و ولش می‌کنن.

### محتوای این بخش چیه؟

این بخش، اجزای مختلفی که توی نمای‌کلیِ معماری نشون داده شدن رو یکی‌یکی مرور می‌کنه و با جزئیات توصیفشون می‌کنه. برای هر جزء، باید چهار زیربخش توی سند باشه:

**۱. نقشِ جزء توی معماری.** یه مرورِ کوتاه از توصیفی که توی بخشِ نمای‌کلیِ معماری بود.

**۲. پشته‌ی فناوری.** این زیربخش باید با جزئیات توصیف کنه چه فناوری‌هایی توی توسعه‌ی این جزء استفاده می‌شن. اول باید بخش‌های مختلفی که فناوریشون باید انتخاب بشه رو مشخص کنه — دیتاستور، بک‌اند و فرانت‌اند — و بعد برای هر کدوم، فناوریِ انتخاب‌شده رو توصیف کنه.

بذار رک باشیم: انتخابِ پشته‌ی فناوری، یکی از داغ‌ترین موضوعاتِ دنیای نرم‌افزاره. قبلاً درباره‌ی مشکلاتی که موقعِ تصمیم‌گیری درباره‌ی پشته‌ی موردنیازِ سیستم باهاشون روبه‌رو می‌شی حرف زدیم. به همین دلیل، فوق‌العاده مهمه که زیربخشِ پشته‌ی فناوری خیلی دقیق باشه، و مهم‌تر از اون، شامل منطقِ پشتِ این انتخاب بشه. مثلاً موقع بحث درباره‌ی دیتاستور، اگه تصمیم رفتن سمتِ یه دیتابیس NoSQL مثل MongoDB باشه، باید واضح باشه چرا این تصمیم گرفته شده — دلایلی مثل ساختارِ داده‌ی موردانتظار، تجربه‌ی توسعه‌دهنده‌ها، performance و راحتیِ توسعه، همه دلایلِ مشروعی‌ان و باید توی این بخش بیان بشن. حتی بهتره MongoDB رو صراحتاً با دیتابیس‌های رابطه‌ای مثل SQL Server مقایسه کنی و به‌تفصیل مزایا و معایبِ هر گزینه و دلیلِ تصمیم رو توضیح بدی.

نکته‌ی مهم: لازم نیست برای هر جزء این سطح از جزئیات رو تکرار کنی — این فرایند رو برای اولین جزء انجام بده و اگه همون دلایل برای اجزای دیگه هم معتبره، خواننده رو به فرایندِ انتخابِ توضیح‌داده‌شده برای اولین جزء ارجاع بده؛ نیازی نیست همون بخش رو بارها کپی‌پیست کنی.

**۳. معماریِ جزء.** این زیربخش، معماریِ درونیِ جزء رو توصیف می‌کنه — مکملِ نمای‌کلیِ معماری که تصویر بزرگ‌تر رو نشون داده، حالا با رفتن توی هر جزء و توضیحِ دقیقِ اینکه چی باید انجام بشه و چطور. یادته الگوهای معماری‌ای که قبلاً بررسی کردیم؟ الگوی n-tier، تزریق وابستگی، stateless و بقیه؟ اینجا جاییه که ازشون استفاده می‌کنی.

با توصیفِ API جزء (اگه داشته باشه) شروع کن. از توصیفِ خودِ متدهای API نترس — این کار توسعه رو خیلی راحت‌تر و سریع‌تر می‌کنه. معمولاً یه جدول می‌سازیم که همه‌چیزی که باید درباره‌ی API دونست — نقشش، URL، کدهای پاسخ و توضیحات — رو نشون می‌ده. این تکنیکِ فوق‌العاده‌ای موقع کار با توسعه‌دهنده‌هاست، چون از قبل می‌دونن جزء چطور خودش رو در معرض دید می‌ذاره و زمینه رو برای بقیه‌ی معماری فراهم می‌کنه.

نقشِ هر لایه رو تا سطحِ متد با جزئیات توصیف کن. این کمک می‌کنه توسعه‌دهنده‌ها کاملاً بفهمن نقشِ لایه‌ها چیه و چی باید و نباید توشون باشه. اگه ملاحظاتِ مهمی هست که باید در نظر گرفته بشن، اینجا ذکرشون کن — مثلاً اگه یه کلاس باید از مکانیزم تزریق وابستگی توی سازنده‌ش استفاده کنه، اینجا بگو. نتیجه‌ی نهایی ساده‌ست: تا حد ممکن دقیق باش و از تجسم‌سازی تا حد ممکن استفاده کن — این کار زندگیِ تو و توسعه‌دهنده‌ها رو بعداً خیلی راحت‌تر می‌کنه.

**۴. دستورالعمل‌های توسعه.** معمولاً یه زیربخشِ کوچیک — حداکثر نیم‌صفحه — که شاملِ یه لیستِ بولت از دستورالعمل‌های عملیِ توسعه‌ست. این دستورالعمل‌ها باید راهنمایی‌های خاصی رو مشخص کنن که بخشی از معماری نیستن، ولی همچنان برای توسعه‌دهنده‌ها مرتبطن. مثلاً استفاده از یه کتابخونه‌ی خاص برای یه کارِ خاص، یا مطمئن‌شدن از اینکه API با فرمتی مستند شده که ابزارهایی مثل Swagger بتونن ازش استفاده کنن. مهمه این لیست کوتاه، مختصر و کاملاً عملی بمونه — از بحث درباره‌ی الگوها و تئوری‌ها اینجا پرهیز کن. این یه لیستِ «بکن/نکن»ـه، نه چیز دیگه.

باز هم، مثل همه‌ی بخش‌هایی که اینجا بررسی کردیم، یه سندِ معماریِ کاملاً کاربردی رو توی انتهای بخشِ بعدی — جایی که یه مطالعه‌ی موردیِ واقعی رو بررسی می‌کنیم و معماریش رو با هم می‌سازیم — پیدا می‌کنی. اونجا این بخش رو می‌بینی و دقیقاً می‌تونی ببینی چه شکلیه.

### جمع‌بندی

این‌طوری بخشِ سند معماری رو تموم می‌کنیم. این سند، مرکزِ کارِ معماره، هرچند تنها کاری نیست که انجام می‌دی. فوق‌العاده مهمه. این سند همه‌ی بینش‌هایی که موقع کار روی معماری تولید شدن رو در بر می‌گیره — و بعداً کمکت می‌کنه تصمیم‌هایی که قبلاً توی فرایند گرفتی رو توجیه کنی.

همیشه سعی کن به ذهنِ مخاطبت فکر کنی. خلاصه‌ی مدیریتی رو برای مدیریت بنویس و جزئیاتِ اجزا رو برای توسعه‌دهنده‌ها هدف بگیر. این‌طوری، سند دقیقاً همون چیزی می‌شه که باید باشه: سنگ‌بنا و پایه‌ی سیستم.
