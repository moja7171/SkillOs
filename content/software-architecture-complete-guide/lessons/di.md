## تزریق وابستگی (DI)

تزریق وابستگی، مکمل الگوی اینترفیسیه که توی درس قبل بررسی کردیم. یادته گفتیم اینترفیس‌ها مکانیزم بهتری برای ارتباط بین کلاس‌ها هستن تا کد رو ماژولارتر و منعطف‌تر کنن؟ اون درس رو با یه سؤال باز تموم کردیم: چطور یه پیاده‌سازیِ مشخص رو به اینترفیس تزریق کنیم تا کدِ فراخوان بتونه ازش استفاده کنه؟ و جواب همین سؤاله، موضوع این درسه: **تزریق وابستگی (Dependency Injection)**.

ویکی‌پدیا تزریق وابستگی رو این‌طور تعریف می‌کنه: تکنیکی که توش یه آبجکت، وابستگی‌های آبجکت دیگه رو تأمین می‌کنه. شاید یه‌کم پیچیده و آکادمیک به نظر برسه، ولی توی واقعیت خیلی ساده‌ست.

بیا دوباره به مثال درس قبل نگاه کنیم. یه کلاس اصلی داشتیم که کلاس `Calculator` رو صدا می‌زد. توی این مثال، `Calculator` یه وابستگیِ کلاس اصلیه — کلاس اصلی برای کارکرد درستش بهش وابسته‌ست. با تکنیک تزریق وابستگی، می‌تونیم یه پیاده‌سازیِ مشخص رو به اینترفیسی که نماینده‌ی این وابستگیه تزریق کنیم، بدون اینکه کلاس اصلی بدونه دقیقاً کدوم پیاده‌سازی استفاده می‌شه.

اگه دوباره به کد نگاه کنیم، می‌بینیم تزریق وابستگی دقیقاً توی خط `GetInstance` اتفاق می‌افته:

```csharp
private ICalculator calc = CalculatorFactory.GetInstance();
```

توی این خط، `GetInstance` یه کلاس برمی‌گردونه که اینترفیس `ICalculator` رو پیاده‌سازی کرده. کلاس اصلی هیچ ایده‌ای نداره این کلاس چیه — می‌تونه همون کلاسی باشه که قبلاً دیدیم یا یه کلاس کاملاً متفاوت. تنها چیزی که معلومه اینه که این کلاس، اینترفیس موردنیاز رو پیاده‌سازی کرده. این‌طوری یه واسطه بین کلاس اصلی و کلاس `Calculator` ایجاد کردیم — به عبارت دیگه، اتصال محکم بین این دو رو حذف کردیم و کدمون رو خیلی ماژولارتر و منعطف‌تر کردیم.

### توی متد `GetInstance` واقعاً چه خبره؟

جواب خیلی ساده‌ست. این متد، که معمولاً **متد فکتوری (factory method)** نامیده می‌شه، یه منطق ساده اجرا می‌کنه و تصمیم می‌گیره کدوم کلاس باید تزریق بشه — بعد یه آبجکت از اون کلاس می‌سازه و به‌عنوان اینترفیس برمی‌گردونه.

**ساده‌ترین پیاده‌سازی:**

```csharp
public static ICalculator GetInstance()
{
    return new Calculator();
}
```

این پیاده‌سازی هیچ منطقی نداره — همیشه همون کلاس رو برمی‌گردونه. شاید یه‌کم عجیب به نظر برسه، ولی همین پیاده‌سازیِ ساده هم ارزشمنده، چون حتی با یه کلاس واحد، استفاده از تزریق وابستگی کمک می‌کنه کدی بسازیم که به اتصال محکم گره نخورده و می‌تونیم به یه پیاده‌سازیِ دیگه سوییچ کنیم بدون اینکه کدِ فراخوان ازش خبردار بشه.

**پیاده‌سازیِ پیشرفته‌تر:** توی این حالت، کدِ فراخوان یه پارامتر مشخص می‌کنه که به متد کمک می‌کنه تصمیم بگیره کدوم نمونه رو برگردونه:

```csharp
public static ICalculator GetInstance(string calculatorType)
{
    switch (calculatorType)
    {
        case "basic": return new Calculator();
        case "advanced": return new AdvancedCalculator();
        default: throw new ArgumentException("Unknown calculator type");
    }
}
```

باز هم، کدِ فراخوان هیچ ایده‌ای نداره کدوم پیاده‌سازی رو گرفته — همیشه با اینترفیس کار می‌کنه. یه نسخه‌ی خیلی رایج از همین مثال اینه که پارامتر توی یه فایل پیکربندی تعریف بشه — این‌طوری فکتوری اصلاً پارامتری نمی‌گیره، بلکه پارامتر رو از فایل پیکربندی می‌خونه. این الگو خیلی رایجه، مخصوصاً توی پیاده‌سازیِ لایه‌ی دسترسی به داده، جایی که نوع دیتابیس توی فایل پیکربندی ذخیره می‌شه و متد فکتوری از همونجا می‌خونه و تصمیم می‌گیره کدوم پیاده‌سازی DAL رو برگردونه.

### تزریق سازنده (Constructor Injection)

تا الان تزریق وابستگی با متد فکتوری رو دیدیم، ولی انواع دیگه‌ای هم داره. یکی از رایج‌ترین‌ها، **تزریق سازنده (constructor injection)**ـه. توی این روش، کلاس اینترفیس‌های آماده‌شده رو توی سازنده‌ش (constructor) دریافت می‌کنه و توی متدهاش ازشون استفاده می‌کنه:

```csharp
public class OrderService
{
    private readonly ILogger _logger;

    public OrderService(ILogger logger)
    {
        _logger = logger;
    }

    public void PlaceOrder(Order order)
    {
        _logger.Log($"Placing order {order.Id}");
        // ...
    }
}
```

همون‌طور که می‌بینی، سازنده‌ی کلاس یه اینترفیس `ILogger` به‌عنوان پارامتر می‌گیره و بلافاصله ازش استفاده می‌کنه. توی این حالت، فریم‌ورک خودش نمونه‌سازیش رو انجام می‌ده و کار اضافه‌ای لازم نیست.

مزیت اصلیِ الگوی تزریق سازنده نسبت به الگوی سنتی، **پایداری و راحتیِ تست**ـه. کلاسی که وابستگی‌هاش توی سازنده تزریق می‌شن، تستش خیلی راحت‌تره — متد تست می‌تونه کلاس رو با آبجکت‌های mock نمونه‌سازی کنه و تست رو اجرا کنه:

```csharp
var mockLogger = new MockLogger(); // چیزی نمی‌نویسه، فقط برای تست
var service = new OrderService(mockLogger);
service.PlaceOrder(testOrder);
```

توجه کن که متد تست، کلاس رو با یه mock logger نمونه‌سازی می‌کنه که هیچ کاری نمی‌کنه، و کلاسِ تحت‌تست اصلاً ازش خبر نداره — از دید خودش، این یه logger عادی و کاملاً کارکرده.

### جمع‌بندی

این‌طوری بحث اینترفیس‌ها و تزریق وابستگی رو تموم می‌کنیم. کار پیش‌پاافتاده‌ای نیست، ولی وقتی درست پیاده بشه، نتیجه‌ش کدی ماژولار، منعطف و راحت برای نگهداری و تغییره. امتحانش کن — شاید اولش یه‌کم کلافه بشی، ولی در نهایت نورش رو می‌بینی، قول می‌دیم.
