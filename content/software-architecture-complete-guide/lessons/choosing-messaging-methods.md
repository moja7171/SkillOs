## انتخاب روش پیام‌رسانی

توی درسِ قبل، با چهار سرویس تموم کردیم که این‌شکلیه: Receiver، Handler، Info و سرویسِ لاگِ مرکزی. حالا باید تصمیم بگیریم چه نوع پیام‌رسانی‌ای بینِ هر کدومشون درسته.

### Receiver

Receiver، همون‌طور که از اسمش پیداست، پیام‌ها رو از دستگاه‌های IoT دریافت می‌کنه. توی این حالت، روشِ پیام‌رسانی در واقع توسط نحوه‌ی ارسالِ پیام توسط خودِ دستگاه‌ها تعیین می‌شه. برای فهمیدنش، دوباره باید بریم سراغ مشتری. بعد از چند تماسِ تلفنی، جواب می‌ده: دستگاه‌ها از طریق HTTP و با فعل POST، به‌روزرسانی می‌فرستن. خیلی خوبه — یعنی Receiverِ ما به یه اپلیکیشنِ وب API استاندارد با REST API به‌عنوان رابطش تبدیل می‌شه.

### Handler

اینجا اوضاع کمی پیچیده‌تر می‌شه. یادته نقشِ Handler اینه که پیام‌های دریافتی توسط Receiver رو اعتبارسنجی و پردازش کنه؟ تنها دلیلِ وجودش اینه که وظیفه رو از Receiver بردارد، که باید فقط روی دریافتِ پیام‌ها و آزادکردنِ درخواست‌ها تمرکز کنه. بعد از اینکه Handler پیام رو مدیریت کرد، باید توی دیتاستور برای استفاده‌ی بعدی ذخیره‌ش کنه.

پس بهترین روشِ پیام‌رسانی بینِ Receiver و Handler چیه؟ به نظر می‌رسه بهترین مکانیزم، **صف**ـه. قطعاً می‌خوایم پیام‌ها به همون ترتیبی که دریافت شدن پردازش بشن — که یه ویژگیِ کلاسیکِ صفه — و از قابلیت‌اطمینان و مقیاس‌پذیری‌ای که این مکانیزم ارائه می‌ده هم خوشمون میاد. اگه بینِ Receiver و Handler از REST API استفاده کنیم، Receiver باید کلی کار بکنه، چون باید منتظرِ اتمامِ هر درخواست به Handler بمونه و خطاها و مشکلات رو هم مدیریت کنه — این به performance که برای Receiver این‌قدر مهمه آسیب می‌زنه. با استفاده از صف، اساساً یه مکانیزمِ «فرستادن و فراموش‌کردن» داریم — Receiver پیام رو توی صف می‌ذاره و فراموشش می‌کنه. دقیقاً همین چیزیه که توی این حالت می‌خوایم.

پس نتیجه: REST API برای Receiver، صف برای Handler.

### Info

خب، این یکی راحته. بیا ببینیم چه کسی به Info دسترسی پیدا می‌کنه؟ جوابش، البته، کاربرهای نهایی‌ان. چطوری؟ خب، واضحه، از طریق مرورگر وب. مرورگرهای وب چطور به سرورها دسترسی دارن؟ البته با پروتکل HTTP، و استاندارد de facto برای دسترسی به سرورهای HTTP امروزه، REST API‌ـه. پس Info هم، مثل Receiver، یه REST API پیاده‌سازی می‌کنه.

### سرویسِ لاگ

و آخرین ولی نه کم‌اهمیت‌ترین، سرویسِ لاگ‌ـه. یادت باشه، لاگ‌های تولیدشده توسط سرویس‌های دیگه باید برای تجمیع به سرویسِ لاگ فرستاده بشن. چطور این کار رو بکنیم؟

اولین فکر ممکنه این باشه که سرویسِ لاگ باید یه REST API در معرض دید بذاره تا سرویس‌های دیگه بتونن راحت بهش دسترسی داشته باشن و رکوردهای لاگشون رو بفرستن. ولی این ایده‌ی خوبی نیست. لاگ‌ها معمولاً خیلی زیادن، و انتظار داریم سرویس‌های مختلف تعدادِ زیادی رکوردِ لاگ توی هر لحظه تولید کنن. حالا اگه برای هر رکورد، سرویس‌ها باید یه فراخوانیِ REST API بزنن، این performance رو به‌شدت آسیب می‌زنه. یه راه‌حل لازم داریم که بشه حجمِ زیادی رکورد رو بدونِ آسیب به performance به سرویسِ لاگ فرستاد.

یکی از راه‌حل‌های رایج برای این مشکل، استفاده از **فایل**ـه. توی این راه‌حل، سرویس‌های مختلف رکوردهای لاگ رو توی یه فایل می‌نویسن، و سرویسِ لاگ این فایل‌ها رو pull می‌کنه و محتواشون رو تجمیع می‌کنه. این راه‌حلِ خیلی محبوبیه، ولی دو مشکلِ بزرگ داره:

۱. توی محیطِ کلاود کار نمی‌کنه. این دوره درباره‌ی اپلیکیشن‌های کلاود نیست، ولی همچنان مهمه بدونیم توی کلاود چی ممکنه و چی نه — و نوشتن روی فایل توی یه اپلیکیشنِ کلاود، یه «نه»ی بزرگه.

۲. فایل‌ها گرایش دارن قفل بشن، توسط آنتی‌ویروس اسکن و حذف بشن، یا فقط توسط ادمین‌های بی‌احتیاطِ سیستم پاک بشن. خلاصه، فایل یه منبعِ خیلی غیرقابل‌کنترله که بهتره ازش دوری کنیم.

خب، حالا چی مونده؟ راستش دو گزینه‌ی دیگه: **اول**، لاگ‌ها رو توی یه دیتابیس بنویس و بذار سرویسِ لاگ از دیتابیس کوئری بزنه و رکوردها رو مدیریت کنه. **دوم**، از صف استفاده کن — سرویس‌های مختلف رکوردها رو به صف اضافه می‌کنن و سرویسِ لاگ رکوردها رو از صف می‌کشه و مدیریتشون می‌کنه.

کدوم بهتره؟ توصیه اینه که از **صف** استفاده کنیم. دلیلش اینه که استفاده از دیتابیس توی این حالت، عملاً مجبورش می‌کنه مثل یه صف رفتار کنه — دیتابیس فقط یه ذخیره‌سازیِ موقته، و هر رکوردی که بازیابی بشه، باید فوراً حذف بشه، دقیقاً مثل صف. پس به‌جای دوباره‌اختراع‌کردنِ چرخ، بیا فقط از مکانیزمِ صف استفاده کنیم و مؤثرترین پیام‌رسانی رو داشته باشیم.

### جمع‌بندی

خب، حالا مکانیزم‌های پیام‌رسانیِ مختلفِ سیستم رو تعریف کردیم و یه تصویرِ کاملِ معماریِ سیستم داریم. اجزا رو نقشه‌برداری کردیم و به نتیجه رسیدیم که چی لازمشونه، تصمیم گرفتیم روش‌های پیام‌رسانی بینِ این سرویس‌ها چی باشه، و حالا می‌فهمیم عواملِ تصمیم‌گیری برای هر کدوم از این مکانیزم‌ها چیه. حالا می‌تونیم بریم سراغِ جزئیاتِ اجزا.

ولی قبلش، یه هشدار: قبل از اینکه به مشتری توصیه کنی از صف استفاده کنه، باید مطمئن بشی تیم IT مشتری بلده موتورِ صف رو راه‌اندازی، استفاده و نگهداری کنه. اگه IT اصلاً ایده‌ای درباره‌ی استفاده‌ش نداره، شاید بهتر باشه سراغ یه راه‌حلِ کم‌شیک‌تر ولی با شانسِ موفقیتِ بیشتر بری.

خب، تمومه. بریم جزئیاتِ اولین سرویس رو بررسی کنیم: سرویسِ لاگ.
