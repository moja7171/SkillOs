## فناوری ذخیره‌سازی داده

انتخاب فناوری ذخیره‌سازی داده، یکی از مهم‌ترین تصمیم‌هایی‌یه که توی طراحی پروژه می‌گیری. آخه اینجاست که داده‌ی باارزشت برای استفاده‌ی اپلیکیشن ذخیره می‌شه.

### اول، دو مفهوم رو بشناسیم

اینجا داریم درباره‌ی محصولات ذخیره‌سازی داده مثل SQL Server یا MongoDB صحبت نمی‌کنیم، بلکه درباره‌ی دو **مفهوم** ذخیره‌سازی داده: **SQL** و **NoSQL**.

### دیتابیس‌های SQL (رابطه‌ای)

دیتابیس‌های SQL یا رابطه‌ای، دیتابیس‌های سنتی‌تر هستن — نزدیک به ۴۰ ساله که به صنعت خدمت می‌کنن. محبوب‌ترین‌هاشون Microsoft SQL Server، Oracle و MySQL هستن.

دیتابیس‌های رابطه‌ای چند ویژگی مشترک دارن:

- **ذخیره‌ی داده توی جدول‌ها:** هر جدول یه نوع خاص از موجودیت رو ذخیره می‌کنه، و هر جدول یه سری ستون مشخص داره که ویژگی‌های اون موجودیت رو نشون می‌ده.
- **رابطه بین جدول‌ها:** جدول‌ها می‌تونن با هم رابطه داشته باشن — مثلاً اگه یه جدول سفارش‌ها داری، احتمالاً یه جدول اقلام سفارش هم داری که هر ردیفش با فیلد شناسه‌ی سفارش به یه سفارش خاص وصل می‌شه.
- **تراکنش (Transaction):** یه تراکنش یه مجموعه‌ی اتمیک از اکشن‌هاست که یا همه‌شون اجرا می‌شن یا هیچ‌کدوم. مثلاً اگه مشتری یه کالا رو توی سفارش گذاشت، موجودی اون کالا باید یکی کم بشه — هیچ‌وقت نباید کالا ثبت بشه ولی موجودی به‌روز نشه. تراکنش‌ها با مخفف **ACID** تعریف می‌شن: Atomicity (اتمیک بودن)، Consistency (سازگاری)، Isolation (ایزوله بودن) و Durability (پایداری). فقط دیتابیسی که همه‌ی این‌ها رو پشتیبانی کنه، می‌تونه ادعا کنه از تراکنش پشتیبانی می‌کنه.
- **زبان کوئری:** همه‌ی دیتابیس‌های رابطه‌ای اجازه‌ی کوئری‌گرفتن با زبان SQL رو می‌دن. SQL، مخفف Structured Query Language، یه زبان خیلی بالغه که بیشتر از ۴۰ سال پیش توسط IBM معرفی شد و استاندارد de facto دسترسی به داده توی دیتابیس‌های رابطه‌ایه.

### دیتابیس‌های NoSQL

همون‌طور که از اسمش پیداست، دیتابیس‌های NoSQL سعی می‌کنن نقطه‌ی مقابل دیتابیس‌های SQL باشن. یکی از محدودیت‌های مهم دیتابیس‌های SQL، performance و اندازه‌ست — چون دیتابیس‌های رابطه‌ای برای هر رکورد schema نگه می‌دارن و تراکنش رو اعمال می‌کنن، هرچی دیتابیس بزرگ‌تر بشه، performance‌ش افت می‌کنه. این دقیقاً همون مشکلیه که جنبش NoSQL می‌خواد حلش کنه.

بزرگ‌ترین قدرت NoSQL، مقیاس و performance‌شه. دیتابیس‌های NoSQL می‌تونن واقعاً غول‌پیکر بشن و اغلب روی سرورهای زیادی توزیع می‌شن. مثلاً موتور جست‌وجوی چینیِ Baidu، بیشتر از ۳۰۰ ترابایت رو روی MongoDB — یکی از محبوب‌ترین دیتابیس‌های NoSQL — ذخیره می‌کنه، و دیدن دیتابیس‌های NoSQL با میلیاردها موجودیت هم غیرعادی نیست.

ویژگی‌های دیتابیس‌های NoSQL:

- **بدون schema:** برخلاف SQL که داده رو توی یه جدول با ستون‌های کاملاً مشخص ذخیره می‌کنه، NoSQL هیچ schema‌ای رو اجباری نمی‌کنه — می‌تونه موجودیت‌های کاملاً متفاوت با فیلدهای کاملاً متفاوت رو توی همون «جدول» ذخیره کنه. معمولاً این موجودیت‌ها به شکل سند JSON ذخیره می‌شن، و چون JSON کاملاً منعطفه، به یه فیلد یا اندازه‌ی خاص محدود نیستی. این برای اپلیکیشنی که قراره داده‌ی نیمه‌ساخت‌یافته یا بدون‌ساختار ذخیره کنه، مزیت بزرگیه.
- **تراکنش متفاوت:** پشتیبانی از تراکنش توی دیتابیس‌های NoSQL متفاوته. بیشترشون یه مفهوم به اسم **eventual consistency** (سازگاری نهایی) رو پشتیبانی می‌کنن — یعنی دیتابیس تضمین می‌ده اکشن اجرا می‌شه، ولی تضمین نمی‌ده دقیقاً کِی. البته صحبت از دقیقه‌ها یا معمولاً حتی ثانیه‌ها نیست، ولی فوری هم نیست — پس کد باید بتونه با ناسازگاری موقت داده کنار بیاد. دلیل اینکه NoSQL فقط بخشی از تعریف ACID رو پشتیبانی می‌کنه، دقیقاً به خاطر همون هدف اصلیش — اندازه و performance‌ـه.
- **بدون زبان کوئری استاندارد:** برخلاف SQL که یه زبان یکسان روی همه‌ی دیتابیس‌های رابطه‌ای کار می‌کنه، هر دیتابیس NoSQL زبان و درایور خودش رو داره و منحنی یادگیری خودش رو می‌طلبه.

### جمع‌بندی: کِی کدوم رو انتخاب کنیم؟

اگه سیستمت قرار نیست غول‌پیکر بشه (منظور از غول‌پیکر، حداقل چند ده ترابایت)، داده‌ت بیشتر ساخت‌یافته‌ست و سازگاریِ داده برات مهمه، برو سراغ دیتابیس‌های SQL سنتی. فرقی نمی‌کنه کدوم رو انتخاب کنی — همه‌شون کار خوبی انجام می‌دن، فقط مطمئن شو با پلتفرم توسعه‌ت سازگاره.

اگه، از طرف دیگه، برنامه داری یه انبار داده‌ی غول‌پیکر و بدون‌ساختار داشته باشی، برو سراغ NoSQL. MongoDB الان محبوب‌ترین دیتابیس NoSQL‌ـه و از سمت تقریباً هر فروشنده‌ی نرم‌افزار بزرگی پشتیبانی می‌شه — پس یه انتخاب طبیعیه.

### یه نکته‌ی آخر

اخیراً مرز بین دیتابیس‌های SQL و NoSQL داره کم‌رنگ می‌شه و می‌بینیم قابلیت‌های مختلف از یه نوع به نوع دیگه نشت می‌کنن. مثلاً به‌طور سنتی، دیتابیس‌های NoSQL توی کوئری‌گرفتن از سند JSON عالی بودن، درحالی‌که دیتابیس‌های SQL، رک بگم، افتضاح بودن. ولی امروز، توی دیتابیس‌هایی مثل SQL Server و Postgres، قابلیت‌های عالی کوئریِ JSON پیدا می‌کنیم. راستش یکی از مشتری‌های مدرس این دوره تصمیم گرفت MongoDB رو کنار بذاره و SQL Server رو انتخاب کنه، چون واقعاً از ترکیب پشتیبانی کامل تراکنش و کوئری JSON خوشش اومد.

نمونه‌ی دیگه‌اش پشتیبانی تراکنشه — MongoDB چند وقت پیش پشتیبانی کامل ACID اضافه کرد، که یه جهش بزرگ برای دیتابیس‌های NoSQL بود. ادعا می‌کنن این کار performance رو تحت‌تأثیر قرار نمی‌ده، و خیلی جالبه ببینیم آیا فروشنده‌های NoSQL دیگه هم همین رویکرد رو در پیش می‌گیرن یا نه.
