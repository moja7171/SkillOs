## پیام‌رسانی

بیا درباره‌ی پیام‌رسانی (messaging) حرف بزنیم. اصطلاح messaging به روش‌های ارتباط بین سرویس‌های مختلف سیستم اشاره داره. توی بخش قبل، درباره‌ی «شبکه‌ی تار عنکبوت» حرف زدیم — وضعیتی که همه‌ی سرویس‌ها مستقیم با هم ارتباط برقرار می‌کنن، که به یه آشفتگیِ بزرگ از URLهای درهم‌تنیده منجر می‌شه که با تغییر یه URL، کرش می‌کنه و می‌سوزه. این سناریو وقتی مرتبطه که سرویس‌ها از طریق REST API ارتباط برقرار کنن.

ولی راه‌های دیگه‌ای هم برای ارتباط بین سرویس‌ها هست، و مهمه که ازشون آگاه باشی تا بتونی یه تصمیم آگاهانه درباره‌ی پلتفرمِ پیام‌رسانیِ مناسب بگیری. یه نکته: انتخاب پلتفرم پیام‌رسانی انحصاری نیست — خیلی وقت‌ها سیستم‌هایی می‌بینیم که از چند روش پیام‌رسانی استفاده می‌کنن، هر کدوم برای هدف خودش، و هیچ مشکلی هم توش نیست — راستش توصیه هم می‌شه، فقط مطمئن شو همیشه از روش درست برای وظیفه‌ی درست استفاده می‌کنی.

### معیارهای مقایسه

قبل از بررسیِ روش‌های مختلف، بیا معیارهایی که باهاشون مقایسه‌شون می‌کنیم رو مشخص کنیم:

- **Performance:** همیشه یه روش پیام‌رسانیِ سریع‌تر رو ترجیح می‌دیم.
- **اندازه‌ی پیام:** بیشتر سیستم‌ها به پیام‌های بزرگ بین سرویس‌ها نیاز ندارن، ولی گاهی مفیده.
- **مدل اجرا:** بعضی پلتفرم‌های پیام‌رسانی مدلِ درخواست-پاسخ می‌خوان (که محدودیت داره)، و بعضی‌ها اجازه‌ی اجرای فرایندهای طولانی‌مدت رو می‌دن.
- **بازخورد و قابلیت‌اطمینان:** منظور از بازخورد، توانایی تشخیصِ اینکه آیا پیام‌رسانی شکست خورده یا نه، و در صورتِ شکست، توانایی انجام یه اکشنِ اصلاحی. همه‌ی روش‌های پیام‌رسانی وضعیت رو گزارش نمی‌دن، و این قطعاً یه ملاحظه‌ی مهمه. بازخورد هم به قابلیت‌اطمینان خیلی مرتبطه — یه روشِ قابل‌اطمینان تضمین می‌کنه پیام حتی اگه مشکلی هم پیش بیاد، دریافت می‌شه. این برای سیستم‌های حیاتی که داده‌ی توی پیام باید هر طور شده دریافت بشه، خیلی مهمه.
- **پیچیدگیِ پیاده‌سازی:** اگه یه پلتفرم پیام‌رسانی به تلاش توسعه‌ی زیادی نیاز داره، خوبه از قبل بدونیمش.

### REST API

بیا لیستمون رو با رایج‌ترین روشِ پیام‌رسانی شروع کنیم: REST API. REST API استاندارد de facto برای پیام‌رسانیِ مبتنی بر HTTP بین سرویس‌هاست. سرویس یه API در معرض دید می‌ذاره که از استاندارد پروتکل HTTP، شامل فعل‌های HTTP که نوع اکشن رو نشون می‌دن، استفاده می‌کنه — مثلاً `GET` یعنی «موجودیت رو بازیابی کن» و `POST` یعنی «موجودیت جدید بساز» و بیشتر.

از نظر performance، REST API معمولاً خیلی سریعه. بیشتر وب‌سرورها با درخواست‌های HTTP معمولی — که دقیقاً همون REST API‌ه — performance عالی دارن. و چون ارتباط مستقیم بین سرویس‌ها رو بدون هیچ مکانیزم واسطه‌ای فعال می‌کنه، یکی از سریع‌ترین پلتفرم‌های پیام‌رسانیه. درباره‌ی اندازه‌ی پیام، REST API از همون محدودیت‌های پروتکل HTTP پیروی می‌کنه — عملیات `GET` معمولاً به ۸ کیلوبایت محدوده، درحالی‌که `POST` یا `PUT` معمولاً تا چند ده مگابایت مجازن (بسته به وب‌سرور و پلتفرم فرق می‌کنه).

مدل اجرای REST API، درخواست-پاسخه — که یعنی برای اکشن‌های سریع و کوتاه عالیه، ولی برای فرایندهای طولانی مناسب نیست. بازخورد چطوره؟ اینجاست که REST API واقعاً می‌درخشه. چون یه روش هم‌گام (synchronous) ـه، فراخوان‌کننده فوراً از طریق کد پاسخِ HTTP بازخورد می‌گیره — اگه مشکلی توی اجرا باشه ۵۰۰ می‌گیره، اگه مشکل از خودِ پیام باشه ۴۰۰، و اگه همه‌چیز خوب پیش رفته باشه ۲۰۰ (کدهای دیگه‌ای هم هست، ولی این‌ها رایج‌ترین‌ها هستن). با این بازخوردِ فوری، فراخوان‌کننده می‌تونه یه سیاستِ خطا پیاده کنه — مثل retry، لاگ‌گیری و بیشتر. پس با اینکه REST API از این نظر که پیام حتی موقع مشکل هم حتماً می‌رسه قابل‌اطمینان نیست، بازخوردِ عالیش این کمبود رو جبران می‌کنه. با این حال، همچنان به یه سیستمِ کاملاً قابل‌اطمینان نمی‌رسیم.

پیچیدگیِ REST API عملاً صفره. همه‌ی زبان‌های توسعه‌ی مدرن، کتابخونه‌های تخصصی دارن که کمک می‌کنن REST API بسازی و بخش‌های فنیِ دیگه — مثل سریالایز‌کردنِ JSON و تبدیلش به آبجکت — رو مدیریت کنی. مثلاً توی .NET، ASP.NET Web API؛ توی Java، Spring؛ توی Python، Flask. خلاصه‌ش اینه: ساختِ REST API فوق‌العاده راحته.

**کِی استفاده کنیم؟** REST API فوق‌العاده برای سیستم‌های وب سنتی مفیده که رابط کاربری‌شون می‌تونه REST و JSON صحبت کنه (تقریباً هر فناوری کلاینتی امروزه این کار رو می‌تونه بکنه) یا سرویس‌های دیگه‌ای که APIش رو فرا می‌خونن. اگه داری همچین سیستمی طراحی می‌کنی، REST API باید اولین جایی باشه که برای پیام‌رسانی نگاش می‌کنی.

### Push Notification (Pub/Sub)

روش بعدی، push notificationهای HTTP یا الگوی Pub/Sub‌ـه. push notification یعنی یه کلاینت روی یه رویداد subscribe می‌کنه، و وقتی اون رویداد اتفاق بیفته، یه اعلان از سرور دریافت می‌کنه. ابزارهای زیادی این روش رو با فناوری‌های مختلف پیاده می‌کنن؛ بیشترشون از همون REST API که بررسی کردیم استفاده می‌کنن.

تمرکز اینجا روی نوع خاصی از push notification‌ـه که ارتباط بلادرنگ برای اپلیکیشن‌های وب رو ممکن می‌کنه — با کتابخونه‌هایی مثل SignalR یا Socket.io. این کتابخونه‌ها از تکنیک‌های پیشرفته‌ی وب مثل WebSocket استفاده می‌کنن تا یه کلاینتِ HTTP همیشه به مرورگر متصل بمونه، و ارتباط دوطرفه‌ی بلادرنگ رو ممکن می‌کنن — برخلاف مدل سنتیِ درخواست-پاسخ که فقط کلاینت ارتباط رو شروع می‌کنه. این روش برای اپلیکیشن‌هایی مثل چت، که کلاینت‌های زیادی باید از رویدادها — مثل تایپ‌کردنِ یه پیام توسط یه کاربر — باخبر بشن، فوق‌العاده مفیده.

از نظر performance، این روش عالیه — پیام‌ها با سرعت زیاد و مقیاس بالا فرستاده و دریافت می‌شن؛ یه ماشین می‌تونه بیشتر از ۱۰,۰۰۰ پیام در ثانیه بفرسته. درباره‌ی اندازه‌ی پیام، این روش نسبتاً محدوده — هرچند همیشه محدودیتِ رسمی وجود نداره، معمولاً اندازه‌ی پیام از چند کیلوبایت بیشتر نمی‌شه تا performance و مقیاس موردنظر حفظ بشه.

مدل اجرای push notification نسبتاً منحصربه‌فرده: یه متدِ کلاینت روی یه رویدادِ سرور subscribe می‌شه، و وقتی رویداد رخ بده، این متد اجرا می‌شه. subscription معمولاً با یه اتصال WebSocket باز یا یه پیاده‌سازیِ long polling نگه داشته می‌شه. خودِ سرور منتظر تمومِ‌شدنِ متد نمی‌مونه، پس مشکلاتی مثل timeout یا threadهای مشغول پیش نمیاد.

بازخورد و قابلیت‌اطمینان، بزرگ‌ترین ضعف این روشه. این کتابخونه‌ها به‌شکل «fire and forget» کار می‌کنن — یعنی وقتی پیام به subscriberها فرستاده می‌شه، هیچ ایده‌ای نیست که آیا دریافت شده یا نه. این یعنی اگه به هر دلیلی — مشکل شبکه یا باگ توی کلاینت — پیام دریافت نشه، سرور هیچ‌وقت نمی‌فهمه. این باعث می‌شه این کتابخونه‌ها برای اپلیکیشن‌هایی که به قابلیت‌اطمینانِ بالا نیاز دارن — که بیشترِ اپلیکیشن‌های سمت‌سرور همین‌طوری‌ان — مناسب نباشن. به همین دلیل، این کتابخونه‌ها عمدتاً توی اپلیکیشن‌های کلاینت-سرور استفاده می‌شن، جایی که قابلیت‌اطمینان نقش کمتر مهمی داره. مثلاً توی یه اپ چت، اگه یه پیام تحویل داده نشه، فاجعه نیست. ولی اگه یه درخواست برای انجام یه اکشن روی یه سرویس دریافت نشه، عواقبش خیلی بدتره. البته روش‌هایی برای قابل‌اطمینان‌ترکردنِ push notification هست، ولی توسعه‌ی پیچیده‌ای می‌طلبن که کل قضیه رو کمتر جذاب می‌کنه.

پیچیدگیِ پیاده‌سازیِ این روش خیلی کمه — کتابخونه‌ها خیلی راحت استفاده می‌شن و معمولاً بیشتر از دو-سه خط کد سمت سرور و دو خط سمت کلاینت لازم نیست.

**کِی استفاده کنیم؟** توی سناریوهایی که باید کلاینت‌های زیادی رو اول از همه باخبر کنیم و می‌تونیم روی قابلیت‌اطمینان مصالحه کنیم — مثل اپ‌های چت یا اپ‌های پایش که مدام اعلان می‌گیرن و از دست‌دادنِ یه اعلان قابل‌قبوله.

### Queue

روش پیام‌رسانیِ بعدی، صف (Queue) ـه. با صف به‌عنوان پلتفرم پیام‌رسانی، جریان کار کاملاً متفاوته: سرویسی که می‌خواد یه پیام به سرویس دیگه بفرسته، پیام رو توی یه موتور صف — مثل RabbitMQ یا MQSeries — می‌ذاره. سرویس دیگه یا به‌صورت دوره‌ای صف رو poll می‌کنه یا از صف اعلان می‌گیره و پیام رو از صف برمی‌داره.

مزیت اصلیِ صف اینه که می‌تونیم مطمئن باشیم پیام **یک‌بار و فقط یک‌بار** پردازش می‌شه — بعد از اینکه یه سرویس پیام رو گرفت، هیچ سرویس دیگه‌ای این پیام رو دریافت نمی‌کنه. علاوه بر این، صف می‌تونه تضمین کنه پیام‌ها به همون ترتیبی که دریافت شدن پردازش می‌شن — که همیشه توی REST API این‌طور نیست.

از نظر performance، این یکی از ضعیف‌ترین نقاطِ این روشه. برخلاف REST API و push notification که اتصال مستقیم بین دو سرویس رو برقرار می‌کنن، اینجا یه توقفِ اضافی داریم — خودِ صف — که مقداری تأخیر اضافه می‌کنه. علاوه بر این، اگه سرویس‌ها از polling برای بررسیِ پیام جدید استفاده کنن، معمولاً یه تایمر زمان‌بندیِ pollها رو کنترل می‌کنه که یه تأخیرِ دیگه هم اضافه می‌کنه. اگه صف از persistence استفاده کنه — یعنی پیام قبل از انتقال توی دیتابیس نوشته بشه تا قابلیت‌اطمینان بیشتر بشه — performance حتی بدتر هم می‌شه.

درباره‌ی اندازه‌ی پیام، بین موتورهای صف فرق می‌کنه — مثلاً RabbitMQ اندازه‌ی پیام رو به ۲ گیگابایت محدود می‌کنه (هرچند توصیه می‌شه پیام‌های خیلی کوچیک‌تر استفاده بشن)، IBM WebSphere MQ اندازه رو به ۱۰۰ مگابایت محدود می‌کنه. با این حال، best practice همیشه استفاده از پیام‌های کوچیک‌تره — اگه محتوای پیام خیلی بزرگه (مثلاً یه فایل ویدیویی)، باید توی یه دیتاستور بیرونی ذخیره بشه و خودِ پیام فقط یه ارجاع به محل ذخیره‌شدنش رو نگه داره.

مدل اجرای صف، همون‌طور که گفتیم، polling‌ـه. سرویسی که منتظر پیامه، باید به‌طور دوره‌ای صف رو poll کنه و پیام جدید رو بررسی کنه، و وقتی پیدا شد، بگیرتش و مدیریتش کنه.

بازخورد و قابلیت‌اطمینان چطور؟ اینجا وضعیت یه‌کم پیچیده‌تره. فرستنده‌ی پیام — یعنی کسی که پیام رو توی صف می‌ذاره — هیچ ایده‌ای نداره آیا گیرنده واقعاً پیام رو گرفته یا نه. تنها چیزی که می‌دونه اینه که آیا خودِ صف پیام رو دریافت کرده و آماده‌ی انتقالشه یا نه. از طرف دیگه، صف معمولاً ابزارهای مدیریت و پایش جامعی داره که مطمئن می‌شن پیام‌ها توی مسیر گم نمی‌شن و خودش مکانیزم‌هایی داره تا مطمئن بشه هیچ مشکلی توی مسیر پیش نمیاد. پس بازخورد برای فرستنده، فراتر از تحویلِ اولیه به صف، خیلی حیاتی نیست. نتیجه‌ی نهایی اینه که صف یکی از قابل‌اطمینان‌ترین شکل‌های پیام‌رسانیه، و اگه این اولویتِ اصلیته — به قیمتِ performance — قطعاً باید استفاده‌ش کنی.

پیچیدگی چطور؟ این هم یکی از نقاط ضعف صفه. برای استفاده ازش، باید یه موتور صف رو به معماریمون اضافه کنیم و یاد بگیریم چطور ازش استفاده کنیم — باید زمان برای آموزش و راه‌اندازی اختصاص بدیم، و موتورهای صفِ پیچیده می‌تونن نگهداریشون سخت باشه. خیلی پیچیده‌تر از یه REST API ساده‌ست.

**کِی استفاده کنیم؟** مورد استفاده‌ی معمول برای صف‌ها، سیستمی با کلی پیام در حال جریانه، جایی که ترتیب و قابلیت‌اطمینان اولویتِ اصلی‌ان و performance ثانویه‌ست. یه مثال رایج، سیستمی که حجم عظیمی از داده رو پردازش می‌کنه — داده توی صف قرار می‌گیره و نوبتش رو صبر می‌کنه، بعد پردازش می‌شه و توی دیتاستور ذخیره می‌شه. توی همچین سیستمی، performance معمولاً اولویت اصلی نیست چون هیچ کاربر یا سرویسی اونطرف منتظرِ داده‌ی پردازش‌شده نیست — داده برای استفاده‌ی آینده که هنوز مشخص نیست ذخیره می‌شه. همچین سیستمی یه مثال کلاسیک از پیام‌رسانیِ مبتنی بر صفه، چون از نقاط قوتِ صف — ترتیب و قابلیت‌اطمینان — بهره می‌بره، بدون اینکه از ضعف اصلیش — performance — آسیب ببینه.

### پیام‌رسانیِ مبتنی بر فایل و دیتابیس

آخرین روش پیام‌رسانی‌ای که بررسی می‌کنیم، پیام‌رسانیِ مبتنی بر فایل و دیتابیسه. این اصطلاحِ سنگین در واقع خیلی شبیه روشِ صفه، با یه فرق مهم. توی روشِ صف، پیام توی یه صف قرار می‌گرفت و موتورِ صف مطمئن می‌شد پیام یک‌بار و فقط یک‌بار پردازش می‌شه. توی این روش، پیام یا به‌عنوان یه فایل توی یه پوشه‌ی مشخص، یا به‌عنوان یه رکورد توی دیتابیس قرار می‌گیره. بعد از ذخیره‌شدن، سرویس‌ها به‌طور دوره‌ای فایل‌سیستم یا دیتابیس رو poll می‌کنن و دنبال پیام‌های جدید می‌گردن. وقتی پیدا شد، پیام یا با خوندنِ فایل یا با بازیابیِ داده گرفته می‌شه و پردازش می‌شه.

از مرورِ همه‌ی معیارها صرف‌نظر می‌کنیم چون خیلی شبیه معیارهای صفه، جز اندازه‌ی پیام که همون‌طور که می‌بینی توی این روش محدود نیست. ولی می‌خوام روی فرقِ اصلیِ این روش با صف تأکید کنم:

با صف، یه تضمین هست که پیام یک‌بار و فقط یک‌بار مدیریت می‌شه. توی این روش، همچین تضمینی وجود نداره.

### یه سناریوی خطرناک

فرض کن توی اپلیکیشنمون، یه سرویس داریم که مدام فایل‌سیستم رو برای فایل‌های جدیدِ حاویِ داده‌ی تله‌متری poll می‌کنه. چون می‌خوایم سیستم افزونه باشه، سه نمونه از این سرویس داریم که همگی به همون پوشه نگاه می‌کنن. حالا فرض کن یه فایل جدید به پوشه اضافه می‌شه — بلافاصله، هر سه سرویس سعی می‌کنن بازش کنن و محتواش رو پردازش کنن.

این دو مشکل ایجاد می‌کنه: **اول**، فایل ممکنه توسط اولین سرویسی که بهش دسترسی پیدا کرده قفل بشه، و بقیه استثنا می‌گیرن — که راستش از دید معماری می‌تونه چیز خوبی باشه، چون این‌طوری داده بیشتر از یه بار پردازش نمی‌شه. و این ما رو به مشکل دوم می‌رسونه: اگه فایل قابل‌دسترسی باشه، حالا سه سرویس داریم که محتواش رو پردازش می‌کنن و ذخیره می‌کنن. این ممکنه توی بعضی سناریوها قابل‌تحمل باشه، ولی توی خیلی از سناریوهای دیگه می‌تونه داده رو خراب کنه. تصور کن یه فایل حاویِ رکوردهای انتقالِ پول باشه — اگه یه رکورد بیشتر از یه بار پردازش بشه، می‌تونه برای صاحب حساب فاجعه‌بار باشه.

این مشکلات با مکانیزم‌ها و فلگ‌های پیچیده قابل‌حل‌ان، ولی بهتره اگه ممکنه ازشون دوری کنی. هر جا مکانیزم polling لازمه، بهتره از صف استفاده کنی.

### جمع‌بندی

این‌طوری بحثِ روش‌های پیام‌رسانی رو تموم می‌کنیم. همیشه یادت باشه از روش درست برای هر موقعیت استفاده کن — هیچ مشکلی نداره از بیشتر از یه روش توی سیستمت استفاده کنی، فقط مطمئن شو همیشه روش درست رو انتخاب می‌کنی.

| روش | Performance | اندازه‌ی پیام | مدل اجرا | بازخورد/قابلیت‌اطمینان | پیچیدگی |
|---|---|---|---|---|---|
| REST API | سریع | چند مگابایت | درخواست-پاسخ | بازخورد عالی، اطمینان متوسط | خیلی کم |
| Push Notification (Pub/Sub) | خیلی سریع | چند کیلوبایت | رویدادمحور، fire-and-forget | ضعیف | خیلی کم |
| Queue | کندتر | چند مگابایت تا چند گیگابایت | Polling | اطمینان بالا | زیاد |
| فایل/دیتابیس | مشابه صف | نامحدود | Polling | بدون تضمینِ یک‌بار پردازش | متوسط |
