## الگوی Factory

اسم Factory احتمالاً برات آشناست — و واقعاً هم آشناست. قبلاً توی این دوره، مخصوصاً توی بحث لایه‌ها، درباره‌ی متدهای فکتوری صحبت کردیم. ولی حالا وقتشه یه غواصیِ واقعی توی الگوی Factory بکنیم و انگیزه و توضیح کاملش رو بدیم.

پس الگوی Factory چیه؟ به زبان ساده: الگوی Factory، الگوییه که اجازه می‌ده آبجکت‌ها رو بدون مشخص‌کردنِ کلاس دقیقشون بسازیم. چرا می‌خوایم همچین کاری کنیم؟ همون‌طور که قبلاً گفتیم، مشخص‌کردنِ کلاس توی کدِ ساخت، یه اتصال محکم ایجاد می‌کنه و کد رو به اون کلاس گره می‌زنه. اگه بعداً بخوایم برای همون منطق از یه کلاس دیگه استفاده کنیم، باید همه‌ی کدهایی که این کلاس رو می‌سازن — که می‌تونن توی کل اپلیکیشن پخش باشن — رو پیدا و تغییر بدیم. الگوی Factory اجازه می‌ده از همچین اتصال محکمی دوری کنیم.

### یه مثال

فرض کن یه اپلیکیشن داریم که باید پیش‌بینیِ آب‌وهوای شهرهای مختلف دنیا رو بدونه. چند ارائه‌دهنده‌ی پیش‌بینیِ آب‌وهوا هست، و توسعه‌دهنده‌ها تصمیم می‌گیرن با ارائه‌دهنده‌ای به اسم «HotOrNotWeather» کار کنن. یه کلاس به اسم `HONWeather` با یه متد به اسم `GetWeather` می‌سازن که اسم شهر و تاریخ رو می‌گیره و دمای اون شهر توی اون تاریخ رو برمی‌گردونه:

```csharp
var hon = new HONWeather();
var temp = hon.GetWeather("Tehran", date);
```

این یه پیاده‌سازیِ ساده‌ست و کاملاً بی‌ضرر به نظر می‌رسه. شش ماه بعد از اینکه سایت به production رفت، ارائه‌دهنده‌ی خیلی موفقِ HotOrNotWeather ورشکسته می‌شه و توسعه‌دهنده‌ها باید یه جایگزین پیدا کنن. بعد از یه جست‌وجوی سخت، یکی پیدا می‌کنن به اسم «EtherNeatherWeather» — یه کلاس دیگه به اسم `ENWeather` می‌سازن با همون امضای متد `GetWeather`، همون آرگومان‌ها (شهر و تاریخ) و همون مقدار برگشتی (دما).

حالا چی؟ چون کلاس قبلی `HONWeather` مستقیماً با کلیدواژه‌ی `new` ساخته می‌شد، تیم باید همه‌ی جاهایی که این کلاس استفاده شده رو پیدا کنه و کد رو تغییر بده تا به‌جای `HONWeather`، `ENWeather` رو بسازه. این یه کار طاقت‌فرسا، خسته‌کننده و مستعد خطاست. چیزی که تیم متوجهش می‌شه اینه: new چسبه.

### راه‌حل الگوی Factory

الگوی Factory برای این مشکل یه راه‌حل پیشنهاد می‌ده. با الگوی Factory، این کارها رو می‌کنیم:

۱. یه اینترفیس به اسم `IWeatherProvider` می‌سازیم با یه متد واحد، `GetWeather`، که اسم شهر و تاریخ رو می‌گیره و دما رو برمی‌گردونه. کلاس‌های `HONWeather` و `ENWeather` این اینترفیس رو پیاده‌سازی می‌کنن.

۲. یه متد فکتوری می‌سازیم — بذار اسمش رو `GetWeatherProvider` بذاریم — که یه پیاده‌سازیِ اینترفیس `IWeatherProvider` رو برمی‌گردونه:

```csharp
public static IWeatherProvider GetWeatherProvider()
{
    return new HONWeather();
}
```

همین — یه خط. ولی همین یه خط همه‌چیز رو عوض می‌کنه. از این به بعد، وقتی کد به اطلاعات آب‌وهوا نیاز داره، به‌جای صدازدنِ مستقیمِ `HONWeather`، متد فکتوری رو صدا می‌زنه، نمونه‌اش رو می‌گیره و باهاش کار می‌کنه:

```csharp
var provider = WeatherFactory.GetWeatherProvider();
var temp = provider.GetWeather("Tehran", date);
```

کد اصلاً نمی‌دونه از چه کلاس مشخصی داره استفاده می‌کنه — و همین باعث می‌شه تغییر خیلی راحت باشه. وقتی توسعه‌دهنده‌ها بخوان از `HONWeather` به `ENWeather` سوییچ کنن، فقط کافیه کدِ داخل متد فکتوری رو تغییر بدن. همین. ببین چقدر راحته! استفاده از متد فکتوری قطعاً کدت رو راحت‌تر برای نگهداری می‌کنه — که یکی از اهداف اصلی معماره.

### فکتوری‌های پیچیده‌تر

انواع پیچیده‌تری هم از متد فکتوری هست. مثلاً فرض کن دو ارائه‌دهنده‌ی آب‌وهوا داریم — یکی برای آسیا و یکی برای اروپا — و می‌خوایم کد نسبت به منطقه‌ی موردنظر بی‌تفاوت باشه. توی این حالت، از متد فکتوری به‌عنوان جایی برای تصمیم‌گیری درباره‌ی نمونه‌ی برگشتی استفاده می‌کنیم:

```csharp
public static IWeatherProvider GetWeatherProvider(string continent)
{
    return continent switch
    {
        "Asia" => new AsiaWeather(),
        "Europe" => new EuropeWeather(),
        _ => throw new ArgumentException("Unknown continent")
    };
}
```

همون‌طور که می‌بینی، متد فکتوری اسم قاره رو می‌گیره و بر اساسش یه نمونه‌ی متفاوت برمی‌گردونه. این یه الگوی خیلی رایج توی فکتوری‌هاست — مثال‌های زیادی از فکتوری‌هایی هست که بر اساس یه پارامتر، تصمیم می‌گیرن کدوم نمونه رو برگردونن. یه الگوی رایج دیگه هم استفاده از یه فایل پیکربندیِ بیرونی برای تصمیم‌گیری درباره‌ی نمونه‌ی برگشتیه.

### جمع‌بندی

الگوی Factory، همون‌طور که احتمالاً حالا فهمیدی، خیلی محبوبه و به‌حق هم همین‌طوره. زندگیت رو خیلی راحت‌تر می‌کنه و کدت رو خواناتر، منعطف‌تر و راحت‌تر برای نگهداری می‌کنه. علاوه بر این، الگوی Factory اغلب پایه‌ی الگوهای دیگه هم هست — همون‌طور که توی الگوی Repository می‌بینیم.

پس نتیجه‌ش ساده‌ست: همیشه تلاش کن از الگوی Factory استفاده کنی. یادت باشه: new چسبه. با الگوی Factory از اتصال محکم دوری کن.
