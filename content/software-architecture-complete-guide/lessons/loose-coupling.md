## اتصال سست (Loose Coupling)

قبلاً توی بخش اجزای نرم‌افزاری درباره‌ی اتصال سست حرف زدیم، اونجا که گفتیم باید کلاس‌ها رو با تزریق وابستگی از هم مستقل کنیم تا تغییر یه کلاس، لزوماً کلاس‌های دیگه رو تحت‌تأثیر قرار نده. این مفهوم توی معماری سیستم هم صادقه، فقط توی یه مقیاس دیگه.

وقتی درباره‌ی اتصال سست توی معماری سیستم حرف می‌زنیم، منظورمون اینه که مطمئن بشیم اجزا یا سرویس‌های مختلف، به سرویس‌های دیگه گره محکم نخوردن. دلیلش هم شبیه دلیل اتصال سست توی داخلِ اجزاست: اگه سرویس‌ها به هم گره بخورن، هر بار که یه سرویس تغییر کنه — و توی سیستم‌های مدرن این خیلی زیاد اتفاق می‌افته — این تغییر ممکنه سرویس‌های دیگه‌ای که ازش استفاده می‌کنن رو هم تحت‌تأثیر بذاره. با اتصال سستِ سرویس‌ها، استقلال هر سرویس رو تضمین می‌کنیم و مطمئن می‌شیم می‌شه با کمترین تأثیر روی سرویس‌های دیگه (اگه اصلاً تأثیری باشه) تغییرشون داد. این سیستمت رو خیلی منعطف‌تر و قطعاً راحت‌تر برای نگهداری می‌کنه.

### یه سؤال خوب

حالا شاید بپرسی: چون سرویس‌های مختلف توی فرایندهای جدا اجرا می‌شن و کدشون رو با هم شریک نیستن، اصلاً اتصال سست چه فایده‌ای داره؟ یعنی وقتی یه کلاس توی سرویس A تغییر می‌کنه، ربطی به کلاس‌های سرویس B نداره، درسته؟ خب، سؤال خیلی خوبیه.

اتصال سست توی سرویس‌ها یا اجزا، معنای متفاوتی از اتصال سست داخل یه جزء داره. به‌طور کلی، اتصال سست توی سرویس‌ها یعنی اینکه اینکه یه سرویس روی یه پلتفرم خاص پیاده‌سازی شده یا یه API خاص در معرض دید گذاشته، سرویس‌های دیگه رو مجبور به استفاده از همون پلتفرم نمی‌کنه. علاوه بر این، اتصال سست یعنی تغییرات توی API یه سرویس — مثل URL یا پارامترهاش — باید کمترین تأثیر (یا هیچ تأثیری) روی سرویس‌های فراخوان‌کننده بذاره.

### یه مثال

فرض کن یه سرویس داریم که قیمت سهام رو در معرض دید می‌ذاره. این سرویس با Java نوشته شده. حالا فرض کن یه سرویس دیگه لازم داریم که پرتفوی مشتری‌ها رو مدیریت کنه. طبیعتاً این سرویس باید از سرویس قیمت سهام داده بخواد. سرویس سهام، APIش رو با Java RMI (Remote Method Invocation) در معرض دید می‌ذاره — یه روش ساده، سریع و مؤثر برای اجرای API روی آبجکت‌های ریموت. مشکل اینه که با RMI، سرویس فراخوان‌کننده — یعنی سرویس پرتفوی — هم باید با Java توسعه داده بشه؛ این یه محدودیتِ Java RMI‌ـه. پس توی این مثال، یه اتصال محکم ایجاد کردیم — پیاده‌سازیِ سرویس سهام، توسعه‌دهنده‌ها رو مجبور کرد سرویس پرتفوی رو هم با Java بسازن.

### یه مثال مدرن‌تر

فرض کن توسعه‌دهنده‌های سرویس سهام می‌فهمن RMI راه‌حل درستی برای اپ‌های مدرن نیست و به REST API — استاندارد de facto امروزی برای API — سوییچ می‌کنن. یه سرویس دیگه که پیشنهاد سرمایه‌گذاری می‌سازه، با Python توسعه داده می‌شه و از سرویس سهام داده می‌خواد — این بار با یه فراخوانی REST. توجه کن که این‌بار سرویس با Python پیاده‌سازی شده و هیچ مشکلی هم نیست.

همه‌چیز چند ماه خوب پیش می‌ره. بعد، سرویس سهام به یه URL جدید — به دلایل مربوط به IT — منتقل می‌شه. حالا چی می‌شه؟ چون URL سرویس سهام تغییر کرده، همه‌ی سرویس‌هایی که باهاش کار می‌کنن باید کدشون رو تغییر بدن و به URL جدید اشاره کنن. این یعنی یه چیز: بین سرویس‌ها اتصال محکم وجود داره — حتی با اینکه خودِ API با یه REST API استانداردِ مستقل از پلتفرم در معرض دید گذاشته شده.

### شبکه‌ی تار عنکبوت

برای روشن‌شدنِ بیشتر، بیا درباره‌ی یه اپلیکیشنِ کامل حرف بزنیم. این اپلیکیشن احتمالاً حداقل شش سرویس داره. طبیعتاً باید با هم ارتباط برقرار کنن. اگه مستقیم و به همین شکل با هم ارتباط برقرار کنن، به یه چیزی به اسم «شبکه‌ی تار عنکبوت» (spider web) می‌رسیم — احتمالاً می‌فهمی چرا این اسم رو داره. حالا تصور کن اگه یه سرویس URLش رو عوض کنه چی می‌شه — ببین چند سرویس تحت‌تأثیر قرار می‌گیرن. اگه نقشه‌ی سرویس‌هات شبیه یه تار عنکبوت باشه، آماده باش که با تغییر حتی یه URL، یه سورپرایز ناخوشایند دریافت کنی. تار عنکبوت، نشونه‌ی مطمئنِ یه سیستم با اتصال محکمه.

### دو راه برای حل این مشکل

**۱. ساختن یه دایرکتوریِ زردصفحه (Yellow Pages):** هر وقت یه سرویس نیاز به ارتباط با سرویس دیگه داره، از دایرکتوری، URL اون سرویس رو می‌پرسه و از همون استفاده می‌کنه. این‌طوری، URL توی کد سرویس هاردکد نمی‌شه، و وقتی تغییر می‌کنه، فقط یه جا تحت‌تأثیر قرار می‌گیره: خودِ دایرکتوری. توی این راه‌حل، فقط یه URL هست که سرویس‌ها باید بشناسن — URL دایرکتوری. می‌تونی خودت یکی بسازی، یا از ابزارهای خوبی که همین کار رو می‌کنن — مثل Consul — استفاده کنی.

**۲. ساختن یه میانجی یا دروازه (Gateway):** توی این سناریو، سرویس به میانجی دسترسی پیدا می‌کنه و ازش می‌خواد بره سراغ سرویس سهام و یه کوئری بزنه. میانجی یه جدولِ نگاشتِ داخلی داره که وظیفه‌ها رو به URLها نگاشت می‌کنه، پس می‌دونه برای انجام وظیفه‌ای که سرویس فراخوان‌کننده خواسته، به کدوم URL بره. سرویس فراخوان‌کننده اصلاً نمی‌دونه URL سرویس سهام چیه، یا حتی اصلاً همچین سرویسی وجود داره یا نه — فقط می‌دونه از میانجی خواسته یه کاری بکنه و انجام شده. اهمیتی نمی‌ده چطور، کجا و توسط کی. توی این راه‌حل هم فقط یه URL هست که سرویس باید ازش خبر داشته باشه — میانجی. پس تغییرات فقط به همین یه URL محدود می‌مونن.

### جمع‌بندی

مهم نیست کدوم راه‌حل رو انتخاب می‌کنی — هر دو خوبن. نسخه‌های ترکیبیِ این دو رو هم می‌بینی، و بعضی‌وقت‌ها حتی خوبه هر دو رو پیاده کنی. ولی نکته‌ی مهم اینه که با استفاده از حداقل یکی از این‌ها، از اتصال محکم دوری کنی. همیشه ایده‌ی خوبیه که سرویس‌هات رو تا حد ممکن سست‌متصل نگه داری — این‌طوری سیستمت خیلی منعطف‌تر و قابل‌نگهداری‌تر می‌شه.
