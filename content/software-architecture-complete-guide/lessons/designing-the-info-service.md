## طراحی سرویس اطلاعات

آخرین سرویسِ سیستممون، سرویسِ Infoـه. برای یادآوری: این سرویس به کاربرهای نهایی اجازه می‌ده داده‌ی ذخیره‌شده توی دیتاستور رو کوئری بزنن و به شکل‌های مختلف نمایشش بدن. توجه کن که این سرویس فقط مسئولِ بازیابیِ داده‌ست — خودش داده رو نمایش نمی‌ده. اون مسئولیتِ کلاینته، هر کلاینتی که باشه.

### نوعِ اپلیکیشن

اول، بیا نوعِ اپلیکیشن رو مشخص کنیم. راستش این یکی هم راحته. یه سرویس داریم که باید توسط کلاینت‌های مختلف برای اجرای چندتا کوئری در معرض دسترسی باشه. این کتابِ درسیِ یه سرویسِ وب APIـه — چون وب API برای تقریباً هر نوع کلاینتی قابل‌دسترسه و منتظرِ درخواستِ کلاینت می‌مونه قبل از فرستادنِ پاسخ. پس این هم حل شد.

### پشته‌ی فناوری

حالا بریم سراغِ پشته‌ی فناوری. اینجا هم تصمیم نسبتاً راحته. قبلاً تصمیم گرفتیم برای سرویسِ Receiver — که اونم یه وب APIـه — از .NET Core استفاده کنیم، و هیچ دلیلِ واقعی‌ای برای انتخابِ یه فناوریِ دیگه برای سرویسِ Info نیست. پس اینجا هم از .NET Core استفاده می‌کنیم.

### معماری

حالا بریم سراغِ معماری. با نگاه به معماریِ لایه‌ایِ کلاسیک، به نظر می‌رسه یه تطبیقِ کاملیه. قطعاً به لایه‌ی سرویس نیاز داریم. قطعاً به لایه‌ی منطقِ کسب‌وکار برای اعتبارسنجیِ درخواست‌ها نیاز داریم. و البته به لایه‌ی دسترسیِ داده برای دسترسی به دیتابیس و بازیابیِ داده نیاز داریم. و یادمون نره، لاگ‌گیری.

پس این همه‌شه؟ خب، نه دقیقاً. یکی از قدم‌های مهمِ فازِ معماری، تعریفِ متدهای دقیقِ APIـه. توی سرویسِ Receiver این کار رو نکردیم چون متدها توسط دستگاه‌ها تعیین می‌شدن. ولی اینجا توی موقعیتِ متفاوتی هستیم و می‌تونیم خودمون تصمیم بگیریم چه اکشن‌هایی رو به‌عنوانِ بخشی از API در معرض دید بذاریم.

### طراحیِ متدهای API

بعد از بحث با مشتری، به نظر می‌رسه چیزی که واقعاً برای کاربرهای نهایی جالبه، دو نوع اطلاعاته: **وضعیتِ فعلیِ دستگاه‌ها** و **رویدادهای گذشته**. علاوه بر این، کاربرهای نهایی می‌خوان هم وضعیتِ یه دستگاهِ خاص رو ببینن، هم یه دیدِ سطح‌بالا از همه‌ی دستگاه‌های یه خونه‌ی هوشمندِ خاص. پس API باید این قابلیت‌ها رو داشته باشه:

۱. گرفتنِ همه‌ی به‌روزرسانی‌های دستگاه‌های یه خونه‌ی خاص برای یه بازه‌ی زمانیِ مشخص
۲. گرفتنِ به‌روزرسانی‌های یه دستگاهِ خاص برای یه بازه‌ی زمانیِ مشخص
۳. گرفتنِ وضعیتِ فعلیِ همه‌ی دستگاه‌های یه خونه‌ی خاص
۴. گرفتنِ وضعیتِ فعلیِ یه دستگاهِ خاص

### طراحیِ path‌های REST

چطور این قابلیت‌ها رو به اکشن‌های REST API تبدیل کنیم؟ این دوره یه دوره‌ی کاملِ طراحیِ API نیست، پس همه‌ی عوامل و ملاحظاتِ طراحیِ API رو بررسی نمی‌کنیم، ولی کافیه بدونیم چیزی که واقعاً مهمه معمولاً دو عاملِ اصلیه: **مسیرِ API** و **کدِ پاسخ و محتواش**.

همون‌طور که یادته، REST API موجودیت (یا موجودیت‌ها)ی موردنظر برای بازیابی رو با یه مسیر که بخشی از URL‌ـه و با فعلِ HTTP `GET` مشخص می‌کنه. مثلاً برای گرفتنِ دستگاهِ شماره‌ی ۱۷، می‌شه از چیزی شبیهِ `GET /devices/17` استفاده کرد، و در پاسخ، یه محتوای JSON با کدِ پاسخِ ۲۰۰ دریافت کرد، که نشون می‌ده همه‌چیز خوبه و کوئری انجام شده.

حالا چطور APIای طراحی کنیم که با قابلیتِ موردنیاز جور دربیاد؟ بیا دوباره ببینیم چی می‌خوایم بازیابی کنیم: «همه‌ی به‌روزرسانی‌های دستگاه‌های یه خونه‌ی خاص برای یه بازه‌ی زمانیِ مشخص». موجودیت‌های مهمِ اینجا رو مشخص کنیم: خونه، دستگاه، و به‌روزرسانی. توی REST API، وقتی موجودیت‌های تودرتو داریم، همیشه از بیرونی‌ترینشون شروع می‌کنیم — توی این حالت، خونه، چون شاملِ دستگاه‌هاست که خودشون شاملِ وضعیت‌هان.

پس API درستِ این نیازمندی همین‌شکلی می‌شه:

```
GET /houses/{houseId}/devices/updates?from={date}&to={date}
```

بیا این URL رو بررسی کنیم. اول دنبالِ یه خونه با شناسه‌ی `houseId` می‌گردیم — کلاینت شناسه‌ی خونه‌ای که می‌خواد به‌روزرسانیش رو بگیره اینجا می‌ذاره. بعد به API می‌گیم برای این خونه، دستگاه‌ها رو می‌خوایم. و برای دستگاه‌ها، به‌روزرسانی‌ها رو می‌خوایم، نه مثلاً شماره‌ی سریال یا نسخه‌ی firmware.

و بازه‌ی زمانی چطور؟ این با **پارامترهای query string** تنظیم می‌شه. چرا این پارامترها بخشی از URL نیستن؟ چرا به‌عنوانِ پارامترِ جدا پاس داده می‌شن، نه مثلاً `/houses/{houseId}/devices/updates/{from}/{to}`؟

جوابش خیلی ساده‌ست: URL شاملِ ارجاع به موجودیت‌های واقعیه. یه خونه با شناسه‌ی مشخص هست. دستگاه‌هایی داخلِ این خونه هست که به‌روزرسانی دارن. این‌ها همه موجودیت‌های واقعی‌ان که شناسه، ویژگی و کارکرد دارن. بازه‌ی زمانی، از طرف دیگه، فقط یه پارامتره. موجودیت نیست. مقادیرِ `from` و `to` فقط مقادیری‌ان که کمک می‌کنن به‌روزرسانی‌های درست رو بازیابی کنیم. و دقیقاً به همین دلیل، بخشی از URL نیستن — موجودیت نیستن، فقط پارامترن و به همین شکل هم پاس داده می‌شن.

### کدهای پاسخ

خب، مسیرِ API رو داریم. ولی چی باید برگردونه؟ همون‌طور که گفتیم، فوق‌العاده مهمه که به‌وضوح مشخص کنیم کدِ پاسخ برای هر موقعیت چی باید باشه. مثلاً وقتی به‌روزرسانیِ واقعی برای برگردوندن هست، کدِ پاسخ باید ۲۰۰ باشه — یعنی OK. ولی وقتی خونه پیدا نمی‌شه چی؟ وقتی کلاینت اشتباه می‌کنه و به‌جای درخواستِ خونه‌ی شماره‌ی ۱۰۱، خونه‌ی ۱۰۲ رو می‌خواد که وجود نداره؟

توی این حالت، API باید ۴۰۴ برگردونه — یعنی «پیدا نشد». وقتی کلاینت این کدِ پاسخ رو بگیره، می‌فهمه یه چیزی با داده‌ای که فرستاده اشتباه بوده و شاید دوباره امتحان کنه، این‌بار با شناسه‌ی درست.

همون‌طور که می‌بینی، کدهای پاسخ نقشِ مهمی توی طراحیِ API دارن و باید کاملاً درباره‌شون فکر کنی. بعضی معمارهای جونیور اهمیتِ کدهای پاسخ رو نمی‌فهمن و همیشه از API فقط ۲۰۰ OK برمی‌گردونن، فارغ از نتیجه‌ی واقعیِ درخواست. از این موضوع آگاه باش و همیشه کدِ پاسخِ درست رو برگردون.

### جدولِ خلاصه

خب، عالیه، حالا می‌دونیم اولین متدِ API چه شکلی باید باشه. یه جدول که همه‌ی متدهایی که بررسی کردیم، همراه با مسیر و گزینه‌های کدِ پاسخشون، می‌سازیم:

| متد | مسیر | کدهای پاسخِ ممکن |
|---|---|---|
| به‌روزرسانی‌های همه‌ی دستگاه‌های یه خونه | `GET /houses/{houseId}/devices/updates?from&to` | ۲۰۰، ۴۰۴ |
| به‌روزرسانی‌های یه دستگاهِ خاص | `GET /houses/{houseId}/devices/{deviceId}/updates?from&to` | ۲۰۰، ۴۰۴ |
| وضعیتِ فعلیِ همه‌ی دستگاه‌های یه خونه | `GET /houses/{houseId}/devices/status` | ۲۰۰، ۴۰۴ |
| وضعیتِ فعلیِ یه دستگاهِ خاص | `GET /houses/{houseId}/devices/{deviceId}/status` | ۲۰۰، ۴۰۴ |

خوب نگاش کن و مطمئن شو کاملاً می‌فهمی چرا این‌شکلی طراحی شدن. این جدول توی معماریِ سرویس فوق‌العاده مهمه و باید بخشی از سند معماری باشه. حتماً توش بگنجونش، چون توسعه‌دهنده‌ها رو درباره‌ی پیاده‌سازیِ واقعیِ سرویس راهنمایی می‌کنه.

### جمع‌بندی

خب، عالیه، حالا معماریِ این سرویس رو داریم و می‌تونیم ادامه بدیم.
