## آیا واقعاً به `UIControl` نیاز داریم؟

توی درس قبل، `TextBox` و `DropDownList` هر دو از کلاس پایه‌ی انتزاعی `UIControl` ارث می‌بردن تا تابع `draw` بتونه چندریختی داشته باشه. حالا بیایم `UIControl` رو کاملاً حذف کنیم:

```python
class TextBox:
    def draw(self):
        print("TextBox")


class DropDownList:
    def draw(self):
        print("DropDownList")


def draw(controls):
    for control in controls:
        control.draw()
```

```python
draw([DropDownList(), TextBox()])
# DropDownList
# TextBox
```

جالبه: با اینکه هیچ کلاس پایه‌ی مشترکی بینشون نیست، این کد **دقیقاً همون‌طور که قبلاً کار می‌کرد** کار می‌کنه!

## چرا؟ چون پایتون به نوع دقیق آبجکت اهمیت نمی‌ده

توی پارامتر `controls`، هیچ‌جا نوع دقیقش رو مشخص نکردیم — فقط یه اسمه. تنها چیزی که تابع `draw` واقعاً بهش نیاز داره اینه که:

1. `controls` پیمایش‌پذیر باشه (چون با `for` روش می‌ریم).
2. هر عضوش یه متد `draw` داشته باشه.

پایتون چک نمی‌کنه این آبجکت از کدوم کلاس ساخته شده؛ فقط موقع اجرا می‌بینه آیا متد `draw` رو داره یا نه. اگه داشته باشه، صداش می‌زنه — وگرنه با خطا مواجه می‌شی.

## «اگه مثل اردک راه بره و مثل اردک صدا کنه...»

به این رفتار می‌گیم **Duck Typing**: «اگه یه چیزی مثل اردک راه بره و مثل اردک صدا کنه، پس اردکه» — یعنی مهم نیست چه نوعی داری اعلام می‌کنی؛ مهم اینه چه رفتاری (چه متدهایی) داره. این ویژگی به این خاطره که پایتون یه زبان **پویا-تایپ** (dynamically typed) هست و نوع دقیق پارامترها رو در زمان نوشتن کد چک نمی‌کنه.

## پس چرا اصلاً از `UIControl` استفاده کنیم؟

اگه پایتون بدون کلاس پایه هم چندریختی رو پشتیبانی می‌کنه، چرا زحمت ساختن `UIControl` رو کشیدیم؟ چون داشتن یه کلاس پایه‌ی انتزاعی، هنوز هم یه **روش خوب** (good practice) حساب می‌شه: یه رابط یا قرارداد مشترک رو صریح مستند می‌کنه و مطمئن می‌شه هر نوع کنترل جدید حتماً متد `draw` رو داره — به‌جای اینکه فقط به یه قرارداد نانوشته امیدوار باشیم.
