## الگوی Repository

الگوی Repository هم یکی از شناخته‌شده‌ترین و پراستفاده‌ترین الگوهاست و خیلی خوب توی یه معماریِ لایه‌ایِ خوش‌طراحی جا می‌گیره. این الگو می‌گه ماژول‌هایی که مستقیماً با دیتاستور کار نمی‌کنن، باید کاملاً از نوع دیتاستور، زبان کوئریش، اتصالش، مدیریت تراکنشش و بیشتر بی‌خبر باشن. مثلاً اگه دیتاستور یه دیتابیس MySQL‌ـه، دستورات SQL باید فقط توسط ماژول‌هایی صادر بشن که بخشی از کدِ مدیریتِ داده هستن.

به عبارت دیگه، الگوی Repository یه تکنیکِ انتزاعِ داده رو توصیف می‌کنه که برای رسیدن به همین ایزوله‌سازی استفاده می‌شه.

شاید این تعریف آشنا به نظر برسه — چون خیلی شبیه لایه‌ی دسترسی به داده (DAL) هست که توی بحث لایه‌ها بررسی کردیم، و این تصادفی نیست. هم الگوی Repository و هم الگوی معماریِ لایه‌ای، از یه اصل مشترک نشأت می‌گیرن: منعطف و قابل‌نگهداری‌ترکردنِ نرم‌افزار. فرق اصلیشون مخاطبشونه — الگوی لایه‌ای بیشتر توسط معمارها استفاده می‌شه، و الگوهای طراحی بیشتر سمت توسعه‌دهنده‌ها هدف‌گذاری شدن. با این حال، به‌عنوان معمار، خیلی درباره‌ی الگوی Repository می‌شنوی و قطعاً باید بدونی همه‌ی این سروصدا سر چیه.

### یه مثال

فرض کن اپلیکیشنمون دپارتمانِ منابع انسانیِ شرکت رو مدیریت می‌کنه. اپلیکیشن باید عملیات CRUD (ایجاد، خواندن، به‌روزرسانی، حذف) سنتی رو روی دیتاستور انجام بده. برای عملیات خواندن، دو نیازمندی داریم: باید بتونیم یه کارمند رو با شناسه‌ش پیدا کنیم، و یه لیست از کارمندها رو با نام دپارتمانشون بگیریم.

توی یه سیستم ساده‌لوحانه، توسعه‌دهنده‌ها یه متد می‌سازن که همه‌ی دسترسی به داده رو مدیریت می‌کنه — این متد توسط لایه‌ی UI یا SI صدا زده می‌شه و کارهای سطح‌پایینِ کار با دیتابیس رو انجام می‌ده. توی مثالمون، دیتابیس SQL Server‌ـه، پس متد، دستورات SQL استاندارد صادر می‌کنه. طبیعتاً بیشتر از یه جا توی اپ نیاز به بازیابیِ داده‌ی کارمندهاست، پس توسعه‌دهنده‌ها متدهای بیشتر و بیشتری می‌سازن — همه‌شون مستقیماً به دیتابیس دستور SQL می‌فرستن، و اساساً همه‌شون همون کار واحد رو انجام می‌دن: بازیابیِ داده‌ی کارمند.

سیستم به production می‌ره و همه راضی‌ان. سه ماه بعد، فاجعه اتفاق می‌افته: یه اسم ستون باید تغییر کنه — تغییر بزرگی نیست، فقط یه غلط تایپی که باید اصلاح بشه. حالا تأثیر این تغییر کوچیک چیه؟ توی پیاده‌سازیِ فعلی، توسعه‌دهنده‌ها باید همه‌ی متدهای اپ رو بگردن، همه‌جایی که اسم قدیمی استفاده شده رو پیدا کنن و به اسم جدید تغییرش بدن. یه کار طاقت‌فرسا، خسته‌کننده و مستعد خطا که تیم رو مجبور می‌کنه بخش بزرگی از کد رو تغییر بده و در نتیجه، همه‌ی تست‌ها رو دوباره اجرا کنه.

### الگوی Repository به کمک میاد

با الگوی Repository، این متدها هیچ‌وقت مستقیم با دیتابیس ارتباط برقرار نمی‌کنن. به‌جاش، یه متد فکتوری (که حتماً الان باهاش آشنایی) رو صدا می‌زنن و یه نمونه‌ی repository می‌گیرن. repository نماینده‌ی دیتاستوره و اکشن‌هایی که اپلیکیشن بهشون نیاز داره رو در معرض دید می‌ذاره. مثلاً repository ما، که با اینترفیس `IEmployeesRepository` نمایش داده می‌شه، متدهای زیر رو در معرض دید می‌ذاره:

```csharp
public interface IEmployeesRepository
{
    Employee GetEmployeeById(int id);
    IEnumerable<Employee> GetEmployeesByDepartment(string department);
    void UpdateEmployee(Employee employee);
    void CreateEmployee(Employee employee);
    void DeleteEmployee(int id);
}
```

متد فکتوری یه کلاسِ repository رو مقداردهی اولیه می‌کنه — توی این حالت، کلاسی که با SQL Server کار می‌کنه و دستورات SQL درست رو برای هر متد صادر می‌کنه. کدِ فراخوان هیچ ایده‌ای نداره داخل کلاسِ repository چه خبره — داده ممکنه توی دیتابیس ذخیره بشه، توی یه فایل، یا حتی به سیستم‌های دیگه ارسال بشه. کدِ فراخوان اصلاً براش مهم نیست.

حالا وقتی یه ستون عوض بشه چی؟ فقط کلاسِ repository تغییر می‌کنه — هیچ کد دیگه‌ای دست‌خورده نمی‌شه. این تغییر رو خیلی ساده و متمرکز می‌کنه، که یعنی منعطف‌تر و خیلی خیلی راحت‌تر برای نگهداریه.

یه حالتِ حتی افراطی‌تر رو در نظر بگیر: چی می‌شه اگه تصمیم گرفته بشه به یه نوع دیتاستورِ دیگه سوییچ کنیم — مثلاً از SQL Server به MongoDB؟ توی یه سیستمِ بدون repository، تأثیر این تغییر عظیمه — دستورات SQL باید بازنویسی بشن، مکانیزم اتصال باید عوض بشه، تراکنش‌ها یه موجود کاملاً متفاوتن. عملاً یه بازنویسیِ کاملِ کل سیستمه.

ولی با الگوی Repository، تغییر ظریف‌تره: فقط یه کلاس جدید که اینترفیس `IEmployeesRepository` رو پیاده‌سازی می‌کنه می‌سازیم، متد فکتوری رو به کلاس جدید اشاره می‌دیم، و تمام. بقیه‌ی کلاس‌ها حتی نمی‌فهمن چیزی تغییر کرده. و این قدرتِ واقعیِ الگوی Repository‌ـه.

### جمع‌بندی

این شکلِ پایه‌ای الگوی Repository بود. شکل‌های پیشرفته‌تری هم هست که کلاس‌های generic و ارث‌بری رو شامل می‌شن و یه چهارچوب بهتر برای گسترش کارکرد ارائه می‌دن. ولی حتی توی ساده‌ترین شکلش هم، الگوی Repository یکی از مفیدترین الگوهاییه که هرگز استفاده خواهی کرد.
