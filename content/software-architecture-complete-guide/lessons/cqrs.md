## CQRS

الگوی بعدیمون، CQRS‌ـه. بله، اسمِ خنده‌داری داره، ولی مطمئنیم خودِ الگو منطقیه.

پس CQRS دقیقاً چیه؟ CQRS مخفف Command Query Responsibility Segregation‌ـه (تفکیکِ مسئولیتِ دستور و کوئری). معنی واقعیش اینه: توی سیستم‌های سنتی، همون دیتابیس برای بازیابی و آپدیتِ داده استفاده می‌شه، ولی توی سیستم‌های مبتنی بر CQRS، این دو کار به دو دیتابیسِ جداگونه تقسیم می‌شن — یعنی یه دیتابیس برای ذخیره‌ی داده و یه دیتابیس برای بازیابیِ داده، و یه سرویسی که این دو رو همگام می‌کنه.

توی نگاه اول، شاید عجیب به نظر برسه. چرا باید همچین کاری بکنیم؟ منطقی‌تر نیست بازیابی و آپدیت رو از همون دیتابیس انجام بدیم؟ خب، بعضی‌وقت‌ها آره، ولی بعضی‌وقت‌ها نه‌چندان.

### ارتباط با Event Sourcing

بیا دوباره به الگوی Event Sourcing نگاه کنیم. یادته با Event Sourcing، وضعیتِ موجودیت رو نگه نمی‌داریم، بلکه رویدادهایی که برای موجودیت اتفاق افتادن رو اضافه می‌کنیم. این یه ردیابیِ فوق‌العاده کارآمد، مدلِ داده‌ی ساده و performance عالی بهمون می‌ده. از طرف دیگه، بازیابیِ داده رو سخت‌تر می‌کنه، چون دیدِ یکپارچه‌ای از موجودیت نداریم و باید از رویدادهای موجودیت عبور کنیم تا وضعیتش رو جمع‌آوری کنیم — که یه کارِ کند و پردردسره.

الگوی CQRS دقیقاً همین مشکل رو حل می‌کنه. با CQRS، داده‌ی Event Sourcing توی دیتابیسِ A ذخیره می‌شه. هر چند وقت یه‌بار — معمولاً چند ثانیه — داده جمع‌آوری می‌شه و توی دیتابیسِ B ذخیره می‌شه، جایی که وضعیتِ موجودیت رو نشون می‌ده. داده توی هر دو دیتابیس همون موجودیت‌ها رو نمایش می‌ده، ولی توی فرمت‌های متفاوت. دیتابیسِ A برای آپدیت استفاده می‌شه — و این کار رو با Event Sourcing انجام می‌ده، که performance عالی‌ای بهش می‌ده. و دیتابیسِ B برای بازیابی استفاده می‌شه و وضعیتِ کاملِ فعلیِ موجودیت‌ها رو داره.

پس حالا هر دو دنیا رو داریم — performance عالی برای آپدیت‌ها و قابلیتِ کوئریِ راحت. همه‌ی این‌ها به لطفِ الگوی CQRS ممکنه.

### پس چرا CQRS این‌قدر رایج نیست؟

اگه همه‌چیز این‌قدر خوبه، چرا CQRS این‌قدر رایج نیست؟ چرا همه‌ی معمارها همیشه ازش استفاده نمی‌کنن؟ دلیلِ اصلی، سادگیه. برای پیاده‌کردنِ CQRS، به دو دیتابیس نیاز داریم، یه موتورِ همگام‌سازی که داده رو از دیتابیسِ A جمع‌آوری، تبدیل و توی دیتابیسِ B ذخیره کنه، و یه مکانیزمِ Event Sourcing. پیاده‌سازیِ همه‌ی این‌ها می‌تونه خیلی پیچیده باشه و همیشه هم لازم نیست. اگه با پیاده‌سازیِ فعلیِ یه دیتابیسِ واحد راضی‌ای، به همون ادامه بده.

### کِی از CQRS استفاده کنیم؟

بهترین کاربرد، توی سیستم‌هایی با آپدیتِ فرکانسِ بالاست که به قابلیتِ کوئریِ تقریباً بلادرنگ نیاز دارن. دوباره به سیستم‌های تله‌متری فکر کن — این سیستم‌ها معمولاً داده‌ی زیادی می‌گیرن و باید تا حد ممکن سریع مدیریتش کنن. این یه کاندیدای عالی برای پیاده‌سازیِ CQRS‌ـه.
