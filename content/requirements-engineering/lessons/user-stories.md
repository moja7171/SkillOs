## چابک و user story

یه فرایند برای توسعه‌ی سریع و مؤثر نرم‌افزار هست به اسم **متد چابک (Agile)**. خلاصه‌ش: توسعه و تست کد به‌صورت مداوم توی بازه‌های کوچیک به اسم **اسپرینت (sprint)** — از چند روز تا چند هفته، ولی معمولاً دو هفته.

توی چابک، فیچرهایی که پیاده‌سازی می‌شن، همیشه از نیازمندی‌هایی که توی این دوره درباره‌شون صحبت می‌کنیم نمیان؛ بلکه از مرور فیچرهای فعلی و یه **بک‌لاگ (backlog)** از فیچرهای موردنظر مشتری، کاربران نهایی و ذی‌نفعان دیگه (مثل مدیران سیستم/دیتابیس) میان. این فیچرها با **user story** توصیف می‌شن.

user story یه نوع/زیرمجموعه‌ی سناریوئه، برای همین توی همین بخش از دوره بهش می‌رسیم. علاوه بر توسعه‌ی چابک نرم‌افزار، می‌شه ازش توی خود فرایند استخراج نیازمندی هم استفاده کرد — که توی ماژول بعدی این دوره بهش می‌رسیم.

## user story چیه

user story توصیف یه فیچر کوچیکه که کاربر یا ذی‌نفع دیگه می‌خواد توی سیستم ایده‌آلش ببینه. یادتونه گفتیم «کاربر» همیشه به معنای کاربر نهایی نیست — می‌تونه نگه‌دار، مدیر سیستم، مالک، یا حتی کاربر خصمانه (هکر، خرابکار) هم باشه. user story، یه فیچر کوچیک که به کاربر کمک می‌کنه به هدفش برسه رو توصیف می‌کنه — شبیه سناریوی معمولی، ولی توی یه جمله‌ی کوتاه و مختصر.

user story به تیم توسعه کمک می‌کنه بفهمن کاربرشون از سیستم چی می‌خواد، و گاهی چقدر خوب می‌خوان اون کار انجام بشه. همچنین به اولویت‌بندی فیچرها و مدیریت کلی توسعه‌ی سیستم کمک می‌کنه.

## ساختار: چه کسی، چه چیزی، چرا

user story از یه جمله تشکیل شده که سه‌تا رو در بر داره: **نقش (role)**، **فیچر/عملکرد** و **دلیل/توجیه (benefit)** — یعنی چه کسی، چه چیزی، چرا. معمولاً به لحن غیررسمی و محاوره‌ای نوشته می‌شه، و باید تا حد ممکن دقیق باشه، تا چیزی توی ترجمه‌ی بین ذهن نویسنده و پیاده‌سازی طراحان گم نشه.

مثال:

> به‌عنوان کاربر خودپرداز، می‌خوام بتونم از هر حسابی به هر حساب دیگه‌ای توی همون بانک پول انتقال بدم، تا بتونم بدون رفتن به بانک، از راه دور پولم رو مدیریت کنم.

- «به‌عنوان کاربر خودپرداز» = چه کسی
- «می‌خوام از هر حسابی به هر حساب دیگه پول انتقال بدم» = چه چیزی
- «تا بتونم از راه دور پولم رو مدیریت کنم» = چرا

با پیشروی از user story تا پیاده‌سازی فیچر، معمولاً بحث‌های بیشتری برای شفاف‌سازی لازمه — چون شاید user story دقیقاً همون چیزی رو که نویسنده‌ش توی ذهنش داشته توضیح نداده باشه. مثل سناریوها و نیازمندی‌ها، user storyها هم می‌تونن با اطلاعات جدید پالایش و به‌روز بشن، هرچه از تعریف مفهوم سیستم به پیاده‌سازی و تولید نزدیک می‌شیم. این به‌خصوص توی جاهایی که نیازمندی‌ها قراردادی و الزام‌آور نیستن مفیده — یکی از مزایای متد چابک.

## شش قانون سرانگشتی: INVEST

قبل از رفتن به use case، شش قانون سرانگشتی برای ساخت user story رو مرور می‌کنیم (بر اساس مقاله‌ای از Bill Wake در XP123): user story باید **مستقل (Independent)**، **قابل‌مذاکره (Negotiable)**، **باارزش (Valuable)**، **قابل‌برآورد (Estimable)**، **کوچک (Small)** و **قابل‌تست (Testable)** باشه — سرواژه‌ی این‌ها می‌شه **INVEST**.

**مستقل.** user story باید طوری نوشته بشه که سازمان بتونه به‌تنهایی پیاده‌سازی، تست و تحویلش بده — بدون وابستگی به user story دیگه. اگه دو user story به هم وابسته به‌نظر برسن، بهتره ترکیبشون کنیم. این با ویژگی «کوچک» تعامل داره. داشتن user storyهای مستقل به ما اجازه می‌ده لیستی از اون‌ها بسازیم و بر اساس اولویت پیاده‌سازی کنیم — به مشتری فیچرهای ملموس زودتر می‌دیم و بازخورد می‌گیریم.

**قابل‌مذاکره.** اگه ذی‌نفعانی تحت‌تأثیر یه user story باشن (مثلاً فیچر یه user story روی فیچر یه user story دیگه اثر بذاره)، باید بشه بین ذی‌نفعان درگیر بحث و توافق کرد. می‌شه هر زمانی قبل از شروع پیاده‌سازی مذاکره کرد؛ بعد از شروع پیاده‌سازی، هر تغییری اثر موجی روی بقیه‌ی سیستم می‌ذاره، پس بهتره قبل از پیاده‌سازی به توافق برسیم و تغییرات رو ثبت کنیم.

**باارزش.** باید برای کاربران یا ذی‌نفعان ارزشمند باشه. این ساده‌تر از چیزیه که به‌نظر می‌رسه — چون یه فیچر ممکنه برای یه ذی‌نفع باارزش باشه و برای دیگری نه. مثلاً کدهای عیب‌یابی برای راننده‌ی ماشین بی‌فایده‌ست، ولی برای نگه‌دار خودرو خیلی باارزشه. user story باید به یه نیاز، مشکل یا هدف اولیه‌ی پروژه ردیابی بشه — اگه فیچر به این‌ها کمک نکنه، شاید اصلاً لازم نباشه (اصطلاحش **gold plating**؛ یعنی اضافه‌کردن فیچر بیشتر از حد نیاز). ارزش باید با امکان‌پذیری (هزینه، زمان، فناوری) هم متعادل بشه.

**قابل‌برآورد.** باید بشه دامنه‌ی پیاده‌سازی، یکپارچه‌سازی، عیب‌یابی و تست رگرسیون فیچر رو (از نظر زمان، پول و منابع) برآورد کرد. اگه user story به‌اندازه‌ی کافی جزئی نیست که این برآورد ممکن باشه، باید به قطعات کوچیک‌تر تجزیه بشه.

**کوچک.** باید به‌اندازه‌ای کوچیک باشه که توی طول یه اسپرینت (معمولاً دو هفته) پیاده‌سازی و تست بشه. اگه بیشتر طول می‌کشه، باید تجزیه بشه. اگه user story چند تا حرف ربط داره («و»، «یا»)، احتمالاً باید به چند user story جدا تقسیم بشه — مثلاً «به‌عنوان کاربر خودپرداز، می‌خوام پول برداشت کنم، موجودی چک کنم، انتقال بدم و واریز کنم» باید به چهار user story جدا تبدیل بشه.

**قابل‌تست.** باید بشه تأیید کرد که تیم درست پیاده‌سازیش کرده. مثلاً «به‌عنوان کاربر نهایی، می‌خوام خودپرداز رابط کاربری خوبی داشته باشه» قابل‌تست نیست، چون «خوب» برای هرکس معنی متفاوتی داره. برای قابل‌تست‌کردنش باید بگیم «می‌خوام خودپرداز با استاندارد رابط کاربری XYZ سازگار باشه» — که خودش قابل تجزیه به user storyها یا نیازمندی‌های سطح پایین‌تره.

> جمع‌بندی: user story جمله‌ای کوتاه با ساختار «چه کسی، چه چیزی، چرا»ست که فیچرهای کوچیک رو توصیف می‌کنه. شش قانون INVEST (مستقل، قابل‌مذاکره، باارزش، قابل‌برآورد، کوچک، قابل‌تست) کمک می‌کنن user storyهای خوبی بنویسیم.
