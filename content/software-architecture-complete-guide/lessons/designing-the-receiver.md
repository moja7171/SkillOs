## طراحی دریافت‌کننده (Receiver)

سرویسِ بعدیمون، Receiverـه. بیا یه یادآوریِ سریع بکنیم: Receiver سرویسیه که پیام‌ها رو از دستگاه‌های IoT دریافت می‌کنه و برای مدیریت‌شدن توسط Handler به صف می‌فرسته.

### نوعِ اپلیکیشن

اول، این سرویس چه نوع اپلیکیشنیه؟ خب، این یکی راحته. گفتیم دستگاه‌ها پیام‌هاشون رو از طریق HTTP و با پروتکل REST می‌فرستن. پس نتیجه‌ی واضح اینه که این سرویس یه وب API‌ـه که endpointهای REST در معرض دید می‌ذاره. خوبه. واقعاً راحت بود.

### پشته‌ی فناوری

بریم سراغِ قدمِ بعدی، انتخابِ پشته‌ی فناوری. این هم یه تصمیمِ راحته. قبلاً تصمیم گرفتیم اولین سرویس بر پایه‌ی .NET Core باشه، و باید یه دلیلِ خیلی خوب برای انحراف از این تصمیم داشته باشیم. استفاده از چند فناوریِ مختلف توی یه اپلیکیشنِ واحد، اگه به دلایلِ اشتباه انجام بشه، می‌تونه کلی سردرد ایجاد کنه. پس بیا ببینیم آیا دلیلِ خوبی برای ادامه‌ندادنِ .NET Core توی این سرویس هست.

آیا .NET Core پشتیبانیِ خوبی از اپلیکیشن‌های وب API داره؟ جواب، قطعاً بله‌ست. از پایه برای پشتیبانی از اپلیکیشن‌های وب API با کتابخونه‌های ASP.NET Core ساخته شده و پشتیبانیِ عالی‌ای ازش داره. علاوه بر این، performanceِ وب APIش هم عالیه. پس به نظر می‌رسه هیچ دلیلی برای استفاده‌نکردن از .NET Core اینجا نیست، و همینه که استفاده می‌کنیم.

### معماریِ سرویس

بریم سراغِ معماریِ سرویس. یادته معماریِ لایه‌ای که قبلاً بررسی کردیم؟ بیا ببینیم آیا برای این سرویس هم مناسبه. وقتی به دیاگرامی که سه لایه‌ی کلاسیکِ معماری رو نشون می‌ده نگاه می‌کنیم، به نظر می‌رسه دقیقاً برای سرویسمون مناسبه، ولی یه نگاهِ دقیق‌تر یه مشکل رو نشون می‌ده. به لایه‌ی پایینی، لایه‌ی دسترسیِ داده، نگاه کن. یادته سرویسمون قراره با پیام‌ها چیکار کنه؟ قراره توی یه صف بذارتشون. درسته، این سرویس هیچ دیتاستوری نداره. البته می‌تونی بگی صف هم یه نوع دیتاستوره، ولی توی واقعیت این‌طور باهاش رفتار نمی‌کنیم — بلکه به‌عنوانِ یه روشِ انتقالِ پیام از یه نقطه به نقطه‌ی دیگه.

پس درحالی‌که سرویسمون قطعاً به یه لایه‌ی سرویس (که دستگاه‌ها باهاش حرف می‌زنن) و لایه‌ی منطقِ کسب‌وکار (که پیام‌ها رو اعتبارسنجی می‌کنه) نیاز داره، باید لایه‌ی دسترسیِ داده رو با یه لایه‌ی دیگه جایگزین کنیم. توی این حالت، یه لایه‌ی جدید به اسم **لایه‌ی مدیریتِ صف** می‌سازیم که مسئولِ وظایفِ مختلفِ کار با صفه — عمدتاً اضافه‌کردنِ پیام به صف.

این یه مثالِ عالی از قدرتِ معماریِ لایه‌ایه. باید یه کارکردِ کاملِ سیستم رو با استفاده از صف به‌جای دیتاستور جایگزین می‌کردیم، و فقط یه لایه تحتِ‌تأثیر قرار گرفت. لایه‌ی سرویس و لایه‌ی منطقِ کسب‌وکار هیچ ایده‌ای ندارن چیزی تغییر کرده. لایه‌ی سرویس همچنان دقیقاً همون‌طور که قبل از تغییر با لایه‌ی منطقِ کسب‌وکار کار می‌کرد کار می‌کنه، و لایه‌ی منطقِ کسب‌وکار همچنان با اینترفیس‌هایی که نماینده‌ی لایه‌ی داده‌ان کار می‌کنه و هیچ ایده‌ای نداره پیاده‌سازیِ مشخص عوض شده. پس اگه از خودت بپرسی چرا معماریِ لایه‌ای لازمه، امیدواریم الان جوابت رو گرفته باشی.

### لایه‌ی لاگ‌گیری

آخرین ولی نه کم‌اهمیت‌ترین، یه لایه‌ی لاگ‌گیری اضافه می‌کنیم تا سرویس بتونه هر چیزی که موقعِ دریافتِ پیام اتفاق می‌افته رو لاگ کنه. حالا ببین این چطور توی دیاگرام نشون داده می‌شه — این یه لایه‌ی معمولی نیست و بینِ لایه‌های دیگه قرار نمی‌گیره. شبیهِ یه **لایه‌ی عمودی**ـه، یا به اصطلاحِ حرفه‌ای‌تر، یه **cross-cutting concern**. این نوع لایه، که دقیقاً یه لایه نیست، برای همه‌ی لایه‌ها در دسترسه — که منطقیه، چون همه‌ی لایه‌ها باید بتونن هر چیزی که درباره‌ی پیام‌هایی که مدیریت می‌کنن اتفاق می‌افته رو لاگ کنن. پس همه‌ی لایه‌ها یه ارجاع به مکانیزمِ لاگ‌گیری دارن و از این cross-cutting concern بهره می‌برن.

### تطبیق با نیازمندی‌های غیرکارکردی

خب، الان زمانِ خوبیه که برگردیم به نیازمندی‌های غیرکارکردیِ تعریف‌شده برای سیستم و مطمئن بشیم معماریمون باهاشون سازگاره. راستش دو نیازمندیِ غیرکارکردی برای این سرویس مرتبطه: نیازمندیِ load که روی ۵۴۰ درخواستِ همزمان تنظیم شده (۵۰۰ تاش از دستگاه‌هاست) و نیازمندیِ از‌دست‌رفتنِ پیام که روی ۱٪ از‌دست‌رفتنِ مجاز ایستاده.

بیا با نیازمندیِ load شروع کنیم. با ۵۰۰ درخواستِ همزمان، با طراحیمون کاملاً راحتیم. معماری کاملاً stateless‌ـه و به‌راحتی scale out می‌شه. اضافه کن به این واقعیت که سرویس، به‌خاطرِ performance، کارِ زیادی جز اضافه‌کردنِ پیام به صف انجام نمی‌ده، و به نظر می‌رسه این سرویس هیچ مشکلی با رعایتِ این عدد نخواهد داشت.

و نیازمندیِ از‌دست‌رفتنِ پیام چطور؟ یادته زودتر گفتیم فرقِ اینکه نیازمندی ۹۹٪ باشه، نه ۱۰۰٪، خیلی بزرگه؟ اینجاست که این فرق رو می‌بینیم. چون ۱٪ از پیام‌ها می‌تونن از دست برن، یه REST API استاندارد کافیه. احتمالِ از‌دست‌رفتنِ بیشتر از ۱٪ درخواست توی همچین APIای خیلی خیلی پایینه، و از اونجایی که سرویس اصلاً کارِ زیادی انجام نمی‌ده، می‌تونیم راحت با این نیازمندی کنار بیایم. اگه باید مطمئن می‌شدیم هیچ‌جور هیچ پیامی از دست نمی‌ره، توی موقعیتِ خیلی سخت‌تری بودیم و احتمالاً باید یه مکانیزمِ پیچیده‌ی failsafe پیاده می‌کردیم تا مطمئن بشیم پیام همیشه دریافت می‌شه.

### جمع‌بندی

و این‌طوری معماریِ سرویسِ Receiver رو تموم می‌کنیم. الان یه معماریِ کامل برای این سرویسِ مهم داریم، شاملِ نوعِ اپلیکیشن، پشته‌ی فناوری، و معماریِ درونیش — از جمله مکانیزمِ لاگ‌گیری. عالیه، حالا می‌تونیم بریم سراغِ سرویسِ بعدی.
