## لاگ‌گیری و پایش

سیستم‌های نرم‌افزاری، موجودات پیچیده‌ای هستن. کلی قطعه‌ی متحرک دارن و در نتیجه، کلی چیز می‌تونه اشتباه پیش بره. و مطمئن باش، اشتباه پیش می‌ره — این یکی از اصول ثابتِ دنیای نرم‌افزاره. سؤال واقعی اینه: وقتی یه چیزی اشتباه پیش می‌ره، چه اتفاقی می‌افته؟ گاهی همین جواب، فرقِ بین یه سیستمِ خوش‌معماری و قابل‌نگهداری با یه سیستمی که دید تصویر بزرگ نداره رو مشخص می‌کنه.

یه معماریِ خوب همیشه شامل موتورهای لاگ‌گیری و پایشه. این‌ها سنگ‌بنای سیستم‌های قابل‌نگهداری‌ان و پیدا‌کردن و رفعِ مشکل رو خیلی ساده‌تر و سریع‌تر می‌کنن. هدف اینه که وقتی مشکلی پیش میاد، یه نگاهِ سریع به لاگ‌های سیستم، فوراً ما رو به منشأ مشکل هدایت کنه و تا حد ممکن اطلاعات درباره‌ی مشکل — مثل مصرف بالای حافظه یا تعداد استثنای بالاتر از حد معمول — بهمون بده.

قبلاً توی بخش معماریِ اجزا درباره‌ی لاگ‌گیری و پایش صحبت کردیم؛ حالا می‌خوایم دو موضوعِ خیلی مهم برای یه سیستمِ کامل بهش اضافه کنیم.

### ۱. سرویس لاگ مرکزی

چون بیشتر سیستم‌ها از بیشتر از یه سرویس تشکیل شدن که معمولاً توسط تیم‌های جدا توسعه داده می‌شن، هر تیم اغلب مکانیزم لاگ‌گیریِ خودش رو داره. نتیجه‌ش اینه که هر سرویس فرمتِ لاگ خودش، داده‌ی لاگ خودش و محل لاگ خودش رو داره — یه سرویس شاید لاگش رو توی فایل‌سیستم به‌شکل یه فایلِ فرمت‌ثابت نگه داره، یکی دیگه رکوردهای لاگ رو توی یه دیتابیس رابطه‌ای ذخیره کنه، و سومی سندهای JSON رو توی یه دیتابیس NoSQL بذاره. هر کدوم رویکردِ مشروعی‌ان، ولی فهمیدنِ اینکه واقعاً توی سیستم چه خبره خیلی سخت می‌شه — چون توسعه‌دهنده‌ها باید به کلی منبعِ مختلف با فرمت‌های مختلف نگاه کنن تا لاگ‌ها رو بخونن.

رویکردِ ترجیح‌داده‌شده اینه: یه **سرویس لاگ مرکزی** بسازیم که همه‌ی سرویس‌های دیگه توش می‌نویسن. این سرویس مرکزی، لاگ‌ها رو توی یه مخزنِ مرکزی — ترجیحاً یه دیتابیس برای بهبودِ کوئری‌پذیری و تحلیل — ذخیره می‌کنه، و در نتیجه یه نقطه‌ی واحد برای دیدنِ داده‌ی لاگ ایجاد می‌کنه.

روش‌های مختلفی هست که سرویس می‌تونه لاگ‌ها رو بگیره — می‌تونه یه API در معرض دید بقیه‌ی سرویس‌ها بذاره، یا پوشه‌های خاصی رو برای فایل‌های لاگ زیر نظر بگیره و جمعشون کنه. ابزارهایی مثل Logstash دقیقاً همین کار رو می‌کنن — یه پوشه رو زیر نظر می‌گیرن و وقتی فایلی اضافه یا تغییر می‌کنه، جمعش می‌کنن و توی یه دیتاستور ذخیره می‌کنن. مهم نیست کدوم روش رو انتخاب می‌کنی، نتیجه‌ی نهایی باید یکی باشه: لاگ‌های کل سیستم باید از یه نقطه‌ی مرکزی قابل‌دسترس باشن و به‌شکل یه فرمتِ واحد ارائه بشن.

### ۲. شناسه‌ی همبستگی (Correlation ID)

وقتی سیستممون سرویس‌های زیادی داره، کلی جریان کاری داریم که بیشتر از یه سرویس رو شامل می‌شن. مثال قبلی رو یادته — یه سرویس پیشنهاد سرمایه‌گذاری که سرویس قیمت سهام رو فرا می‌خونه؟ اونجا دو سرویس توی یه جریان واحد شرکت دارن.

یکی از چالش‌های همچین جریانی، این فهمیدنه که کدوم رکورد لاگ به کدوم جریان تعلق داره. مثلاً فرض کن کاربر ۱ یه پیشنهاد می‌خواد. سرویسِ پیشنهاد از سرویس سهام داده می‌خواد، و بعد توی سرویس سهام یه خطا پیش میاد. هر دو سرویس لاگ‌گیری دارن، پس یه مستندسازیِ خوب از دقیقاً چه اتفاقی افتاده داریم. توی این حالت، یه لاگ توسط سرویسِ پیشنهاد نوشته شده که نشون می‌ده کاربر چی خواسته، و یه لاگ توی سرویس سهام که خطا رو مستند می‌کنه. تا اینجا خوبه.

ولی چی می‌شه اگه همزمان با درخواستِ کاربر ۱، یه درخواستِ دیگه از طرف کاربر ۲ هم شروع بشه؟ فرض کن توی این حالت هیچ خطایی توی سرویس سهام پرتاب نمی‌شه. حالا چهار رکورد لاگ داریم — دو تا از سرویس پیشنهاد و دو تا از سرویس سهام، که یکیش خطا رو مستند می‌کنه. چطور می‌فهمیم کدوم رکورد به کدوم جریان تعلق داره؟ واضح نیست که خطا مربوط به درخواستِ کاربر ۱ باشه، چون هیچ چیزی توی داده نیست که خطا رو به یه درخواستِ خاصِ سرویس پیشنهاد مرتبط کنه.

### راه‌حل: Correlation ID

راه‌حل این مشکل، **شناسه‌ی همبستگی (correlation ID)**ـه. correlation ID یه شناسه‌ست که توی شروعِ یه جریان اختصاص داده می‌شه و از سرویس به سرویس منتقل می‌شه. توی هر رکورد لاگ گنجونده می‌شه و اجازه می‌ده جریان رو از ابتدا تا انتها ردیابی کنیم.

خودِ correlation ID می‌تونه هر شناسه‌ای که بخوای باشه — GUID یه انتخاب محبوبه. تنها چیزی که مهمه اینه که مطمئن بشی توی شروعِ جریان ساخته می‌شه و توی هر رکورد لاگ گنجونده می‌شه. با استفاده از correlation ID، می‌تونیم راحت یه جریانِ کامل رو ردیابی کنیم و بفهمیم دقیقاً چه اتفاقی افتاده و، مهم‌تر از اون، چرا.

### جمع‌بندی

از لاگ‌گیری مرکزی و correlation ID استفاده کن تا سیستم راحت‌تر برای نگهداری بشه — مخصوصاً وقتی سیستم سرویس‌های زیادی داره که توسط جریان‌های کاریِ مختلف استفاده می‌شن.
