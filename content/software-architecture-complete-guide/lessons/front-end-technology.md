## فناوری فرانت‌اند

> این ویدیو هم نسبتاً قدیمیه (مثلاً PWA رو به‌عنوان یه استاندارد نوظهور معرفی می‌کنه) — جزئیات محبوبیت و بلوغ ابزارها رو با این در نظر بخون، ولی چهارچوب تصمیم‌گیری همچنان معتبره.

قبل از اینکه بریم سراغ فناوری فرانت‌اند، بذار یه یادآوری کوتاه بکنیم: فرانت‌اند بخشی از نرم‌افزاره که کاربر واقعی با چشم‌های خودش می‌بینه — دکمه‌ها، متن‌ها، لیست‌های کشویی، رنگ‌ها، پیام‌ها و بیشتر. پس طبیعیه که موقع انتخاب فناوری فرانت‌اند، دنبال چیزی هستیم که قابلیت‌های بصری قوی داشته باشه، ولی کارمون رو هم خیلی سخت نکنه.

### کدوم انواع اپلیکیشن اصلاً فرانت‌اند دارن؟

- **اپ وب:** قطعاً. اپ وب رو به‌عنوان اپلیکیشنی که توی مرورگر اجرا می‌شه و HTML نمایش می‌ده تعریف کردیم — قطعاً فرانت‌اند داره.
- **وب API:** نه واقعاً. کلاینت‌های وب API، اپلیکیشن‌های دیگه‌ای مثل اپ موبایل هستن که خودشون ممکنه فرانت‌اند داشته باشن، ولی خودِ اپلیکیشنِ وب API فرانت‌اند نداره.
- **موبایل:** بله، که کل هدفشه.
- **کنسول:** پیچیده‌ست. از نظر فنی یه رابط کاربری برای اپلیکیشن کنسول هست، ولی جدا از خود اپ ساخته نمی‌شه و سرمایه‌گذاری سنگینی هم روی UI اپلیکیشن کنسول نمی‌شه. پس برای بحثمون، کنسول فرانت‌اند نداره.
- **سرویس:** کل نکته‌ی سرویس همینه که رابط کاربری نداره — پس فرانت‌اندی هم درکار نیست.
- **دسکتاپ:** قطعاً. با اینکه اپ‌های دسکتاپ خیلی متنوعن، وجه اشتراک همه‌شون اینه که کاربر می‌تونه ببینه و باهاشون تعامل کنه.

### فرانت‌اند اپ وب: Angular یا React؟

فرانت‌اند اپ‌های وب، بنا به تعریف، مبتنی بر وبه — یعنی از ترکیب HTML، JavaScript و CSS استفاده می‌کنیم. سؤال واقعی اینه: از کدوم فریم‌ورک JavaScript استفاده کنیم؟ محبوب‌ترین فریم‌ورک‌ها Angular و React هستن (گزینه‌های خوب دیگه‌ای مثل Vue.js هم هست، ولی تمرکزمون روی محبوب‌ترین‌هاست).

**محبوبیت:** توی Google Trends، محبوبیت این دو تقریباً مشابهه. توی stackoverflow.com، سؤال‌های بیشتری درباره‌ی Angular هست، ولی چون Angular قدیمی‌تره (۲۰۱۰ در مقابل ۲۰۱۳ برای React)، این اعداد در واقع خیلی به هم نزدیک‌ان.

**قابلیت‌ها:** Angular یه فریم‌ورک کامله با تمام قابلیت‌هایی که یه فریم‌ورک فرانت‌اند نیاز داره — مثل data binding، مدیریت state، routing، سرویس‌ها و بیشتر. یادگیریش زمان می‌بره و حتی برای توسعه‌دهنده‌های باتجربه هم راحت نیست. React، در عوض، بیشتر یه کتابخونه‌ست تا یه فریم‌ورک کامل. تمرکزش روی رابط کاربریه و توی این کار عالیه؛ اگه قابلیت دیگه‌ای لازم باشه، باید از کتابخونه‌های جداگونه استفاده کنی. در عوض، منحنی یادگیری React خیلی کوتاه‌تره و توسعه‌دهنده‌های وب می‌تونن توی چند روز باهاش راه بیفتن، درحالی‌که آموزش Angular می‌تونه چند هفته یا بیشتر طول بکشه.

پس اگه دنبال یه راه‌حل همه‌کاره برای همه‌ی نیازهای فرانت‌اند وبت هستی و وقت آموزش داری، Angular رو انتخاب کن. در غیر این صورت، React.

### فرانت‌اند موبایل: Native، Hybrid یا Cross-Platform؟

موقع طراحی اپ موبایل، اولین کار انتخاب رویکرد توسعه‌ست. سه رویکرد اصلی هست: **Native**، **Hybrid** و **Cross-Platform**. این رویکردها نماینده‌ی مصالحه‌ی بین زمان توسعه و قابلیت‌ها هستن.

**Native:** از پلتفرم توسعه‌ی بومیِ هر سیستم‌عامل موبایل استفاده می‌کنه — مثلاً توسعه‌ی بومیِ آیفون با Objective-C یا Swift توی Xcode، و اپ‌های اندروید عمدتاً با Java توی Android Studio. محیط توسعه‌ی iOS کاملاً با اندروید فرق داره، پس به توسعه‌دهنده‌هایی جدا با تخصص هر پلتفرم نیاز داری. در عوض، اپ‌های native دسترسی کامل به همه‌ی قابلیت‌های گوشی — دوربین، شتاب‌سنج، بلوتوث، فایل‌سیستم و بیشتر — رو دارن و بهترین تجربه‌ی کاربری و بالاترین واکنش‌گرایی رو ارائه می‌دن.

**Hybrid:** کاملاً برعکسِ native‌ـه. اپ‌های hybrid یه wrapper نازک بومی ارائه می‌دن (معمولاً با ابزارهایی مثل PhoneGap) و داخلش یه صفحه‌ی وب معمولی با HTML، JavaScript و CSS هست. می‌شه اپ‌های hybrid رو مثل یه مرورگرِ فاخر با قابلیت محدود گوشی در نظر گرفت، ولی همچنان یه صفحه‌ی وبه و به اتصال اینترنت نیاز داره. دسترسی به قابلیت‌های گوشی مثل شتاب‌سنج یا دوربین می‌تونه چالش‌برانگیز باشه و محدودیت‌های زیادی داره؛ تجربه‌ی کاربری و performance گرافیکیش هم پایین‌تره.

توی سال‌های اخیر، یه استاندارد جدید به اسم **Progressive Web App (PWA)** ظاهر شده که به اپ‌های hybrid اجازه می‌ده بیشتر شبیه اپ‌های native رفتار کنن — با قابلیت آفلاین، دسترسی سخت‌افزاریِ بهتر و بیشتر. این استاندارد امیدوارکننده به نظر می‌رسه و ارزش دنبال‌کردن داره، ولی هنوز به‌اندازه‌ی کافی بالغ نیست.

بزرگ‌ترین مزیت اپ‌های hybrid، زمان توسعه‌ست. جدا از wrapper بومی که یه‌کم آموزش لازم داره، بقیه‌ی کارها توسعه‌ی وب معموله — اگه تیمت بلده اپ وب بسازه، بلده اپ hybrid هم بسازه.

**Cross-Platform:** بین native و hybrid قرار می‌گیره. توسعه توی یه محیط تخصصی انجام می‌شه که مستقیماً به هیچ‌کدوم از پلتفرم‌های موبایل وصل نیست. محیط‌های cross-platform پیشرو امروزه Xamarin و React Native هستن — توی Xamarin با #C و Visual Studio توسعه می‌دی، توی React Native با JavaScript. بعد از اتمام توسعه، اپلیکیشن رو کامپایل می‌کنی و نتیجه، اپ native برای پلتفرم انتخابی می‌شه — می‌تونی برای iOS و اندروید کامپایل کنی و اپ native برای هر دو بگیری، بدون نوشتن حتی یه خط Java یا Objective-C.

مزایاش واضحه: کد رو یه بار می‌نویسی و روی هر دو پلتفرم به‌عنوان اپ native اجرا می‌شه. معایبش چیه؟ چندتا: اول، معمولاً یه شکاف بین پشتیبانی از جدیدترین قابلیت‌های سیستم‌عامل بومی و ابزارهای cross-platform هست — ابزارهای cross-platform همیشه دارن دنبال پلتفرم‌های موبایل می‌دوند. دوم، اپ‌های cross-platform با گرافیک سنگین خوب کار نمی‌کنن — اگه برنامه‌ت اینه، باید بری سراغ native. سوم، توی بعضی سناریوها — به‌خصوص دسترسی به سنسورهای خاص — همچنان باید سراغ برنامه‌نویسی native بری، که یعنی دیگه cross-platform خالص نیست.

| رویکرد | زمان توسعه | دسترسی به قابلیت‌های گوشی | مناسب برای |
|---|---|---|---|
| Native | زیاد (تیم جدا برای هر پلتفرم) | کامل | بهترین تجربه‌ی کاربری، گرافیک سنگین، دسترسی کامل سنسورها |
| Hybrid | کم (فقط توسعه‌ی وب) | محدود | توسعه‌ی سریع، تیم‌هایی که فقط وب بلدن |
| Cross-Platform | متوسط (یک کدبیس) | تقریباً کامل، با شکاف در قابلیت‌های جدید | تعادل بین سرعت توسعه و کیفیت اپ native |

### فرانت‌اند دسکتاپ

اگه داری یه اپلیکیشن دسکتاپ برای PC می‌سازی، به احتمال زیاد هدفت ویندوزه — پس بحث رو به اپ‌های دسکتاپ مبتنی بر ویندوز محدود می‌کنیم. روی ویندوز، سه گزینه برای توسعه‌ی دسکتاپ داریم: **WinForms**، **WPF** و **UWP**.

**WinForms:** قدیمی‌ترین فناوری، معرفی‌شده توی سال ۲۰۰۱ همراه با خود .NET. از نظر مفهومی شبیه پلتفرم‌های قدیمی‌تر مثل VB6‌ـه و توی قابلیت‌های گرافیکی نسبتاً محدوده — مثلاً امتحان کن یه دکمه با گوشه‌های گرد پیاده کنی، شدنیه ولی خیلی سخته. در عوض، توسعه توی WinForms نسبتاً راحته و منحنی یادگیریش کوتاهه.

**WPF:** معرفی‌شده توی سال ۲۰۰۶، وضعیت رو به‌شکل چشمگیری بهبود می‌ده. کنترل کامل روی بصری‌سازی می‌ده و آزادی کامل به طراح‌های بصری. تقریباً هر کاری که بخوای می‌تونی بکنی. ولی، همیشه یه «ولی» هست: خیلی پیچیده‌تر از WinForms‌ـه. برای استفاده از WPF باید یه زبان جدید یاد بگیری، XAML، که شبیه HTML به‌عنوان یه زبان نشانه‌گذاری برای رابط کاربری عمل می‌کنه. XAML یه زبان نشانه‌گذاریِ خیلی غنیه و خیلی راحت می‌شه توش گم شد — حتی می‌شه گفت یه توسعه‌دهنده‌ی بی‌تجربه‌ی WPF می‌تونه آسیب بیشتری از یه توسعه‌دهنده‌ی بی‌تجربه‌ی WinForms بزنه.

**UWP (Universal Windows Platform):** تلاشی از طرف مایکروسافت برای یکپارچه‌کردن همه‌ی صفحه‌نمایش‌هاش — PC، Xbox، Windows Phone، Surface و بیشتر — زیر یه پلتفرم UI واحد. نتیجه‌ی این تلاش، UWP‌ـه، که خیلی شبیه WPF‌ـه ولی با تفاوت‌های مهمی: اول، توی یه sandbox اجرا می‌شه، یعنی دسترسی کاملی به همه‌ی قابلیت‌های سیستم‌عامل نداره (شبیه اپ‌های hybrid توی موبایل). دوم، روی همه‌ی صفحه‌نمایش‌های ویندوزی اجرا می‌شه — پس اگه می‌خوای برای ویندوز و Xbox اپ بسازی، این مسیر رو برو. سوم، خیلی کمتر از WPF بالغ شده.

| فناوری | سطح کنترل بصری | منحنی یادگیری | مناسب برای |
|---|---|---|---|
| WinForms | محدود | کوتاه | اپلیکیشن‌های ساده‌ی ویندوزی با بودجه‌ی زمانی کم |
| WPF | کامل | بلند (XAML) | اپلیکیشن‌های دسکتاپ با نیاز به طراحی بصری غنی |
| UWP | کامل (در sandbox) | بلند، ولی کمتر بالغ | اپ‌هایی که باید روی چند صفحه‌نمایش ویندوزی (PC، Xbox و…) اجرا بشن |

و حالا، بریم سراغ انتخاب فناوری ذخیره‌سازی داده.
