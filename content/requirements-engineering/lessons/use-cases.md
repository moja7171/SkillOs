تا حالا استفاده کردی از یه دستگاه و انتظار یه کار خاص رو داشتی، ولی دستگاه یه کار دیگه کرد؟ یا سخت بود استفاده‌ش؟ یا چند تا دکمه زدی و کل دستگاه هنگ کرد؟ این‌جور مشکلات رو می‌شه با یه ابزار قدرتمند به اسم **تحلیل use case** حل کرد.

## use case چیه

توی حوزه‌ی مهندسی نیازمندی‌ها، use case رو به‌عنوان ابزاری برای شناسایی و پالایش نیازمندی‌ها می‌سازیم. **use case لیستی از گام‌هاییه که یه کاربر (که به‌طور رسمی «بازیگر» یا actor نامیده می‌شه) موقع کارکردن با سیستم طی می‌کنه** — نه فقط عملیات، بلکه می‌تونه استقرار، پشتیبانی یا کنار گذاشتنِ سیستم رو هم شامل بشه. بازیگر این گام‌ها رو برای رسیدن به یه هدف مشخص، مرتبط با یه مفهوم چرخه‌ی عمر انجام می‌ده.

## چرا use case مفیده

- کمک می‌کنه مهندس نیازمندی‌ها تشخیص بده سیستم باید دقیقاً چه توابع/فعالیت‌هایی رو چقدر خوب انجام بده.
- چون از سطح بالا شروع می‌کنیم و به use caseهای کوچیک‌تر تودرتو تجزیه می‌کنیم، **طراحی بالا-به-پایین (top-down)** رو تقویت می‌کنه — روش بهینه برای مهندسی یه سیستم یا حل یه مسئله‌ی پیچیده.
- کمک می‌کنه از قبل به خطاها و نقص‌های احتمالی فکر کنیم و راه بازیابی سیستم رو طراحی کنیم — به‌جای اینکه بذاریم توی تست یا بعد از استقرار کشف بشن، که خیلی گران‌تر و زمان‌برتره.
- به تجزیه‌ی یه مسئله‌ی بزرگ به قطعات کوچیک‌تر و قابل‌مدیریت‌تر کمک می‌کنه — هر قطعه جدا حل می‌شه و بعد با هم ترکیب می‌شن.
- مطمئن می‌شه سیستم درستی می‌سازیم که نیاز اولیه رو برآورده می‌کنه — از منحرف‌شدن تیم از هدف اصلی و اضافه‌کاری بی‌مورد (gold plating) جلوگیری می‌کنه.
- برای غیرمتخصص‌ها هم قابل‌فهمه — هم برای طراحان مفیده، هم برای ذی‌نفعان.

## جایگاه use case در تصویر کلی

use case بخشی از مجموعه‌ی سناریوی مأموریتیه. یادتونه لایه‌ی مأموریت شامل مفاهیم چرخه‌ی عمره که مأموریت‌های اصلی سیستم توی هر فاز چرخه‌ی عمر (معمولاً از فاز تست/راستی‌آزمایی شروع می‌شه) رو توصیف می‌کنه. این مأموریت‌ها به فازهای مأموریت و اون‌ها به زیرفازها تجزیه می‌شن، و هر زیرفاز چند سناریو داره. use case بخشی از این ویژگی‌های سناریوهاست — فرض‌هایی درباره‌ی اینکه کاربر چطور با سیستم تعامل داره، سیستم چطور پاسخ می‌ده، و کاربر چطور به هدفش می‌رسه.

ممکنه فکر کنی باید صدها یا هزاران use case بسازیم تا همه‌ی حالت‌های ممکن رو پوشش بدیم — از نظر فلسفی شاید درست باشه، ولی عملاً توصیه نمی‌شه. ساختن use case زحمت زیادی داره؛ انجامش تا حد افراط، وقت‌گیره و تیم طراحی رو کند می‌کنه یا حتی باعث خطا می‌شه. به‌عنوان مهندس نیازمندی، باید روی مهم‌ترین جنبه‌ها یا حوزه‌های پرریسک پروژه تمرکز کنیم، نه پوشش همه‌ی جزئیات. تیم‌های طراحی باتجربه معمولاً نیازی به use case برای چیزی که ده‌ها بار انجام دادن ندارن.

## اجزای یه use case

- **بازیگر (actor یا actors):** ذی‌نفعانی که با سیستم تعامل دارن یا از یکی از سرویس‌هاش استفاده می‌کنن.
- **پاراگراف خلاصه:** یه توضیح کوتاه درباره‌ی موضوع use case.
- **هدف:** همه‌ی گام‌های use case برای رسیدن به این هدف انجام می‌شن — نتیجه‌ی اصلی که سیستم برای بازیگر فراهم می‌کنه.
- **پیش‌شرط‌ها:** چیزهایی که فرض می‌کنیم درباره‌ی سیستم، محیط یا بازیگر درسته تا use case بتونه به هدفش برسه. اگه برقرار نباشن، باید یه use case دیگه ساخته بشه که اول اون پیش‌شرط‌ها رو برقرار کنه.
- **تضمین‌ها (guarantees):** حداقل کاری که سیستم برای بازیگر انجام می‌ده، حتی اگه به هدف نرسه — مثلاً اگه خودپرداز نتونه پول بده، حداقل دلیلش رو می‌گه و کارت رو پس می‌ده.
- **محرک (trigger):** چیزی که use case رو راه می‌ندازه. بعضی‌ها محرک رو از دنباله‌ی رویدادها جدا می‌گیرن، بعضی‌ها اون رو گام اول دنباله در نظر می‌گیرن — هر دو روش قابل‌قبوله، ولی مشخص‌کردن محرک به تیم کمک می‌کنه بفهمن دقیقاً چی کار رو شروع می‌کنه.
- **دنباله‌ی رویدادها (course of events):** بخش اصلی use case — لیست شماره‌گذاری‌شده‌ای از اقداماتی که بازیگر و سیستم برای رسیدن به هدف اصلی انجام می‌دن. **دنباله‌ی اصلی، کاملاً روز آفتابیه** — نباید استثنا یا جایگزین توش باشه، مگه اینکه خود use case مخصوص پوشش یه استثنا یا جایگزین از یه use case والد باشه (که برای این‌ها فیلد جداگانه هست).
- **مسیرهای جایگزین (alternative paths):** گاهی کاربر برای رسیدن به همون هدف کار رو کمی متفاوت انجام می‌ده — مثل ذخیره‌ی سند با File→Save، Ctrl+S، یا آیکون دیسک.
- **مسیرهای استثنا (exception paths):** وقتی چیزی خراب می‌شه و بازیگر یا سیستم رو از دنباله‌ی اصلی خارج می‌کنه — این‌ها حالت‌های شکست‌ان و گام‌هایی که سیستم/بازیگر برای برگشتن به مسیر اصلی طی می‌کنن. اگه بازیابی ممکن نباشه، use case شکست می‌خوره، ولی بازیگر حداقل تضمین‌هایی که گفتیم رو می‌گیره.
- **مسیرهای توسعه (extension paths):** نقاط ارجاعی که یه use case می‌تونه به use case دیگه اشاره کنه — وقتی چند use case دنباله‌ی رویدادهای مشترک دارن، می‌شه اون بخش رو به یه use case توسعه‌ای جدا برد و توی همه‌ی use caseهای دیگه ارجاعش داد؛ این باعث می‌شه توسعه‌دهنده‌ی نرم‌افزار فقط یه بار اون بخش رو کد بزنه.
- **اطلاعات اداری:** تاریخ ایجاد/آخرین تغییر، نویسنده، مجری، وضعیت و…
- **دیاگرام‌ها:** معمولاً به فرمت UML/SysML.

## دیاگرام use case

use case با یه شکل بیضی نمایش داده می‌شه که اسمش داخلشه. بازیگر به اون از طریق یه **رابطه‌ی ارجاع (association)** وصله. اگه بازیگر آدمه، با یه آدمک نمایش داده می‌شه؛ اگه ماشینه، با یه بلوک یا آیکون. رابطه‌ی ارجاع یه **مالتی‌پلیسیتی (multiplicity)** داره که تعداد نمونه‌های بازیگر یا use case رو نشون می‌ده — مثلاً «۰..*» یعنی از صفر تا هر تعداد. سیستم می‌تونه به شکل یه بلوک نمایش داده بشه که use caseها رو دربر می‌گیره و بازیگرها بیرونش‌ان، شبیه دیاگرام بافت.

اگه یه use case کلی باشه و use caseهای جزئی‌تری مشخصش کنن، از رابطه‌ی **generalization** استفاده می‌شه. اگه یه use case داخلش به use case دیگه ارجاع بده، از رابطه‌ی **include** استفاده می‌شه. برای مسیرهای استثنا یا جایگزین، از رابطه‌ی **extend** استفاده می‌شه — این‌ها use caseهای شرایطی‌ان که بسته به موقعیت ممکنه اتفاق بیفتن یا نه.

## مثال: برداشت پول از خودپرداز

بازیگر اصلی، مشتریه؛ بازیگر پشتیبان، بانکه. use case «برداشت پول نقد» یه زیر-use case زیر یه use case اصلیه. هدف: مشتری از حساب جاری یا پس‌اندازش پول نقد برداشت کنه. پیش‌شرط: مشتری حساب جاری یا پس‌انداز فعال داشته باشه. تضمین موفقیت: مشتری پول نقد و (اختیاری) رسید می‌گیره.

نکته‌ی مهم درباره‌ی نوشتن گام‌های دنباله‌ی رویدادها: باید **کلی و عام** باشن، بدون مشخص‌کردن راه‌حل. مثلاً به‌جای «مشتری صفحه‌ی لمسی رو فشار می‌ده یا با کیبورد تایپ می‌کنه»، می‌گیم «مشتری با خودپرداز تعامل می‌کنه» — چون نمی‌دونیم راه‌حل نهایی صفحه‌ی لمسیه یا کیبورد. یا به‌جای «مشتری کارت خودپرداز رو وارد و پین رو تایپ می‌کنه»، می‌گیم «مشتری اطلاعات هویتی حساب رو ارائه می‌ده» — چون ممکنه راه‌حل نهایی تشخیص چهره یا اثر انگشت باشه. طراحان بعداً، پایین‌تر توی چرخه‌ی عمر، تصمیم می‌گیرن.

دنباله‌ی اصلی فقط روز آفتابیه — یعنی حالتی که مشتری موجودی کافی داره و اطلاعات هویتش تأیید می‌شه. حالت‌هایی مثل «موجودی کافی نیست» یا «هویت تأیید نشد» توی فیلد استثناها میان.

گام‌های اول (ارائه‌ی اطلاعات هویتی) و گام‌های آخر (پرسیدن «کار دیگه‌ای هست؟» و پایان تراکنش) توی هر use case مربوط به خودپرداز (برداشت، واریز، چک موجودی، انتقال) تکرار می‌شن. برای اینکه توسعه‌دهنده‌ی نرم‌افزار مجبور نباشه این منطق رو چندبار بنویسه، این بخش‌ها رو توی use caseهای جداگانه‌ی **مقداردهی اولیه‌ی تراکنش (initialize transaction)** و **نهایی‌سازی تراکنش (finalize transaction)** می‌بریم، و از رابطه‌ی include توی همه‌ی use caseهای دیگه ارجاعشون می‌دیم.

## چطور use caseها رو بنویسیم

use caseها رو معمولاً یه تیم کوچیک با هم می‌نویسه (نه لزوماً، ولی تجربه و دیدگاه‌های متنوع‌تری میاره). گام‌ها:

1. **مرور مستندات منبع** — بیانیه‌ی نیاز، دیاگرام بافت، مفهوم عملیاتی (OPSCON)، و نیازمندی‌های مرتبط از مشخصات (اگه موجود باشن).
2. **شناسایی و لیست‌کردن بازیگران** اصلی و فرعی که با سیستم تعامل دارن.
3. **شناسایی و لیست‌کردن اهداف** بازیگرها که معمولاً از OPSCON یا مستندات نیازمندی میاد.
4. **شناسایی و لیست‌کردن use caseهای سطح‌بالا** — تا حد امکان کلی، چون بعداً به قطعات کوچیک‌تر تجزیه می‌شن — و اولویت‌بندیشون.
5. **انتخاب use case با اولویت بالاتر** و شروع کار روش.
6. **شناسایی بازیگرها، ذی‌نفعان، پیش‌شرط‌ها و تضمین‌های** اون use case خاص.
7. **پیش‌نویس دنباله‌ی اصلی رویدادها** (فقط روز آفتابی).
8. **طوفان فکری برای مسیرهای جایگزین، توسعه و استثنا** — معمولاً بزرگ‌ترین بخش کار، چون احتمالات زیادی هست.
9. **جای‌نگه‌دار برای use caseهای سطح پایین‌تر** بسازید که بعداً بازشون کنید.
10. **مرور و بازبینی use case.**
11 و ۱۲. **رفتن سراغ use case بعدی** توی لیست اولویت‌بندی‌شده و تکرار فرایند.

برای سیستمی مثل خودپرداز، یه تیم کوچیک ممکنه یک تا دو ماه طول بده تا همه‌ی use caseهای مرتبط رو تولید، پالایش و تأیید بگیره — با فرض اینکه خودپرداز قبلاً وجود نداشته و این اولین‌باره که براش use case می‌سازیم.

## بعد از ساخت use case چیکار کنیم

use caseها بخشی از لایه‌ی مأموریت‌ان و به تولید تعاملات کاربردی که سیستم باید انجام بده کمک می‌کنن. مهندس نیازمندی اقدامات use case رو به فعالیت یا اکشن توی مدل سیستم تبدیل می‌کنه، یا اگه use case به‌اندازه‌ی کافی بالغ باشه، مستقیم گام‌ها رو به جمله‌ی نیازمندی تبدیل می‌کنه. همچنین می‌شه از دنباله‌ی رویدادها یا مسیرهای جایگزین/استثنا، دیاگرام N-squared، توالی، ماشین‌حالت یا فعالیت ساخت. use case به نیازمندی‌های محرک، مفهوم عملیاتی یا use caseهای دیگه، دیاگرام بافت، یا توابع میراثی هم ردیابی می‌شه.

> جمع‌بندی: use case، جزئی‌ترین ابزار لایه‌ی مأموریته — لیست گام‌های بازیگر و سیستم برای رسیدن به یه هدف، همراه با پیش‌شرط، تضمین، محرک، دنباله‌ی اصلی (روز آفتابی)، مسیرهای جایگزین/توسعه/استثنا. تمرکز رو بذار روی مهم‌ترین و پرریسک‌ترین قسمت‌های سیستم، نه پوشش همه‌ی حالت‌های ممکن.
