## تعریف

**ارجاع مشترک (shared reference)** یعنی دو متغیر به یک شیء در حافظه اشاره کنند — آدرس یکسان.

```python
a = 10
b = a       # a's reference (not its value) is given to b
```

همین اتفاق موقع فراخوانی تابع می‌افتد: `my_func(t)` یعنی پارامتر `v` داخل تابع به همان شیء `t` اشاره می‌کند. پس ارجاع مشترک چیز نادری نیست؛ هر بار که تابعی صدا می‌زنی رخ می‌دهد.

## ارجاع مشترکی که خودت نساخته‌ای

```python
a = 10
b = 10
a is b           # True

s1 = "hello"
s2 = "hello"
s1 is s2         # True
```

انتظار داشتی `b` شیء جدیدی باشد، ولی memory manager پایتون **خودش** آن‌ها را به یک شیء اشاره داد. چرا این کار را می‌کند، چند درس بعد (interning). سؤال الان: **آیا امن است؟**

بله — چون این اشیا **immutable**‌اند. تنها راه «تغییر» `b` این است که ارجاعش به شیء دیگری برود، و این `a` را دست نمی‌زند:

```python
>>> b = "hello world"
>>> a
'hello'
```

## با mutable باید مراقب بود

```python
a = [1, 2, 3]
b = a
b.append(100)
a          # [1, 2, 3, 100]
```

`b` و `a` یک لیست‌اند. تغییر یکی، تغییر دیگری است. برای همین memory manager **هرگز** برای اشیای mutable به‌طور خودکار ارجاع مشترک نمی‌سازد:

```python
a = [1, 2, 3]
b = [1, 2, 3]
a is b     # False — two separate objects with equal value
```

همین اتفاق وقتی لیست را به تابع پاس می‌دهی می‌افتد: تابع ارجاع مشترکی به لیست تو دارد و می‌تواند تغییرش دهد. گاهی این دقیقاً چیزی است که می‌خواهی (sort درجا، بدون return و انتساب دوباره)؛ گاهی یک باگ پنهان است.

## به ارجاع مشترک خودکار تکیه نکن

```python
a = 500
b = 500
a is b     # False
```

برای ۱۰ ارجاع مشترک ساخت، برای ۵۰۰ نه. کِی و چرا، در درس interning. تا آن موقع: قانونش را حفظ نکن، فقط بدان که *گاهی* اتفاق می‌افتد و نباید رویش حساب کنی.
