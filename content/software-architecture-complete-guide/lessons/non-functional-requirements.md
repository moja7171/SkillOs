## نیازمندی‌های غیرکارکردی

قبلاً توضیح دادیم نیازمندی‌های غیرکارکردی چی هستن، ولی بذار برای اطمینان دوباره مرورشون کنیم. نیازمندی‌های کارکردی می‌گن سیستم چیکار باید بکنه؛ نیازمندی‌های غیرکارکردی می‌گن سیستم با چی باید کنار بیاد.

سیستم‌ها توی عملیاتشون با چالش‌های زیادی روبه‌رو می‌شن: تعداد زیاد کاربر همزمان، کرش‌کردن سرور، بار سنگین درخواست‌ها، و بیشتر. نیازمندی‌های غیرکارکردی اساساً محیط مورد انتظار سیستم رو توصیف می‌کنن، با تأکید ویژه روی حالت‌های حدی (edge cases).

اگه صفحه‌ی ویکی‌پدیا برای نیازمندی‌های غیرکارکردی رو ببینی، یه لیست بلندبالا پیدا می‌کنی. ولی توی دنیای واقعی، معمولاً پنج نیازمندی غیرکارکردی هست که همیشه باهاشون سروکار داری: **performance**، **load**، **حجم داده**، **کاربران همزمان** و **SLA**. بیا هر کدوم رو با هم ببینیم.

### Performance

به نظر ساده میاد، نه؟ «حداکثر سرعت مورد نیاز چیه؟ سریع، تمام!» ولی نه، این‌قدرها هم ساده نیست. وقتی درباره‌ی performance حرف می‌زنیم، دو نکته باید همیشه توی ذهنمون باشه: یک، همیشه با عدد صحبت کن؛ دو، latency و throughput.

**همیشه با عدد صحبت کن.** وقتی مشتری می‌خواد سیستم سریع باشه، سؤال بعدیت باید این باشه: «سریع یعنی چقدر؟» سریع می‌تونه توی سیستم‌های مختلف معنی‌های خیلی متفاوتی داشته باشه — بعضی سیستم‌ها «سریع» یعنی ۳۰ میلی‌ثانیه، بعضی‌ها یعنی ۵ ثانیه. مشتری احتمالاً به عدد دقیق فکر نکرده و باید کمکش کنی به یه عدد برسه. قاعده‌ی سرانگشتی: وقتی کاربر نهایی توی انتهای جریانه، معمولاً باید کار زیر یه ثانیه تموم بشه؛ توی محیط B2B (کسب‌وکار به کسب‌وکار)، معمولاً سیستم‌های سریع‌تری می‌خوایم — گاهی حتی ۱۰۰ میلی‌ثانیه برای هر کار. دلیلش اینه که ما آدم‌ها به تأخیرهای پی‌درپی خیلی حساس نیستیم — داده‌ای که یک ثانیه یا ۷۰۰ میلی‌ثانیه نمایش داده بشه، تقریباً برامون یکیه؛ ولی همون تفاوت برای نرم‌افزاری که روی چرخه‌های CPU چند میلی‌ثانیه‌ای کار می‌کنه، خیلی زمانه. مهم‌ترین چیز اینه که این عدد رو با مشتری یا تحلیل‌گر سیستم مشخص کنی.

**Latency در مقابل Throughput.** این دو مفهوم دو دیدگاه متفاوت از performance بهمون می‌دن. **Latency** جواب این سؤاله: انجام یه کار واحد توی اپلیکیشن چقدر طول می‌کشه؟ مثلاً چقدر طول می‌کشه تا API داده‌ی کاربر رو توی دیتابیس ذخیره کنه؟ **Throughput** جواب یه سؤال کاملاً متفاوته: توی یه واحد زمانی مشخص، چند تا کار می‌شه انجام داد؟ مثلاً توی یک دقیقه، چند کاربر می‌شه ذخیره کرد؟

فرض کن latency ذخیره‌کردن داده‌ی کاربر ۱ ثانیه‌ست (نسبتاً کند، ولی برای بحث باهاش پیش می‌ریم). حالا throughput چیه؟ می‌تونیم فقط با latency بفهمیم چند کاربر توی یه دقیقه ذخیره می‌شن؟ جواب قطعاً نه. اگه اپلیکیشن خوب طراحی شده، روی سخت‌افزار قوی دیپلوی شده و از thread درست استفاده می‌کنه، شاید بتونه ۱۰۰۰ کاربر رو توی یه دقیقه ذخیره کنه. ولی اگه کد پر از باگ و نشتی حافظه باشه و هیچ concurrency‌ای نداشته باشه، حتی به throughput ۶۰ (یعنی latency ضرب‌در ۶۰ ثانیه) هم نمی‌رسیم. پس هر دوی این عددها باید توی نیازمندی performance ذکر بشن.

### Load

نیازمندی load، میزان بار یا حجم کاری‌ای که اپلیکیشن باید بدون کرش‌کردن تحملش کنه رو تعریف می‌کنه. تعریف دقیقش بستگی به نوع اپلیکیشن داره — برای یه اپلیکیشن مبتنی بر Web API، معمولاً به این شکل تعریف می‌شه: چند درخواست همزمان می‌تونه بدون کرش‌کردن دریافت بشه؟

این شاید شبیه throughput به نظر برسه، ولی فرقش اینه: throughput واحد زمانی رو تعریف می‌کنه، ولی load در دسترس‌بودن سیستم رو تعریف می‌کنه — یعنی سیستم باید بتونه بدون کرش‌کردن، اون بار رو مدیریت کنه، حتی اگه کند بشه. مثلاً نیازمندی performance می‌تونه بگه throughput باید ۱۰۰ درخواست در ثانیه باشه، ولی سیستم باید بتونه ۵۰۰ درخواست همزمان رو بدون کرش‌کردن مدیریت کنه، حتی اگه هر کدوم بیشتر از یه ثانیه طول بکشه. این تعریف مهمه چون بدترین چیزی که می‌تونه برای یه سیستم پیش بیاد، کرش‌کردن زیر بار سنگینه — کاربرها کندی رو تحمل می‌کنن، ولی کرش‌کردن رو نه.

بهترین روش اینه که همیشه به اعداد اوج (peak) نگاه کنی. مثلاً یه سایت فروشگاهی توی حالت عادی شاید ۲۰۰ درخواست همزمان داشته باشه، ولی توی جمعه‌ی سیاه بیشتر از ۲۰۰۰ درخواست همزمان. باید برای حالت حدی برنامه‌ریزی کنی، چون دقیقاً همون‌جاست که مهم‌تره سیستم زنده و فعال بمونه.

### حجم داده (Data Volume)

این نیازمندی تعیین می‌کنه سیستم توی طول زمان چقدر داده (به گیگابایت یا ترابایت) جمع می‌کنه. این نیازمندی چند دلیل مهم داره: تعیین می‌کنه چه نوع دیتابیسی باید استفاده بشه (چون همه‌ی دیتابیس‌ها به یه اندازه حجم زیاد رو مدیریت نمی‌کنن)، نوع کوئری‌هایی که می‌نویسی رو مشخص می‌کنه (کوئری روی جدول ۱۰۰ هزار ردیفی کاملاً با کوئری روی جدول ۱۰۰ میلیون ردیفی فرق داره)، و کمک می‌کنه فضای ذخیره‌سازی رو از قبل برنامه‌ریزی کنی.

حجم داده معمولاً دو بُعد داره: یک، چقدر داده روز اول لازمه؛ دو، پیش‌بینی رشد داده چیه. مثلاً یه سیستم شاید روز اول ۵۰۰ مگابایت لازم داشته باشه و انتظار بره سالانه ۲ ترابایت رشد کنه. دوره‌ی رشد هم می‌تونه هفتگی، ماهانه یا فصلی تعریف بشه.

### کاربران همزمان (Concurrent Users)

این نیازمندی تعداد کاربرهایی که همزمان از سیستم استفاده می‌کنن رو تعریف می‌کنه. شبیه نیازمندی load به نظر می‌رسه، ولی یه فرق مهم داره: کاربران همزمان می‌گه چند کاربر دارن از سیستم استفاده می‌کنن، نه چند درخواست دارن اجرا می‌شن.

این تفاوت مهمه. وقتی یه کاربر داره از سیستم استفاده می‌کنه، خیلی وقت‌ها هیچ اتفاقی نمی‌افته. مثلاً کاربر داده‌ای رو درخواست می‌کنه، سیستم به دیتابیس می‌ره و داده رو برمی‌گردونه — این یه اکشن واقعیه. حالا کاربر داره داده رو نگاه می‌کنه — توی این مدت، سیستم هیچ کاری نمی‌کنه، API خاموشه، دیتابیس ساکته، شبکه ساکته. پس همون‌طور که حدس می‌زنی، سیستمی که می‌تونه ۵۰۰ درخواست همزمان رو تحمل کنه، می‌تونه تعداد خیلی بیشتری کاربر همزمان رو تحمل کنه. قاعده‌ی سرانگشتی می‌گه کاربران همزمان تقریباً ۱۰ برابر درخواست‌های همزمانه — پس اگه سیستم باید ۵۰۰ درخواست همزمان رو مدیریت کنه، می‌تونه ۵۰۰۰ کاربر همزمان رو پشتیبانی کنه. البته این عدد به نوع سیستم و الگوی استفاده هم بستگی داره.

### SLA

آخرین نیازمندی غیرکارکردی‌ای که بررسی می‌کنیم، SLA‌ست. SLA مخفف Service Level Agreement (توافق‌نامه‌ی سطح سرویس)، درصد آپ‌تایم مورد نیاز سیستم رو توصیف می‌کنه. این اصطلاح توی تقریباً همه‌ی ارائه‌دهنده‌های کلاود عمومی به‌کار می‌ره — یکی از بزرگ‌ترین رقابت‌ها بینشون سر همین SLA‌ست. مثلاً Azure Cosmos DB به SLA ۹۹٫۹۹٪‌ش افتخار می‌کنه — یعنی کمتر از یه ساعت downtime توی سال.

SLA تأثیر زیادی روی طراحی سیستم داره. مثلاً سیستمی که نباید هیچ‌وقت خاموش بشه، باید یه مکانیزم به‌روزرسانی پیچیده داشته باشه که نیازی به خاموش‌کردن سیستم موقع آپدیت نداشته باشه — شدنیه، ولی باید از اول همین‌طور طراحی بشه.

یه نکته‌ی مهم درباره‌ی SLA، انتظارات مشتریه. اگه از مشتری بپرسی SLA مورد نیاز سیستم چیه، معمولاً یه چیزی نزدیک به «۱۰۰٪» یا همون «۵ تا نه معروف» (۹۹٫۹۹۹٪) رو می‌گه. توی این حالت، معمولاً جواب می‌دم: «مشکلی نیست. برای این کار به حداقل سه دیتاسنتر توی قاره‌های مختلف نیاز داریم، با ایستگاه‌های برق مستقل و دوگانه و failover خودکار بینشون. نظرت چیه؟» این معمولاً مشتری رو به زمین برمی‌گردونه و از اونجا درباره‌ی اهداف SLA واقع‌بینانه‌تر صحبت می‌کنیم.

### جمع‌بندی

این‌ها رایج‌ترین نیازمندی‌های غیرکارکردی‌ای هستن که برای هر سیستمی لازم داری. و باز هم تأکید می‌کنیم: هیچ‌وقت قبل از تعیین این نیازمندی‌ها شروع به کار روی معماری نکن.
