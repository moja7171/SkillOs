## Event Sourcing

الگوی پیشرفته‌ی بعدی که بررسی می‌کنیم، Event Sourcing‌ـه. ولی اول، بیا نگاهی به مدیریتِ سنتیِ موجودیت‌ها بندازیم.

توی اپلیکیشن‌های سنتی، موجودیت‌ها توی دیتابیس، معمولاً به‌شکلِ یه مجموعه‌ی ویژگی، ذخیره می‌شن. وقتی اپلیکیشن باید یه ویژگیِ خاص رو آپدیت کنه، فقط بهش دسترسی پیدا می‌کنه و مقدارش رو تغییر می‌ده.

با Event Sourcing، این کار رو متفاوت انجام می‌دیم. وقتی Event Sourcing رو پیاده می‌کنیم، ویژگی‌های موجودیت رو تغییر نمی‌دیم. در عوض، **رویدادهای مربوط به موجودیت رو ردیابی می‌کنیم**.

شاید فهمیدنِ این مفهوم برات سخت باشه، ولی راستش توی خیلی از جاهایی که دورت هست، این الگو رو می‌بینی. بهترین مثالِ Event Sourcing، حسابِ بانکیته. به صورت‌حسابِ حسابِ بانکیت فکر کن — احتمالاً یه چیزی شبیهِ یه لیست از تراکنش‌هاست، هر کدوم با تاریخ، شرح و مبلغ. این یه مثالِ عالی از Event Sourcing‌ـه. توجه کن اینجا یه موجودیت با چند فیلدِ داده نمی‌بینی. چیزی که می‌بینی، یه لیست از رویدادهاییه که برای موجودیت — که توی این حالت حسابِ بانکیه — اتفاق افتادن. خودِ موجودیت رو نمی‌بینی، فقط رویدادها رو می‌بینی.

### کِی از Event Sourcing استفاده کنیم؟

حساب بانکی فقط یه مثاله. Event Sourcing داره توی کاربردهای زیادی گسترش پیدا می‌کنه. پس بهترین کاندیداها برای استفاده از Event Sourcing کیان؟

مثالِ واضح، وقتیه که **تاریخچه مهمه**. اگه نه‌فقط وضعیتِ فعلیِ موجودیت، بلکه چطور به این وضعیت رسیده هم برات مهمه، Event Sourcing یه انتخابِ طبیعیه. با Event Sourcing، یه دیدِ کاملِ از هر چیزی که برای یه موجودیتِ خاص از لحظه‌ی ساختش اتفاق افتاده داری، و می‌تونی ازش کلی بینش استخراج کنی.

ولی Event Sourcing برای انواع دیگه‌ی اپلیکیشن هم مفیده. بیا مزایا و معایبش رو بررسی کنیم.

### مزایا

**۱. ردیابی.** قبلاً بهش اشاره کردیم — با Event Sourcing، به‌راحتی می‌تونی همه‌ی رویدادهایی که برای موجودیت اتفاق افتادن رو ردیابی کنی.

**۲. مدلِ داده.** با Event Sourcing، مدلِ داده‌ت فوق‌العاده ساده می‌شه. معمولاً باید موجودیت‌های پیچیده با رابطه‌های به موجودیت‌های دیگه طراحی کنی؛ ولی اینجا، تنها کاری که برای گرفتنِ وضعیتِ موجودیت لازمه، عبور از رویدادهاش و ساختنِ یه وضعیتِ موقتی از روشونه.

**۳. Performance.** برای تغییرِ وضعیتِ موجودیت، فقط باید یه رکوردِ کوچیک به دیتاستور اضافه کنی. همین — نیازی به آپدیت‌کردنِ کلی جدول یا اعمالِ محدودیتِ کلیدِ خارجی نیست. یه دستورِ insert ساده و کارت راه میفته.

**۴. گزارش‌گیری.** خیلی از گزارش‌های کسب‌وکاری به تاریخچه‌ی موجودیت‌ها نیاز دارن. با Event Sourcing، این کار خیلی راحته — تاریخچه از قبل توی داده تعبیه شده و فقط باید بازیابیش کنی.

### معایب

بارزترینش اینه که **هیچ دیدِ یکپارچه و واحدی از موجودیت نداری**. می‌خوای وضعیتِ فعلیِ موجودیت رو ببینی؟ باید از رویدادها عبور کنی و وضعیتِ فعلی رو بسازی. این می‌تونه زمان و منابع بگیره.

ضعفِ دوم، **مصرفِ فضای ذخیره‌سازیه**. اگه یه موجودیت تاریخچه‌ی طولانی داشته باشه، رویدادهاش فضای ذخیره‌سازیِ زیادی می‌گیرن، و وقتی کلی موجودیت با تاریخچه‌ی بزرگ داری، می‌تونه به مشکل تبدیل بشه.

### جمع‌بندی

نتیجه‌ش اینه: همه‌ی اپلیکیشن‌ها نباید از Event Sourcing استفاده کنن، ولی اگه به ردیابیِ قویِ موجودیت‌هات نیاز داری و از ایده‌ی یه مدلِ داده‌ی یکپارچه خوشت میاد، قطعاً یه نگاهی به Event Sourcing بنداز.

الگوی بعدیمون، مکملِ Event Sourcing‌ـه و چند تا از ضعف‌هاش رو حل می‌کنه.
