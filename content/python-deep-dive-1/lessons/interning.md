> این درس سه ویدیو دارد: interning اعداد، interning رشته‌ها، و بهینه‌سازی peephole. همه‌ی این‌ها **مخصوص CPython** هستند (پیاده‌سازی مرجع، نوشته‌شده به C). پیاده‌سازی‌های دیگر — Jython (روی JVM)، IronPython (روی .NET)، PyPy (نوشته‌شده به RPython) — می‌توانند رفتار متفاوتی داشته باشند. نسخه‌ی CPython هم اثر دارد.

## ۱. Interning اعداد صحیح

دیدیم `a = 10; b = 10` → `a is b` درست است ولی `a = 500; b = 500` → غلط. با اینکه اشتراک‌گذاری برای هر int امن است (immutable)، پایتون فقط برای بعضی این کار را می‌کند. دلیل: **interning** = استفاده‌ی مجدد از اشیا به‌جای ساختن.

CPython موقع شروع، اعداد **−۵ تا ۲۵۶** را از قبل می‌سازد و کش می‌کند. هر بار که عددی در این بازه لازم شود، به‌جای ساختن، همان شیء کش‌شده استفاده می‌شود — عملاً این اعداد **singleton**‌اند. چرا این بازه؟ اعداد کوچک خیلی پرتکرارند؛ کش کردن بیشتر، حافظه و زمان راه‌اندازی می‌خورد.

```python
a = 256;  b = 256;  a is b     # True
a = 257;  b = 257;  a is b     # False
a = -5;   b = -5;   a is b     # True
a = -6;   b = -6;   a is b     # False

a = 10; b = int(10); c = int("10"); d = int("1010", base=2)
id(a) == id(b) == id(c) == id(d)    # True — مهم نیست چطور ساخته شد
```

## ۲. Interning رشته‌ها

بعضی رشته‌ها هم intern می‌شوند — نه همه. موقع کامپایل کد، همه‌ی **identifier**ها (نام متغیر/تابع/کلاس) intern می‌شوند، و به‌طور کلی هر رشته‌ی literal که **شبیه identifier** باشد (فقط حرف، رقم، زیرخط):

```python
a = "hello";        b = "hello";        a is b   # True
a = "hello world";  b = "hello world";  a is b   # False (فاصله دارد)
a = "this_is_a_long_string_that_could_be_an_identifier"
b = "this_is_a_long_string_that_could_be_an_identifier"
a is b   # True — طول مهم نیست، شکل مهم است
```

چرا؟ پایتون مدام باید نام‌ها را در دیکشنری‌ها جست‌وجو کند — یعنی مقایسه‌ی رشته. مقایسه‌ی دو رشته‌ی intern‌شده با `is` فقط مقایسه‌ی دو عدد (آدرس) است؛ خیلی سریع‌تر از مقایسه‌ی کاراکتر‌به‌کاراکتر با `==`.

**روی interning خودکار حساب نکن.** اگر لازمش داری، خودت انجام بده:

```python
import sys
a = sys.intern("hello world")
b = sys.intern("hello world")
c = "hello world"
a is b     # True
a is c     # False — c intern نشده؛ باید *همه‌ی* نمونه‌ها را intern کنی
```

کِی؟ وقتی تعداد **خیلی** زیادی مقایسه‌ی رشته داری (مثلاً tokenize کردن یک پیکره‌ی متنی بزرگ با تکرار زیاد — NLP). مدرس با یک benchmark ساده (۱۰ میلیون مقایسه) نشان می‌دهد `==` روی رشته‌ی بلند حدود ۴ ثانیه و `is` روی نسخه‌ی intern‌شده حدود ۰٫۴ ثانیه طول می‌کشد. ولی خود intern کردن هزینه دارد؛ برای چند مقایسه ارزش ندارد. **تا لازم نشده بهینه نکن.**

## ۳. بهینه‌سازی Peephole

اتفاق سوم موقع **کامپایل** می‌افتد (کد پایتون قبل از اجرا به bytecode کامپایل می‌شود و تا برنامه زنده است همان نسخه استفاده می‌شود):

**عبارت‌های ثابت** از قبل محاسبه می‌شوند. `minutes = 24 * 60` را برای خوانایی همین‌طور بنویس؛ پایتون خودش `1440` را ذخیره می‌کند. برای دنباله‌های کوتاه (کمتر از ۲۰ عنصر) هم همین‌طور: `(1, 2) * 5`، `"abc" * 3`، `"hello" + " world"`. ولی `"the quick brown fox" * 10` (بلندتر از ۲۰) و `["a", "b"] * 3` (لیست، mutable → ثابت نیست) پیش‌محاسبه نمی‌شوند.

```python
def my_func():
    a = 24 * 60
    b = (1, 2) * 5
    c = "abc" * 3
    d = "ab" * 11          # ۲۲ کاراکتر — نه
    e = ["a", "b"] * 3     # لیست — نه

my_func.__code__.co_consts
# (None, 1440, (1, 2, 1, 2, 1, 2, 1, 2, 1, 2), 'abcabcabc', 'ab', 11, 'a', 'b', 3)
```

**تست عضویت** با collection ثابت هم بهینه می‌شود: `if e in [1, 2, 3]` → لیست به tuple تبدیل می‌شود، `if e in {1, 2, 3}` → set به frozenset.

و نکته‌ی کاربردی: **عضویت در set خیلی سریع‌تر از list/tuple است** (set مثل dict با hash کار می‌کند؛ list باید عنصر‌به‌عنصر بگردد). benchmark مدرس روی ۱۰ میلیون تست `'z' in container` روی حروف ASCII: list ≈ ۵٫۳ ثانیه، tuple ≈ ۵٫۳ ثانیه، set ≈ ۰٫۵ ثانیه. اگر تست عضویت را در حلقه‌ای داغ می‌نویسی، از set استفاده کن.
