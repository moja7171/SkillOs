## لایه‌ها

اگه فیلم پنجم Shrek رو دیده باشی، احتمالاً صحنه‌ی معروف «لایه‌ها» رو یادته — جایی که Shrek سعی می‌کنه به Donkey توضیح بده که غول‌ها، مثل هر موجود زنده‌ی دیگه‌ای، لایه دارن و موجودات شرور یک‌بعدی نیستن. این یکی از خنده‌دارترین صحنه‌های فیلمه.

خب، همین حرف برای معماری نرم‌افزار هم صادقه، چون یه جزء نرم‌افزاریِ خوب، دقیقاً مثل غول‌های محبوب، همیشه لایه داره. البته شکل لایه‌ها توی نرم‌افزار با هیولاها خیلی فرق داره — لایه‌ها توی یه جزء نرم‌افزاری، کارکرد افقیِ کد رو نشون می‌دن.

### سه اکشن پایه

معمولاً اجزای نرم‌افزاری سه اکشن پایه انجام می‌دن:

۱. **در معرض دید قراردادنِ کارکرد نرم‌افزار** از طریق یه نوع رابط — معمولاً API یا رابط کاربری، بسته به نوع اپلیکیشن.
۲. **اجرای منطق** روی داده‌ای که از کاربر دریافت می‌شه — این منطق معمولاً شامل اعتبارسنجی، پردازش، محاسبات اضافی، غنی‌سازی و بیشتره.
۳. **ذخیره و بازیابیِ داده** توی/از دیتاستور.

این سه اکشن معمولاً به‌شکل لایه نمایش داده می‌شن، و هر لایه اسم خودش رو داره:

- **UI (User Interface)** یا **SI (Service Interface):** اگه جزء رابط کاربری داره UI، اگه API در معرض دید می‌ذاره SI.
- **BL (Business Logic):** منطق کسب‌وکار.
- **DAL (Data Access Layer):** لایه‌ی دسترسی به داده.

هر لایه از کلاس‌های مختلفی تشکیل شده که وظیفه‌ی مشخص همون لایه رو انجام می‌دن. مثلاً لایه‌ی DAL کلاس‌هایی داره که باز‌کردن اتصال به دیتاستور، کوئری‌زدن، ذخیره‌ی داده، مدیریت تراکنش و بیشتر رو انجام می‌دن. لایه‌ی BL کلاس‌هایی داره که اعتبارسنجی، غنی‌سازی و محاسبات رو انجام می‌دن. لایه‌ی SI کلاس‌هایی داره که API رو در معرض دید می‌ذارن، اسناد JSON رو به آبجکت تبدیل می‌کنن، احراز هویت و مجوزدهی رو مدیریت می‌کنن و بیشتر.

### چرا اصلاً لایه‌بندی می‌کنیم؟

**اول:** تو رو مجبور می‌کنه کدی بنویسی که خوش‌فرم و متمرکزه. معمولاً ایده‌ی بدیه که یه متد چندین کار رو با هم انجام بده (بعداً توی همین بخش بیشتر درباره‌ش حرف می‌زنیم). با تقسیم کد به لایه‌های مشخص، هر بخش فقط با هدف لایه‌ی خودش سروکار داره.

**دوم:** یه جزءِ لایه‌بندی‌شده، یه جزءِ ماژولاره. یادت باشه، ماژولاریته رو به‌عنوان یکی از مهم‌ترین ویژگی‌های کیفیِ نرم‌افزار بررسی کردیم — و با پیاده‌کردن لایه‌ها، جزءمون دقیقاً همین می‌شه: ماژولار. با فرض اینکه ارتباط بین لایه‌ها به‌درستی انجام بشه (که الان بهش می‌رسیم)، جایگزین‌کردن لایه‌ها خیلی راحت می‌شه. مثلاً اگه پیاده‌سازی فعلیِ DAL روی SQL Server کار می‌کنه و می‌خوای به MongoDB سوییچ کنی، توی یه جزءِ لایه‌بندی‌شده‌ی خوب، فقط لازمه لایه‌ی DAL رو عوض کنی و لایه‌های دیگه دست‌نخورده می‌مونن.

### سه مفهومی که باید رعایت کنی

**۱. جریان کد (Code Flow):** یه لایه فقط می‌تونه لایه‌ی دقیقاً زیر خودش رو صدا بزنه. یعنی مثلاً کدِ لایه‌ی SI فقط می‌تونه کدِ لایه‌ی BL رو صدا بزنه، هیچ‌وقت مستقیم لایه‌ی DAL رو. همچنین، یه لایه هیچ‌وقت نمی‌تونه لایه‌ی بالای خودش رو صدا بزنه — مثلاً DAL هیچ‌وقت کدِ BL رو صدا نمی‌زنه. هدف اینه که جداییِ بین لایه‌ها تا حد ممکن سفت‌وسخت بمونه. اگه اجازه بدیم لایه‌ها رد بشن، یعنی مثلاً SI از DAL خبر داره، و این یعنی هر تغییری توی DAL، لزوماً روی SI هم اثر می‌ذاره — که کل جزء رو خیلی کمتر ماژولار می‌کنه.

**۲. اتصال سست (Loose Coupling):** توی درس بعدی بیشتر درباره‌ش حرف می‌زنیم، ولی فعلاً کافیه بدونی که لایه‌ها باید طوری با هم ارتباط برقرار کنن که موقع تغییر، کمترین تأثیر رو داشته باشه. یه مثال ساده: فرض کن این کد توی لایه‌ی BL هست که DAL رو صدا می‌زنه:

```csharp
// strong coupling — direct reference to the DAL class
var dal = new SqlOrderRepository();
var order = dal.GetOrder(orderId);
```

با اینکه پیاده‌سازیش راحته، این ارجاع مستقیم بین لایه‌ها باعث می‌شه به‌شدت به هم وابسته (strongly coupled) بشن. یعنی اگه بخوای به یه DAL دیگه سوییچ کنی، باید هر جایی که این کلاس رو از BL ارجاع داده کد رو تغییر بدی — و این بده.

روش درست، ارجاع لایه‌ها از طریق **تزریق وابستگی (dependency injection)**ـه — جایی که لایه‌ی فراخوان فقط به یه اینترفیس که کارکرد موردنظر رو نشون می‌ده ارجاع می‌ده، نه خودِ کلاس مشخص:

```csharp
// loose coupling — refers only to the interface
IOrderRepository dal = OrderRepositoryFactory.GetInstance();
var order = dal.GetOrder(orderId);
```

بعداً وقتی به یه پیاده‌سازی دیگه سوییچ کنیم، کدِ BL اصلاً تحت‌تأثیر قرار نمی‌گیره، چون از اول به DAL ارجاع نداده بود. این مفهوم، تزریق وابستگی نام داره و بعداً توی همین بخش دقیق‌تر بررسیش می‌کنیم.

**۳. مدیریت استثنا بین لایه‌ها:** برخلاف دو مفهوم قبلی که نسبتاً شناخته‌شده‌ان، این یکی کمتر شناخته‌شده‌ست و همه‌ی معمارها باهاش آشنا نیستن. این مفهوم می‌گه هر لایه باید استثناهای درونیش رو مخفی کنه و اجازه نده لایه‌های بالاتر ازشون خبردار بشن — بلکه باید بهشون یه پیام خطای عمومی و غیراختصاصی بده.

مثلاً فرض کن DAL ما با MySQL کار می‌کنه. استثناهای دیتابیس معمولاً خیلی مشخص‌ان، که خوبه چون کمک می‌کنه مشکل رو دقیق پیدا کنیم و درستش کنیم. مشکل اینجاست که این استثنا به‌شکل یه کلاس استثناییِ MySQL پرتاب می‌شه و اطلاعاتی درباره‌ی کارکرد درونیِ دیتابیس توش هست. یکی از مهم‌ترین مفاهیم معماریِ لایه‌ای اینه که هر لایه کپسوله‌ست و اطلاعاتی از کارکرد درونیش بیرون نمی‌ده. اگه DAL این استثنا رو پرتاب کنه، یعنی BL می‌فهمه DAL از MySQL استفاده می‌کنه — درحالی‌که باید کاملاً بی‌خبر از این موضوع باشه.

پس الگوی درست اینه که DAL خودش استثنا رو تحلیل کنه، توی لاگ بنویسدش، و یه استثنای جدید — مثلاً `DataException` — با یه پیام خطای عمومی («مشکلی توی دسترسی به ذخیره‌سازی داده پیش اومد») بسازه. این‌طوری، تنها چیزی که BL می‌دونه اینه که DAL یه مشکلی توی اکشن‌های دیتا داره — که کاملاً کافیه، چون این تنها چیزیه که BL باید درباره‌ی DAL بدونه.

### لایه (Layer) در مقابل لایه‌ی توزیع‌شده (Tier)

احتمالاً اصطلاح «اپلیکیشن n-tier» یا «سه‌لایه» (three-tiered) رو شنیدی و شاید فکر کردی همون معنی «لایه» رو داره. ولی این‌طور نیست — یه فرق بزرگ بینشون هست.

**لایه (Layer)** همونیه که درباره‌ش حرف زدیم — تکه‌کدی که بخشی از یه جزء نرم‌افزاریه. یادت باشه، یه جزء، مجموعه‌کدیه که توی یه فرایند واحد اجرا می‌شه — هیچ شبکه‌ای بین کلاس‌های مختلفِ جزء دخیل نیست و همه‌شون یه منبع محاسباتی رو مشترک استفاده می‌کنن.

**Tier**، در مقابل، یه تکه‌کدِ توزیع‌شده‌ست — مستقل دیپلوی می‌شه و از طریق پروتکل‌های شبکه‌ای مثل HTTP با بقیه ارتباط برقرار می‌کنه. پس وقتی می‌گیم یه اپلیکیشن سه‌tier‌ـه، در واقع منظورمون اینه که اپلیکیشن سه جزء مستقلِ دیپلوی‌شده روی شبکه داره که با هم از طریق شبکه ارتباط دارن — که کاملاً با لایه‌ها که همه بخشی از یه فرایند واحدن، فرق داره.

### جمع‌بندی

این‌طوری بحث لایه‌ها رو تموم می‌کنیم. یادت باشه که لایه‌بندی تقریباً همیشه ایده‌ی خوبیه و باید الگوی پیش‌فرضت برای پیاده‌سازی اجزا باشه.
